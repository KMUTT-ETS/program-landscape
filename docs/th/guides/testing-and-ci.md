# การทดสอบและ CI

> **English:** [English version](../../guides/testing-and-ci.md)

**ผลลัพธ์** ท่านรันชุดการทดสอบได้ รู้ว่าการทดสอบปกป้องอะไร และทำให้ CI บน fork ของท่านผ่านได้

## การรันการทดสอบ

| คำสั่ง | ขอบเขต |
|---|---|
| `pnpm test` | Vitest ทุก workspace — 118 ไฟล์ทดสอบ ประมาณ 1,400 เคส |
| `pnpm e2e` | Playwright (`apps/web/e2e/`) — ต้องรัน `npx playwright install` ก่อน |
| `pnpm lint` | ESLint ทั่ว `apps/**` และ `packages/**` |
| `pnpm typecheck` | `tsc --noEmit` ทุก workspace |
| `pnpm check` | lint + typecheck + test **รันก่อน commit ทุกครั้ง** |
| `pnpm ai:eval` | ชุดประเมิน AI ด้วยคำถามมาตรฐาน 25 ข้อ |

การรัน `pnpm test` เต็มชุดจะรายงานจำนวนเคสมากกว่าตัวเลข 1,400 ที่ระบุไว้ข้างบน เพราะ `.each` ขยายหนึ่งเคสออกเป็นหลายเคส

## การทดสอบเหล่านี้ปกป้องอะไรอยู่จริง ๆ

ชุดทดสอบนี้เอนไปทาง **ฟังก์ชันบริสุทธิ์ที่บรรจุนโยบายไว้ข้างใน** มากกว่าการทดสอบเชิงบูรณาการอย่างเห็นได้ชัด ได้แก่ กราฟการเปลี่ยนสถานะและการกั้นตามบทบาท การจัดการค่าว่างของคะแนนสุขภาพ การจับคู่ใน transform ของ connector เคสขอบเรื่องลำดับ prefix ในการจับคู่ตำแหน่งทางวิชาการ ratchet test ของมาตรฐาน prompt โครงสร้างเกณฑ์ AUN-QA และรูปแบบการปฏิเสธคำถามที่ไม่ปลอดภัย นี่เป็นการเลือกโดยตั้งใจ เพราะจุดเหล่านี้คือจุดที่การถดถอยแบบเงียบ ๆ จะเปลี่ยนสิ่งที่สภามหาวิทยาลัยได้รับฟัง

ตอนเขียน connector ของตัวเอง ให้ทำตามแพตเทิร์นเดิม: วาง fixture ไว้ที่ `apps/ingestion/test/fixtures/<slug>/` และเขียน transform test ที่ยืนยันว่าทุกรหัสใน fixture มีการจับคู่ ตัวอย่างที่ควรยึดคือ test ที่ครอบคลุมการจับคู่สถานะของ `kku-registry` ซึ่งกันไม่ให้สำนักทะเบียนเพิ่มรหัสสถานะใหม่เข้ามาแบบเงียบ ๆ

## CI

`.github/workflows/` มี workflow สี่ตัว: `pr.yml`, `release.yml`, `e2e.yml`, `load.yml`

`pr.yml` ทำตามลำดับนี้: รัน migration linter เพื่อหา DDL ที่ทำลายข้อมูล, lint **เฉพาะไฟล์ที่เปลี่ยน**, ตรวจ type, รัน Prisma generate, ยก Postgres พร้อม pgvector ขึ้นมา, apply migration ลงฐานข้อมูลทดสอบ แล้วจึงรันชุดทดสอบ

**สถานะที่รับสืบทอดมา:** `PR checks` เขียวทั้งชุด ส่วน `Release bundle` (ตอน push tag) รัน `pnpm lint` ทั้ง repo และ **แดงเพราะหนี้ lint ที่ค้างอยู่ก่อนแล้ว** ไม่ใช่เพราะการเปลี่ยนแปลงชิ้นใดชิ้นหนึ่ง ตัว tarball แบบ pack-and-ship ที่สร้างบนเครื่องคือ artifact จริงของการปล่อยเวอร์ชัน ควรเคลียร์หนี้ก้อนนั้นแต่เนิ่น ๆ เพื่อให้ป้าย CI สีแดงใน fork ของคุณมีความหมาย
