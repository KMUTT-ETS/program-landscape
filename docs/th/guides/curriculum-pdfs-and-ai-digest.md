# เอกสารหลักสูตรและ pipeline การสรุปด้วย AI

> **English:** [English version](../../guides/curriculum-pdfs-and-ai-digest.md)

**ผลลัพธ์** ท่านนำเข้า PDF หลักสูตร รัน pipeline สรุปด้วย AI สร้างอนุกรมวิธานทักษะ และตั้งงบค่าใช้จ่ายได้

ส่วนนี้คือกลไกที่เปลี่ยนกอง PDF หลักสูตรให้กลายเป็นข้อมูลหลักสูตรที่มีโครงสร้างและค้นได้ เป็นส่วนที่มีมูลค่าสูงที่สุดส่วนหนึ่งของแพลตฟอร์ม และย้ายไปใช้ที่สถาบันอื่นได้แทบไม่ต้องแก้

## ลำดับการทำงาน

```
Curriculum PDF  →  MinIO + PdfDocument row (content-hash deduped)
                →  AI digest (program-digest.v1)
                →  AiExtraction row: AUTO_APPROVED when its confidence clears
                   AI_AUTO_APPROVE_THRESHOLD (code default 0), else PENDING_REVIEW
                   until a human approves it
                →  materialised onto Program + ProgramSkill rows
                   (ProgramSkill only for names that exactly match the taxonomy)
                →  unmatched skill names → PROPOSED_SKILL extractions
                →  pnpm skills:normalise --source=program_digest → new Skill rows
```

## คำสั่ง

| คำสั่ง | ใช้ทำอะไร |
|---|---|
| `pnpm pdf:bulk-load <manifest.jsonl>` | นำเข้าข้อมูลย้อนหลังครั้งเดียว ค่าตั้งต้นเป็น dry-run ใส่ `--commit` เพื่ออัปโหลดจริง |
| `pnpm programs:digest <code\|mhesi\|seq>` | สรุปหลักสูตรเดียว |
| `pnpm programs:digest-bulk [--limit N] [--level X]` | ทำเป็นชุด และทำต่อจากที่ค้างไว้ได้เอง |
| `pnpm programs:approve-pending` | อนุมัติและเขียนผลสรุปที่ยังเป็น `PENDING_REVIEW` ทั้งหมดลงฐานข้อมูล ผลสรุปที่อนุมัติอัตโนมัติถูกเขียนลงไปแล้วตั้งแต่ตอนสร้าง จึงไม่เขียนซ้ำ |
| `pnpm skills:normalise --source=<linkedin\|program_digest> --auto-promote` | สร้างอนุกรมวิธานทักษะ ดู [การสร้างอนุกรมวิธานทักษะของคุณ](#การสร้างอนุกรมวิธานทักษะของคุณ) |
| `pnpm programs:pipeline <code>` | pipeline เต็มรายหลักสูตร (อธิบายด้านล่าง) |
| `/admin/programs/from-pdf` | หน้าจอนำส่งสำหรับผู้ดูแล — หลักสูตรใหม่ *หรือ* ฉบับปรับปรุง |
| `/admin/programs/[id]?tab=files` | แนบ PDF ผ่านหน้าจอ |

ให้แนบ PDF ผ่านหน้าจอหรือผ่าน `pdf:bulk-load` เท่านั้น — มข. เคยมีตัวจับคู่ชื่อไฟล์แบบคลุมเครือเพื่อผูก PDF ที่ไม่มีเจ้าของเข้ากับหลักสูตร **แต่เลิกใช้ไปแล้วหลังจากมันผูกผิดไปราว 30 หลักสูตร** และต้องมาตรวจสอบด้วยเนื้อหาเพื่อแก้กลับทีหลัง อย่าสร้างขึ้นมาใหม่

## pipeline ฉบับเต็ม

`pnpm programs:pipeline <code|seq|id>` (หรือ `--all [--limit=N]`) รวบสิ่งที่เคยเป็นสคริปต์เก้าตัวที่ต้องรันมือไว้ด้วยกัน เรียงตามลำดับการพึ่งพา ฉบับที่เป็นทางการอยู่ในส่วนหัวของ `apps/ingestion/src/scripts/programs-pipeline.ts` สรุปคร่าว ๆ ได้ว่า:

| เฟส | ทำอะไร | หมายเหตุ |
|---|---|---|
| 1 | สกัดข้อมูลจาก PDF ด้วย AI — ผลสรุป อาจารย์ ทักษะ วิธีการสอน | รันขนานกัน |
| 2 | อนุมัติแล้วเขียนผลสรุปลง `ProgramSkill` | แตะเฉพาะฐานข้อมูล เร็ว |
| 2b | สกัดรหัสรายวิชาแบบเจาะจง | แทนที่รายการรายวิชาที่ถูกตัดสั้นในผลสรุป ด้วยรายการเต็ม 40–90 รายวิชา |
| 3 | จับคู่เส้นทางอาชีพ และจับคู่อุปสงค์ | ทำตามลำดับ |
| 4 | เชื่อมข้อมูลของสถาบัน — รุ่นนักศึกษา ศิษย์เก่า การเงิน | ขนานกัน และวิ่งไปที่ระบบสำนักทะเบียน/การเงินของคุณ |
| 6 | ประเมินความพร้อมด้าน AI | **รันก่อนเฟส 5** เพราะทั้งเฟส 5 และ 7 ใช้คะแนนจากเฟสนี้ |
| 5 | เลือกคู่เทียบ และทำ peer review | ทำตามลำดับ |
| RE | ความเชี่ยวชาญด้านการวิจัย | **insert อย่างเดียว** ถ้ามีอยู่แล้วให้ข้าม ไม่มีการสร้างใหม่อัตโนมัติ |
| 8 | วิเคราะห์ความเสี่ยง | การคำนวณแบบกำหนดผลได้แน่นอน บวกคำบรรยาย |
| 7 | เรื่องเล่าเชิงกลยุทธ์ | **รันเป็นเฟสสุดท้าย** ใช้ผลจากทุกเฟสก่อนหน้า รวมถึงผลวิเคราะห์ความเสี่ยง |

`--skip=phase4` คือแฟล็กที่ต้องใช้ตอนที่ connector ของสำนักทะเบียนยังไม่ได้ต่อ ส่วน `--only=phase5` รันเฟสเดียว

## ฉบับปรับปรุง — เมื่อ มคอ.2 ฉบับที่สองเข้ามา

กระบวนการข้างต้นคือการนำเข้าหลักสูตร *ครั้งแรก* เมื่อหลักสูตรมีอยู่ในระบบแล้ว มคอ.2 ฉบับใหม่ต้องไม่เขียนทับของเดิมดื้อ ๆ เพราะผลวิเคราะห์ที่สภามหาวิทยาลัยเห็นเมื่อเดือนก่อนจะเปลี่ยนไปใต้เท้าโดยไม่มีร่องรอยว่าเพราะอะไร แบบจำลองฉบับปรับปรุงมีไว้เพื่อการนี้ และเป็นส่วนของ pipeline นี้ที่คุ้มค่าแก่การลอกไปทั้งชุดที่สุด

`ProgramRevision` คือภาชนะพักงาน — มคอ.2 หนึ่งฉบับที่ผูกกับหลักสูตรหนึ่ง แล้วเดินผ่านสถานะ

```
DRAFT → ANALYSING → IN_REVIEW → APPROVED
                              ↘ REJECTED
(an approved revision later displaced by another) → SUPERSEDED
```

`Program.activeRevisionId` ชี้ไปที่ฉบับที่ใช้งานจริง ผลวิเคราะห์ทุกชิ้นที่ pipeline สร้าง — บทวิเคราะห์เชิงยุทธศาสตร์ ความพร้อมด้าน AI การจัดการเรียนการสอน การทาบทานกับสถาบันเทียบเคียง ความเชี่ยวชาญด้านวิจัย ทักษะ รายวิชา และตัวการเปรียบเทียบฉบับปรับปรุงเอง — ล้วนมี `programRevisionId` กำกับ หน้าหลักสูตรจึงแสดงหลักสูตรที่สอดคล้องกันภายในชุดเดียว และผลของฉบับที่ถูกแทนที่ยังอยู่ครบและระบุที่มาได้ แทนที่จะถูกเขียนทับ

สามเรื่องที่ควรยกไปด้วยหากจะสร้างกลไกนี้เอง

- **ข้อมูลกำกับหลักสูตรถูก "เสนอ" ไม่ใช่ "เขียนทับ"** เมื่อผลสรุปของฉบับปรับปรุงขัดกับค่าปัจจุบันของหลักสูตร `metadataProposalJson` จะบันทึกทั้งค่าที่เสนอและค่าเดิมที่จะถูกแทนที่ แทนการเขียนทับอย่างเงียบ ๆ เมื่อรวมกับหลักการ skip-if-empty ของตัวสรุป การสรุปซ้ำจึงไม่มีทางลบค่าที่มนุษย์ดูแลไว้ให้กลายเป็นค่าว่าง
- **`programRevisionId` เป็น null ได้ และ null หมายถึงฐานตั้งต้นก่อนมีฟีเจอร์นี้** ซึ่งสอดคล้องโดยโครงสร้างกับการที่ `Program.activeRevisionId` เป็น null เช่นกัน **อย่าเติมย้อนหลัง** ด้วยฉบับปรับปรุงที่สร้างขึ้นมาลอย ๆ เพราะนั่นคือการกุที่มาให้ข้อมูลที่เกิดก่อนแนวคิดนี้จะมีอยู่
- **ผู้ดูแลเลือกว่า "ใหม่" หรือ "ปรับปรุง" ตั้งแต่ก่อนอัปโหลด** `/admin/programs/from-pdf` ถามข้อนี้เป็นอันดับแรก แล้วจึงให้อัปโหลด และสำหรับหลักสูตรใหม่จะตรวจความซ้ำจากรหัส ชื่อ และระดับปริญญา ก่อนบันทึกจริง การถามก่อนคือสิ่งที่ทำให้การตรวจความซ้ำมีความหมาย ถ้าไปถามหลังสกัดข้อมูลแล้ว ผู้ดูแลมีแนวโน้มจะคล้อยตามสิ่งที่ AI เดามาให้

ส่วนตัวการเปรียบเทียบเอง (`ProgramCurriculumRevision`) เป็นแถวเชิงวิเคราะห์ล้วน แยกต่างหาก คือคำอธิบายที่ AI สร้างขึ้นว่าหลักสูตรใหม่เปลี่ยนอะไรบ้าง ผ่านตัว **ตรวจกันการกุข้อมูล (anti-fabrication validator)** ที่ตัดข้อความอ้างซึ่งไม่มีหลักฐานรองรับในต้นฉบับออก โดยเก็บภาพนิ่งของข้อมูลนำเข้าแบบกำหนดผลได้และจำนวนข้ออ้างที่ถูกตัดไว้ข้างเคียง payload เพื่อให้ผู้อ่านตรวจสอบฐานที่มาได้โดยไม่ต้องคำนวณใหม่ พึงคาดว่าเนื้อหาจะสั้นและระมัดระวังกว่าบทสรุปที่มนุษย์เขียน — นั่นคือตัวตรวจทำงาน ไม่ใช่โมเดลทำได้ไม่ดี

## ตัว prompt

อยู่ที่ `packages/shared/src/ai/prompts/program-digest.ts` เวอร์ชัน `program-digest.v1` เป็นการเรียกครั้งเดียวบนข้อความ PDF ทั้งฉบับ ได้ผลสรุปแบบมีโครงสร้าง 15 ฟิลด์ ได้แก่ ข้อมูลหลักสูตร รายการรายวิชาพร้อมหน่วยกิตและผลลัพธ์การเรียนรู้ ทักษะทั้งหมดที่หลักสูตรสร้างพร้อมน้ำหนักและข้อความอ้างอิงตามตัวอักษร บทสรุปประชาสัมพันธ์ภาษาไทยที่พร้อมใช้ เส้นทางอาชีพ ระดับความเชื่อมั่นที่โมเดลประเมินตัวเอง และข้อควรระวัง

การเขียนผลลง (`packages/db/src/program-digest-materialize.ts`) ใช้หลัก **ว่างแล้วข้าม** — การสรุปซ้ำจะไม่เขียนค่าว่างทับค่าที่มนุษย์คัดสรรไว้ ชื่อทักษะที่สกัดได้จะจับคู่กับ `Skill.nameEn` (ตัวพิมพ์เล็กแบบตรงตัว) ก่อน แล้วจึง `Skill.nameTh` (ตรงตัว) **ไม่มีการจับคู่แบบคลุมเครือ** ชื่อที่จับคู่ไม่ได้จะกลายเป็นรายการ `PROPOSED_SKILL` ให้นักวิเคราะห์พิจารณา ซึ่งเป็นกลไกที่ทำให้อนุกรมวิธานทักษะโตขึ้นจากคำศัพท์ในหลักสูตรของคุณเอง แทนที่จะติดอยู่กับรายการ ESCO ชุดที่ seed มา

## ต้นทุนที่ มข. จ่ายไป เอาไว้ตั้งงบ

สรุปไปได้ 228 จาก 297 หลักสูตร ตกราว **$0.04 ต่อหลักสูตร รวมประมาณ $8.10** ผ่านการรันซ้ำหกรอบ บน Gemini อีก 69 หลักสูตรที่เหลือไม่มี PDF ให้ใช้ ส่วนใหญ่เป็นหลักสูตรแพทย์เฉพาะทางและหลักสูตรที่เพิ่งเปิดใหม่ ให้เผื่อใจว่าจะขาดความครอบคลุมในสัดส่วนใกล้เคียงกัน และวางแผนงานจัดหาเอกสารแยกออกจากงานวิศวกรรม

## การสร้างอนุกรมวิธานทักษะของคุณ

**การติดตั้งใหม่ไม่มีทักษะเลย**: ตาราง `skills` มี 0 แถว จนกว่าจะสร้างอนุกรมวิธานทักษะ ตัวเลขทักษะทุกตัวในผลิตภัณฑ์จะเป็น 0 รวมถึงการ์ดทั้งสี่ใบของส่วน *Skills coverage* ใน Deep-Dive ไม่ว่าจะรัน pipeline กี่ครั้งก็ตาม เหตุผลคือการจับคู่ทักษะต้องตรงตัว ทักษะที่ digest สกัดได้จะไปถึงหลักสูตร (แถว `ProgramSkill`) ก็ต่อเมื่อชื่อตรงกับรายการในอนุกรมวิธาน โดยเทียบ `Skill.nameEn` แบบตัวพิมพ์เล็กก่อน แล้วจึงเทียบ `Skill.nameTh` ถ้าอนุกรมวิธานว่าง ก็ไม่มีอะไรจับคู่ได้

`pnpm setup` ไม่โหลดอนุกรมวิธานทักษะ และ `pnpm db:seed:kku` ก็ไม่ใช่คำตอบ คำสั่งนี้โหลดคณะ ภาควิชา และบัญชีผู้ใช้ของ มข. พร้อมทักษะจริงราว 60 รายการและทักษะสมมติอีก 500 รายการ connector ของ KMITL ก็ไม่สร้างทักษะเช่นกัน มันโหลดแถวอุปสงค์ทักษะที่ `skill_id` ว่างทั้งหมด จนกว่าจะมีอนุกรมวิธานให้ผูก

สิ่งที่สร้างอนุกรมวิธานคือ `pnpm skills:normalise` (`apps/ingestion/src/scripts/normalise-skill-names.ts`) คำสั่งนี้ส่งชื่อทักษะดิบให้ AI ทีละชุด ชุดละ 25 ชื่อ โมเดลจะจับคู่แต่ละชื่อกับทักษะที่มีอยู่ หรือเสนอเป็นทักษะใหม่ ข้อเสนอจะกลายเป็นแถว `Skill` จริงก็ต่อเมื่อคุณใส่ `--auto-promote` **และ** ความเชื่อมั่นไม่ต่ำกว่า 0.9 ข้อเสนอที่ความเชื่อมั่นต่ำกว่านั้นจะค้างอยู่ใน `skill_aliases` ด้วยสถานะ `NEW_PROPOSED` เพื่อรอการตรวจ ทุกการตัดสินใจถูกเขียนลง `logs/normalise-skills-<timestamp>.jsonl` ด้วย

**ในการติดตั้งใหม่ pipeline สร้างอนุกรมวิธานให้เอง** เฟส 2 ของ `pnpm programs:pipeline` ตรวจผลสรุป (digest) ที่เก็บไว้ของหลักสูตร มันทำงานเฉพาะกับหลักสูตรที่ยังไม่มีทักษะ หลักสูตรที่มีทักษะแล้วจะไม่ถูกแตะ ถ้าชื่อทักษะในผลสรุปไม่ตรงกับอะไรในอนุกรมวิธานเลย มันจะเลื่อนข้อเสนอเก่าของหลักสูตรนั้นที่ความเชื่อมั่นตั้งแต่ 0.9 ขึ้นไป (เช่นจากการรัน `skills:normalise` ที่ไม่มี `--auto-promote`) รัน normaliser กับชื่อของหลักสูตรนั้นเองพร้อม auto-promote แล้วเขียน **ผลสรุปที่เก็บไว้ชุดเดิม** ลงหลักสูตรอีกครั้ง นี่เป็นการเขียนฐานข้อมูล ไม่ใช่การทำ digest ด้วย AI ใหม่ ดังนั้นเฟส 3, 6 และ 7 ในรอบเดียวกันจึงเห็นทักษะแล้ว ถ้าทุกชื่อตรงกันอยู่แล้ว มันไม่ทำอะไร ตั้ง `PIPELINE_BUILD_SKILL_TAXONOMY=0` เพื่อปิด `pnpm skills:normalise` ยังเป็นเครื่องมือแบบทำเอง และเป็นสิ่งที่ใช้กับแหล่ง LinkedIn

กรณีทั่วไปจึงเป็น: ทำ digest ของหลักสูตร แล้วรัน pipeline

ถ้าต้องการเขียนผลสรุปที่เก็บไว้ซ้ำเอง โดยไม่เรียก AI ให้รัน `pnpm programs:approve-pending --rematerialise` (ทุกผลสรุปที่อนุมัติแล้ว) หรือเพิ่ม `--program-id=<id>` สำหรับหลักสูตรเดียว

วิธีทำเองตามลำดับ:

| ขั้น | คำสั่ง | ทำอะไร |
|---|---|---|
| 1 | `pnpm connector:run kmitl-skill-mapping` | โหลดอุปสงค์ทักษะของตลาดแรงงาน (ข้อมูล LinkedIn ผ่าน connector ของ KMITL) ต้องมี credential ดู [tutorial](../tutorials/program-deep-dive.md#labour-market-skills) |
| 2 | `pnpm skills:normalise --source=linkedin --auto-promote` | สร้างอนุกรมวิธานจากชื่อทักษะเหล่านั้น แล้วผูกแถวอุปสงค์และแถวการเติบโตของ KMITL เข้ากับทักษะใหม่ |
| 3 | `pnpm programs:pipeline <code> --only=phase1` หรือ `pnpm programs:digest <code>` | สรุป PDF หลักสูตร ชื่อที่จับคู่ไม่ได้จะกลายเป็นรายการ `PROPOSED_SKILL` |
| 4 | `pnpm skills:normalise --source=program_digest --auto-promote` | เพิ่มคำศัพท์จากหลักสูตรของคุณเองเข้าอนุกรมวิธาน |
| 5 | `pnpm programs:approve-pending --rematerialise` | เขียนผลสรุปที่เก็บไว้ลงอีกครั้งเพื่อให้ทักษะจับคู่ได้ ไม่เรียก AI |
| 6 | `pnpm programs:pipeline <code> --only=phase3` | จับคู่เส้นทางอาชีพและจับคู่อุปสงค์ ต้องรัน **หลัง** ขั้น 2 และ 5 ไม่เช่นนั้นการ์ด *Demand match* จะยังเป็น 0 |

- **ต้นทุนและเวลา:** ราว USD 0.003 ต่อชุด 25 ชื่อ รวมประมาณ USD 1 และ 45 นาทีสำหรับชื่อจาก LinkedIn ราว 5,900 ชื่อ ตัวเลขนี้วัดจากการติดตั้งที่ใช้ OpenRouter ราคาจริงของคุณขึ้นกับโมเดลที่ใช้ แหล่ง digest มักเล็กกว่ามาก
- **รันซ้ำได้อย่างปลอดภัย** ชื่อที่ตัดสินแล้วจะถูกข้าม การรันรอบสองจึงลองใหม่เฉพาะชื่อที่ล้มเหลว บรรทัด `Failed:` ในสรุปคือบรรทัดที่ต้องอ่าน สคริปต์จบด้วย exit 0 แม้บางชุดล้มเหลว เช่นกรณี OpenRouter ปฏิเสธเพราะยอดเงินไม่พอ ([ดูด้านล่าง](./configure-ai.md#การใช้งานผ่าน-openrouter))
- **ถ้าไม่มีสิทธิ์เข้าถึง KMITL หรืออยู่นอกประเทศไทย** ให้ข้ามขั้น 1, 2 และ 6 ขั้น 3 ถึง 5 ยังให้อนุกรมวิธานที่สร้างจากหลักสูตรของคุณเองทั้งหมด การ์ด *Demand match* จะว่างอยู่ เพราะไม่มีใครให้ข้อมูลอุปสงค์
- **การอนุมัติ `PROPOSED_SKILL` ไม่สร้างทักษะ** ถ้าไม่ได้ตั้ง `AI_AUTO_APPROVE_THRESHOLD` (ค่าตั้งต้นในโค้ดคือ 0) รายการเหล่านี้จะอนุมัติอัตโนมัติทันทีที่ถูกเขียน การอนุมัติเปลี่ยนแค่สถานะการตรวจ มีเพียงขั้น 4 ที่เปลี่ยนรายการเหล่านี้เป็นแถว `Skill`

**การเขียนผลสรุปซ้ำไม่เรียก AI** `--rematerialise` เขียนผลสรุปที่เก็บไว้ลงอีกครั้ง การรัน digest ด้วย AI ใหม่ (`pnpm programs:digest <code> --force`) จำเป็นเฉพาะเมื่อต้องการให้อ่านหลักสูตรใหม่

## การออก PDF ภาษาไทยต้องใช้ TH Sarabun New

PDF ที่ระบบ *ผลิตออกมา* ทั้งหมด (เอกสารประกอบการประชุมสภามหาวิทยาลัย บทสรุป บันทึกมติ) เรนเดอร์ผ่าน Gotenberg โดยฝังฟอนต์ TH Sarabun New ไฟล์ `.ttf` ทั้งสี่ไฟล์ **จงใจไม่เก็บใน git** และต้องวางไว้ที่ `infra/gotenberg/fonts/` ก่อนรัน `docker compose build gotenberg` วิธีหาไฟล์อยู่ใน `infra/gotenberg/README.md`

มีสองเรื่องที่จะสะดุด:

- การ build Docker จะ **ล้มเหลวทันทีและเห็นชัด** ถ้าไม่มีฟอนต์ — ทั้ง `COPY` ที่หยุดการ build และการตรวจนับจำนวน face ของ Sarabun ที่ลงทะเบียนแล้วหลัง `fc-cache` ตรงนี้จงใจ เพราะทางเลือกอีกทางคือเรนเดอร์เป็นกล่องสี่เหลี่ยมเงียบ ๆ ในเอกสารราชการ
- **"Sarabun" ของ Google Fonts เป็นฟอนต์คนละตัว** (ของ Cadson Demak) ไม่ใช่ TH Sarabun New และไม่เข้าเงื่อนไขที่คณะรัฐมนตรีกำหนดสำหรับเอกสารราชการ อย่าเอามาใช้แทน

ห้ามสร้าง PDF ในกระบวนการของแอปเอง ไม่ puppeteer ไม่ react-pdf ไม่ html-pdf — โดยเฉพาะ `@react-pdf/renderer` จัดวางวรรณยุกต์ภาษาไทยผิด และห้ามใช้ใน codebase นี้อย่างชัดเจน ทุกอย่างต้องวิ่งผ่าน `PdfGenerationService` → Gotenberg สัญญาฉบับเต็มอยู่ใน `docs/pdf-generation.md`
