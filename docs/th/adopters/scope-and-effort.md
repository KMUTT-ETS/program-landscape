# ขอบเขตและภาระงาน

> **English:** [English version](../../adopters/scope-and-effort.md)

**ผลลัพธ์** ท่านรู้ว่า repository นี้ไม่ได้ให้อะไรบ้าง และวางแผนงานตามลำดับพร้อมประมาณภาระงานได้

## สิ่งที่จะไม่ได้รับ

ต้องมองเรื่องนี้ให้ตรงก่อนวางแผน สิ่งที่ได้รับคือซอร์สโค้ดกับเอกสาร สิ่งที่ไม่ได้รับคือ:

| สิ่งที่ไม่ได้มาด้วย | ผลที่ตามมา |
|---|---|
| **ข้อมูลของ มข.** | ไม่มีระเบียนนักศึกษา บุคลากร การเงิน วิจัย การประเมิน หรือผลลัพธ์บัณฑิตใด ๆ ทุกหน้าจอเชิงวิเคราะห์เริ่มจากศูนย์ |
| **ข้อมูลรับรอง** | ไม่มีรหัสผ่านฐานข้อมูล ไม่มี API key ไม่มี client secret ของ SSO ไม่มีบัญชีบริการ ค่าใน `.env.example` เป็นค่าตัวอย่างทั้งหมด |
| **ตารางแม่หลักสูตร 297 หลักสูตร** | รายการหลักสูตรที่ มข. คัดสรรไว้ พร้อมรหัส อว. และเลขลำดับ ต้องสร้างของตัวเองขึ้นมา |
| **PDF หลักสูตรของ มข.** | 228 ฉบับ ต้องไปจัดหาเอง |
| **ไฟล์ฟอนต์ TH Sarabun New** | จงใจไม่เก็บใน git ด้วยเหตุผลด้านความสะอาดของสัญญาอนุญาต แหล่งที่มาอยู่ใน `infra/gotenberg/README.md` **การ build Docker จะล้มเหลวถ้าไม่มีไฟล์เหล่านี้** |
| **ข้อมูลรับรองของ KMITL Skill Mapping** | ต้องขอ client ID และ secret key ของตัวเองจาก สจล. |
| **API key ของ Scopus / Elsevier** | เป็นการบอกรับของสถาบัน ขอผ่านห้องสมุด |
| **การบอกรับข้อมูลการจัดอันดับ** | THE, QS, SCImago, IMD |
| **ความเห็นชอบจากเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคลของ มข.** | โอนกันไม่ได้ ดู [PDPA และธรรมาภิบาลข้อมูล](./pdpa-and-governance.md) |
| **การถ่วงน้ำหนักระเบียบวิธีที่ผูกกับสภามหาวิทยาลัย** | น้ำหนักในคะแนนสุขภาพเข้ารหัสจุดยืนของสภามหาวิทยาลัยขอนแก่นไว้ ดู [การปรับระเบียบวิธีให้เข้ากับสถาบันของคุณ](../guides/adapt-a-methodology.md) |
| **เครื่องหมายการค้าและอัตลักษณ์ของ มข.** | ชื่อ ตราสัญลักษณ์ และโลโก้ สงวนไว้ ไม่ได้อนุญาตให้ใช้ ต้องปรับแบรนด์ใหม่ ดู [สัญญาอนุญาต — CC BY-NC-SA 4.0](./README.md#สัญญาอนุญาต--cc-by-nc-sa-40) และ [การปรับแบรนด์และ UI](../guides/rebrand.md) |
| **คำวินิจฉัยว่า "ไม่ใช้เพื่อการค้า" อนุญาตให้ทำอะไรได้บ้าง** | มข. ยังไม่ได้เผยแพร่การตีความ ให้ขอคำยืนยันการใช้งานที่ตั้งใจไว้เป็นลายลักษณ์อักษร ดู [สัญญาอนุญาต — CC BY-NC-SA 4.0](./README.md#สัญญาอนุญาต--cc-by-nc-sa-40) |

### สิ่งที่ยังไม่เสร็จใน repository และรับสืบทอดมาในสภาพยังไม่เสร็จ

ความตรงไปตรงมาตรงนี้มีค่ามากกว่ารายการฟีเจอร์ที่ดูสวย:

- **รายการเกณฑ์ AUN-QA ยังไม่ได้ตรวจสอบ** `packages/shared/src/aunqa/criteria.ts` มีคำเตือนเรื่องที่มาระบุไว้ในส่วนหัวของตัวเอง: เกณฑ์ชุดนี้เขียนขึ้นจากความรู้ของผู้ช่วย AI เกี่ยวกับ AUN-QA v4 **ไม่มีคู่มือ AUN-QA อยู่ใน repository** และยังไม่มีการตรวจสอบเทียบกับเอกสารที่เผยแพร่จริงเลย เกณฑ์สองข้อ (Student Support Services และ Facilities & Infrastructure) ไม่มีข้อมูลรองรับในแพลตฟอร์มเลย จึงแยกรายการไว้ต่างหากเพื่อไม่ให้ผู้อ่านเข้าใจผิดว่าหกเกณฑ์คือทั้งกรอบ ยิ่งกว่านั้น จากหลักสูตรของ มข. สามหลักสูตรที่สุ่มดู กรอบประกันคุณภาพที่แต่ละหลักสูตรประกาศไว้คือ WFME หรือ TQF — **ไม่มีหลักสูตรใดระบุ AUN-QA** การจัดเรียงหลักฐานตามแนว AUN-QA จึงเป็นชั้นการวิเคราะห์ที่แพลตฟอร์มวางทับลงไปเอง ไม่ใช่สิ่งที่เอกสารต้นทางกล่าวอ้าง **ต้องตรวจสอบเทียบกับคู่มือฉบับทางการก่อนนำไปใช้กับการขอรับรองคุณภาพใด ๆ**
- **การจัดสรรต้นทุนยังเป็น v0** และไม่มีตัวเลขต้นทุนรายหลักสูตรตัวใดที่เสนอต่อสภามหาวิทยาลัยได้ ดู [การปรับระเบียบวิธีให้เข้ากับสถาบันของคุณ](../guides/adapt-a-methodology.md)
- **`kku-alumni` ยังไม่มี connector ตัวจริง** ผลลัพธ์บัณฑิตและอุปทานระดับจังหวัดจึงยังไม่ได้ต่อที่ มข. เช่นกัน การวิเคราะห์ช่องว่างเชิงภูมิภาคจึงแสดงหมายเหตุชัดเจนว่าฝั่งอุปทานยังรอข้อมูล
- **แผนที่ประเทศไทยเป็นแบบแผนผัง ไม่ใช่ choropleth จริง** — เป็นบล็อกหกภูมิภาคที่ไล่ความเข้มสี เพราะยังไม่มีข้อมูลบัณฑิตระดับจังหวัด
- **CI ตัว `Release bundle` แดงอยู่** เพราะหนี้ lint ทั้ง repo ที่ค้างมาก่อน
- **มีรายการในแคตตาล็อกที่เลิกใช้แล้วห้ารายการ** (`kku-tcas-funnel`, `jobthai`, `jobsdb`, `scopus`, `openalex`) เก็บไว้เพียงเพื่อไม่ให้แถว `IngestionRun` ในอดีตกลายเป็นแถวกำพร้า อย่าไปต่อมันเข้ากับอะไร
- **Storybook ตั้งค่าไว้แล้วแต่ยังไม่มี story** หน้า `/styleguide` ในแอปเว็บทำหน้าที่เป็นสัญญาเชิงภาพแทน
- **กล่องโต้ตอบขอเหตุผลการส่งออกข้อมูลรายเทมเพลต** — decorator `@RequireExportReason` และ `DataExportGuard` วางโครงไว้แล้ว แต่ยังไม่มี route ที่ใช้งานจริง (เกตข้อ 8 ของรายการตรวจสอบความพร้อมผ่านในระดับโครงสร้างพื้นฐาน แต่ยังไม่ผ่านในระดับหน้าจอ)

## ลำดับงานที่แนะนำ พร้อมประมาณการภาระงาน

ประมาณการนี้ตั้งอยู่บนสมมติฐานว่ามีนักพัฒนา full-stack ที่มีฝีมือหนึ่งถึงสองคน ซึ่งยังไม่เคยเห็น codebase นี้ และรวมเวลารอสิทธิ์เข้าถึงระบบของสถาบันไว้แล้ว ซึ่งตามปกติคือเส้นทางวิกฤต

| ระยะ | งาน | ประมาณการ |
|---|---|---|
| 0 | **ขอคำยืนยันเป็นลายลักษณ์อักษรจาก มข. ว่าการใช้งานที่ตั้งใจไว้อยู่ในเงื่อนไข NonCommercial ของ CC BY-NC-SA** เป็นงานที่บล็อกทุกอย่างถ้าการใช้งานเข้าใกล้เชิงพาณิชย์ | หลายวันถึงหลายสัปดาห์ และไม่ได้อยู่ในการควบคุมของคุณ |
| 1 | ตั้ง instance บนเครื่องให้รันได้ ตั้ง fork พร้อม upstream อ่าน `CLAUDE.md`, `architecture.md`, `evaluation-pipeline.md` | 3–5 วัน |
| 2 | ปรับแบรนด์ fork `CLAUDE.md` ยึดสิทธิ์ `/setup` อัปโหลดคณะและภาควิชา | 1 สัปดาห์ |
| 3 | อัปโหลดรายการหลักสูตรพร้อมรหัส อว. แล้วตามด้วย spreadsheet ตัวชี้วัดที่มีอยู่แล้ว (จำนวนนักศึกษา การเงิน บุคลากร ทีมอาจารย์ประจำหลักสูตร ผลงานตีพิมพ์) | 1–2 สัปดาห์ (การรวบรวมข้อมูล ไม่ใช่โค้ด) |
| 4 | เริ่มขอสิทธิ์เข้าถึงระบบของสถาบัน **ทุกระบบพร้อมกัน** — สำนักทะเบียน บุคคล การเงิน UniCon การประเมิน | เริ่มตั้งแต่วันแรก คาดว่าใช้เวลา 4–12 สัปดาห์ |
| 5 | connector UniCon ตัวแรก (DS2001 หรือ DS2004) | 1–3 วันหลังได้สิทธิ์แล้ว |
| 6 | connector UniCon อีกสามตัวที่เหลือ | 1 สัปดาห์ |
| 7 | แหล่งข้อมูลภายนอก Tier 2 — สจล. TCAS ธนาคารโลก ฟีดรายงานนโยบาย | 1–2 สัปดาห์ ขึ้นกับข้อมูลรับรอง |
| 8 | จัดหา PDF หลักสูตร และรัน pipeline การสรุป | 2–4 สัปดาห์ โดยการจัดหาเอกสารกินเวลาส่วนใหญ่ |
| 9 | เขียน Tier 3 ตัวแรกใหม่ (สำนักทะเบียน ส่งผลมากที่สุด) แทนการอัปโหลด spreadsheet ชุดที่ตรงกัน | 2–4 สัปดาห์ |
| 10 | connector Tier 3 ที่เหลือ ตามลำดับความสำคัญ | ตัวละ 2–4 สัปดาห์ |
| 11 | ปรับระเบียบวิธีร่วมกับสภามหาวิทยาลัยหรือองค์กรเทียบเท่า | 2–4 สัปดาห์ ส่วนใหญ่เป็นเรื่องเชิงสถาบัน ไม่ใช่เชิงเทคนิค |
| 12 | เชื่อม SSO deploy ขึ้น production และประสานทีมเครือข่าย | 2–3 สัปดาห์ |
| 13 | การทบทวนและให้ความเห็นชอบโดยเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล | ทำคู่ขนานไปกับทุกอย่าง เริ่มแต่เนิ่น ๆ |
| 14 | ช่วงรอประวัติการรันเขียว 30 วันต่อ connector ก่อนใช้กับสภามหาวิทยาลัย | 30 วัน เลี่ยงไม่ได้ วางแผนเผื่อไว้ |

**หมุดหมายที่สมจริงสำหรับผลลัพธ์ที่ใช้งานได้ครั้งแรกคือสี่ถึงหกเดือน หากเริ่มจาก connector** โดยเวลาส่วนใหญ่หมดไปกับการเข้าถึงข้อมูลและการจัดหาเอกสาร ไม่ใช่งานวิศวกรรม **หากเริ่มจากการอัปโหลด spreadsheet จะเหลือเพียงไม่กี่สัปดาห์** ขั้นที่ 2–3 ทำให้ cockpit และ deep-dive มีข้อมูลจากไฟล์ที่หน่วยงานส่งออกได้อยู่แล้ว ขั้นที่ 4–10 จึงกลายเป็นการแทนการอัปโหลดด้วยระบบอัตโนมัติ แทนที่จะขวางทางไปสู่ผลลัพธ์แรก งานวิศวกรรมส่วนใหญ่ทำเสร็จไปแล้ว สิ่งที่ codebase นี้ช่วยประหยัดให้คือเวลาในส่วนของงานวิศวกรรม ไม่ใช่เวลาในส่วนของการขอสิทธิ์เข้าถึงข้อมูลและการจัดหาเอกสาร

**คำแนะนำเรื่องลำดับงานที่สำคัญกว่าตัวเลขประมาณการ:** เริ่มยื่นขอสิทธิ์เข้าถึงทุกระบบตั้งแต่สัปดาห์แรก ก่อนเขียนโค้ดบรรทัดใด connector หนึ่งตัวคืองานหนึ่งถึงสามวัน บวกการรอบัญชีบริการอีกแปดสัปดาห์ ให้จัดคิวงานตามข้อเท็จจริงข้อนี้
