## 1. อ่านส่วนนี้ก่อน

**ข้อเท็จจริงข้อเดียวที่มีประโยชน์ที่สุดสำหรับมหาวิทยาลัยไทยที่จะนำแพลตฟอร์มนี้ไปใช้:** connector สี่ตัวอ่านจาก **ชุดข้อมูลมาตรฐานระดับชาติ MHESI UniCon** ซึ่งเป็นชุดข้อมูลเดียวกับที่สถาบันของคุณส่งให้กระทรวงอยู่แล้ว และเป็น schema เดียวกัน สี่ตัวนี้แทบจะนำไปใช้ได้ทันที เปลี่ยนแค่ host กับชื่อฐานข้อมูล อย่าไปแก้โครงสร้างตาราง

| Connector | ชุดข้อมูล | ข้อมูลที่บรรจุอยู่ |
|---|---|---|
| `unicon-ds1001` | DS1001 | ข้อมูลนักศึกษา หนึ่งแถวต่อ (นักศึกษา × ปีการศึกษา × ภาคการศึกษา) |
| `unicon-ds2001` | DS2001 | ทะเบียนหลักบุคลากร — ตำแหน่งทางวิชาการ สัญญาจ้าง แหล่งงบประมาณ สถานะการปฏิบัติงาน |
| `unicon-ds2003` | DS2003 | คุณวุฒิการศึกษาของบุคลากรทุกคน |
| `unicon-ds2004` | DS2004 | อาจารย์ประจำหลักสูตร (การเป็นกรรมการบริหารหลักสูตร) |

ตรวจสอบได้จากคอมเมนต์ส่วนหัวของ `apps/ingestion/src/connectors/sources/unicon-ds2001/connector.ts` — ทั้ง URL ของแหล่งข้อมูล การ projection คอลัมน์แบบเจาะจง และแนวปฏิบัติด้าน PDPA บันทึกไว้ในไฟล์นั้นครบ

ส่วนที่เป็นระบบเฉพาะของแต่ละสถาบัน — คลังข้อมูลสำนักทะเบียน ระบบบุคคล ระบบการเงิน ระบบประเมินการสอน คะแนนสมรรถนะดิจิทัล — สร้างขึ้นให้เข้ากับระบบของ มข. โดยเฉพาะ ต้องเขียนใหม่ให้ตรงกับระบบเทียบเท่าของแต่ละแห่ง [บทที่ 8](#8-การเชื่อมต่อข้อมูล--สี่ระดับของภาระงานในการนำไปใช้) จัดแหล่งข้อมูลทั้ง 39 รายการในแคตตาล็อกออกเป็นระดับตามปริมาณงานที่ต้องลงแรง

**สามเรื่องที่ควรเข้าใจให้ขึ้นใจก่อนเริ่ม:**

- ระบบนี้เป็น **ระบบสนับสนุนการตัดสินใจที่มีเดิมพันสูง** — การปิดหลักสูตร การควบรวม ชีวิตความเป็นอยู่ของอาจารย์ codebase ออกแบบโดยมี provenance (การสืบค้นที่มาของตัวเลข) การบันทึก audit log การกำกับเวอร์ชันระเบียบวิธี และการเปิดเผยระดับความเชื่อมั่น เป็นแกนกลาง สิ่งเหล่านี้ไม่ใช่ของประดับ ถอดออกเมื่อไรก็เหลือแค่ dashboard ที่ไม่มีใครในสภามหาวิทยาลัยเชื่อถือ
- **ไม่มีทางลัดให้ใส่ข้อมูลปลอม เพราะเป็นนโยบาย** กติกาของโครงการคือแหล่งข้อมูลที่ยังต่อไม่ได้ต้อง *ว่างเปล่า* ไม่ใช่กรอกของปลอมแทน ส่วนที่ว่างจะขึ้นสถานะชัดเจนว่า "ไม่มีข้อมูล — ให้รัน connector ตัวนี้" ต้องห้ามใจไม่ให้เติมตัวเลขที่ดูสมเหตุสมผลลงไปแทน เพราะห่วงโซ่ provenance ทั้งเส้น (ดู [`realDataWhere()`](#กับดักที่-2-realdatawhere--ส่วนที่ว่างเปล่าทั้งที่ฐานข้อมูลมีข้อมูล)) ออกแบบมาจับพฤติกรรมแบบนี้โดยเฉพาะ
- **โค้ดเผยแพร่ภายใต้ CC BY-NC-SA 4.0 ซึ่งมีภาระผูกพันจริง** — แสดงที่มา อนุญาตแบบเดียวกัน และไม่ใช้เพื่อการค้า — และ *ไม่ได้* อนุญาตให้ใช้เครื่องหมายการค้าของ มข. ไม่ครอบคลุมชุด dependency และไม่ครอบคลุมข้อมูลใด ๆ ของ มข. อ่านบทถัดไปให้จบก่อนนำโค้ดนี้ไปทำอะไรที่เป็นสาธารณะ

## 2. สัญญาอนุญาต — CC BY-NC-SA 4.0

แฟ้ม `LICENSE` ใน repository นี้คือ **สัญญาอนุญาตครีเอทีฟคอมมอนส์ แบบแสดงที่มา-ไม่ใช้เพื่อการค้า-อนุญาตแบบเดียวกัน 4.0 นานาชาติ (CC BY-NC-SA 4.0)** โดยมีส่วนหัวของมหาวิทยาลัยขอนแก่นนำหน้าข้อความสัญญาอนุญาตฉบับเต็ม ลิขสิทธิ์ © พ.ศ. 2569 มหาวิทยาลัยขอนแก่น

ภาระผูกพันมีสี่ข้อ ถ้อยคำในสี่ข้อนี้ยกมาจากประกาศลิขสิทธิ์ฉบับภาษาไทยของ มข. ที่ `apps/web/app/(legal)/copyright/page.tsx` จึงเป็นภาษากฎหมายและเป็นทางการกว่าคำอธิบายรอบข้างโดยเจตนา:

- **การแสดงที่มา (BY)** — ท่านต้องระบุที่มาตามรูปแบบที่กำหนดไว้ในข้อ 11 ของประกาศดังกล่าว ระบุลิงก์ไปยังสัญญาอนุญาต และแจ้งว่าท่านได้ดัดแปลงงานหรือไม่ ต้องแสดงไว้ทั้งใน repository ในเอกสารประกอบ และในหน้าจอ "เกี่ยวกับ" หรือหน้าเครดิตที่ผู้ใช้มองเห็น
- **อนุญาตแบบเดียวกัน (SA)** — หากท่านปรับปรุง แปลง หรือต่อยอดจากงาน ท่านต้องเผยแพร่ส่วนที่ท่านสร้างสรรค์ขึ้นภายใต้สัญญาอนุญาต CC BY-NC-SA 4.0 หรือสัญญาอนุญาตที่ครีเอทีฟคอมมอนส์กำหนดให้ใช้ร่วมกันได้
- **ไม่ใช้เพื่อการค้า (NC)** — ท่านจะใช้งานนี้เพื่อวัตถุประสงค์ทางการค้ามิได้ อันหมายถึงการใช้ที่มุ่งประสงค์เป็นสำคัญต่อประโยชน์ทางการค้าหรือค่าตอบแทนอันเป็นตัวเงิน
- **คงข้อความแจ้งไว้ครบถ้วน** — ให้คงข้อความแสดงลิขสิทธิ์ ข้อความแสดงที่มา และข้อความแจ้งสัญญาอนุญาต ไว้ในทุกสิ่งที่เผยแพร่ต่อ

ส่วนหัวของแฟ้ม `LICENSE` มีข้อความแสดงที่มาแบบสำเร็จรูปให้คัดลอกไปใช้อยู่แล้ว ใช้ข้อความนั้น อย่าคิดถ้อยคำขึ้นเอง

**สามสิ่งที่สัญญาอนุญาตนี้ไม่ได้ให้ และแต่ละข้อจะเล่นงานใครสักคนในทีมแน่นอน:**

- **เครื่องหมายของ มข. ไม่ได้อยู่ภายใต้สัญญาอนุญาต** ทั้ง "Khon Kaen University", "มหาวิทยาลัยขอนแก่น", "KKU", ตราสัญลักษณ์ประจำมหาวิทยาลัย และแฟ้มโลโก้ใน `apps/web/public/brand/` สงวนไว้โดยชัดแจ้ง สัญญาอนุญาตครีเอทีฟคอมมอนส์ให้สิทธิเฉพาะในทางลิขสิทธิ์ และข้อ 2(b)(2) ระบุเรื่องนี้ไว้ตรง ๆ ระบบที่คุณนำไปติดตั้งใช้งานเองต้องถอดเครื่องหมายเหล่านี้ออกหรือเปลี่ยนเป็นของสถาบันตนเอง [บทที่ 11](#11-การปรับแบรนด์และ-ui) คือรายการตรวจสอบ และมีไฟล์ประมาณ 101 ไฟล์ใต้ `apps/web` ที่เอ่ยชื่อ มข.
- **ชุด dependency ไม่ได้อยู่ภายใต้สัญญาอนุญาตของ มข.** `node_modules` อิมเมจคอนเทนเนอร์ฐาน และฟอนต์ ต่างมีข้อกำหนดของตัวเอง ฟอนต์ TH Sarabun New เป็นกรณีที่ชัดที่สุด — ไม่ได้อยู่ใน repository และมีเงื่อนไขของตัวเอง ตรวจสอบให้ครบก่อนเผยแพร่ต่อ
- **ไม่มีข้อมูลของ มข. มาพร้อมกับโค้ด** ทั้งฐานข้อมูลหลักสูตร 297 หลักสูตร ระเบียนนักศึกษาและบุคลากร และผลการประเมินทุกอย่างที่คำนวณจากข้อมูลเหล่านั้น อยู่นอกขอบเขตการเผยแพร่ครั้งนี้ทั้งหมด [บทที่ 19](#19-สิ่งที่จะไม่ได้รับ) คือรายการฉบับเต็ม

**เรื่อง "ไม่ใช้เพื่อการค้า" อ่านตรงนี้ก่อนจะเดาเอง** คำนี้ไม่ได้นิยามละเอียดพอสำหรับบริบทมหาวิทยาลัย และมหาวิทยาลัยก็ทำหลายอย่างที่คาบเส้นนั้นอยู่ เช่น การดำเนินงานที่ใช้เงินค่าธรรมเนียมการศึกษา งานวิจัยตามสัญญาจ้าง หลักสูตรผู้บริหาร หลักสูตรระยะสั้นที่เก็บค่าลงทะเบียน และบริษัท spin-off ตอนนี้ มข. ยังไม่ได้เผยแพร่การตีความคำนี้สำหรับงานชิ้นนี้ **ถ้าการใช้งานที่ตั้งใจไว้อยู่ใกล้เส้นนั้น ให้ขอคำยืนยันเป็นลายลักษณ์อักษรจากผู้ประสานงานด้านสัญญาอนุญาตของ มข. ก่อนลงแรงต่อยอด** ชื่อผู้ประสานงานอยู่ท้ายแฟ้ม `LICENSE`

## 4. การขอสิทธิ์เข้าถึง การ fork และการรับ fix จาก upstream ในอนาคต

### การขอสิทธิ์เข้าถึง

repository ต้นทางคือ `https://github.com/khon-kaen-university/program-landscape` ขอสิทธิ์เข้าถึงได้ที่ฝ่ายการศึกษาและดิจิทัล มหาวิทยาลัยขอนแก่น สิ่งที่จะได้รับคือ repository เท่านั้น ไม่มีข้อมูลรับรอง ไม่มีข้อมูล ไม่มีฟอนต์ (ดู [บทที่ 19](#19-สิ่งที่จะไม่ได้รับ))

### fork ไว้ อย่าตัดขาดจากต้นทาง

ให้รับโค้ดไปในรูป **git fork ที่ตั้ง remote `upstream` ไว้ด้วย** ไม่ใช่คัดลอกครั้งเดียวจบ เพราะยังไงก็ต้องดึง bug fix ของ มข. มาใช้ codebase ยังพัฒนาต่อเนื่อง และหลายระบบย่อย — มาตรฐาน prompt ระเบียบวิธีคะแนนสุขภาพ ห่วงโซ่ provenance ของคุณภาพข้อมูล — ขยับไปมากในช่วงไม่กี่เดือนที่ผ่านมา

```bash
git clone git@github.com:<your-university>/program-landscape.git
cd program-landscape
git remote add upstream https://github.com/khon-kaen-university/program-landscape.git
git fetch upstream
```

### จัดโครงสร้างการแก้ไข เพื่อให้ merge ในอนาคตยังทำได้

ตัวแปรเดียวที่ชี้ขาดว่าอีกหนึ่งปีจะยัง merge upstream ได้อยู่หรือไม่ คือ **ตำแหน่งที่วางโค้ดเฉพาะของสถาบัน** ข้อแนะนำ เรียงจากคุ้มค่าที่สุดลงมา:

| ประเภทการแก้ไข | ทำแบบนี้ | ไม่ใช่แบบนี้ |
|---|---|---|
| connector ของคุณ | สร้างไดเรกทอรีใหม่ใต้ `apps/ingestion/src/connectors/sources/<your-slug>/` แล้วเพิ่มเป็นรายการใหม่ใน `SOURCE_CATALOG` และแถวใหม่ใน registry | แก้ไฟล์ connector ของ มข. ทับลงไป |
| ข้อมูลคณะ/ภาควิชา/หลักสูตรของคุณ | เขียนโมดูล seed ของตัวเอง แล้ว import จาก `packages/db/prisma/seed.ts` | แก้อาร์เรย์คณะของ มข. ในไฟล์เดิม |
| แบรนด์ | เปลี่ยนไฟล์สินทรัพย์และ *ค่า* ของ token แต่คง *ชื่อ* token ไว้ | เปลี่ยนชื่อ token หรือรื้อโครงสร้าง `tailwind-preset.ts` |
| น้ำหนักในระเบียบวิธี | เพิ่มเลขเวอร์ชันแล้ววางเวอร์ชันของคุณคู่ไว้ ดู [บทที่ 12](#12-ระเบียบวิธี--การปรับการให้คะแนนให้เข้ากับสถาบันของคุณ) | แก้สูตรของ มข. ทับลงไป |
| `CLAUDE.md` ของคุณ | เขียนใหม่ได้เต็มที่ ไฟล์นี้ *ตั้งใจ* ให้แยกทาง | — |

ไฟล์ต่อไปนี้ต้องเผื่อใจไว้ว่าจะชนทุกครั้งที่ merge ให้รวมการแก้ไขของคุณไว้ในจุดน้อยที่สุดเท่าที่จะทำได้:

- `packages/shared/src/ingestion/catalog.ts` (ต่อรายการของคุณไว้ท้ายอาร์เรย์)
- `apps/ingestion/src/connectors/registry.ts` (เช่นเดียวกัน)
- `packages/db/prisma/seed.ts`
- `packages/design/src/tokens/*.ts`
- `.env.example`

### migration จะชนกัน และนี่คือจุดที่เจ็บที่สุด

migration ของ Prisma คือไดเรกทอรีที่ตั้งชื่อด้วย timestamp ใต้ `packages/db/prisma/migrations/` ถ้าคุณเพิ่ม migration และ มข. ก็เพิ่ม migration ทั้งคู่จะถูก apply ได้ตามปกติ — แต่ถ้าแก้ *ตารางเดียวกัน* ต้องมานั่งประสานด้วยมือ บรรเทาได้สองทาง:

- ตั้งชื่อ migration ให้แยกแยะออกชัด (`20260901120000_yourthuni_registrar_bridge`) ประวัติจะอ่านรู้เรื่อง
- เลือกการเปลี่ยน schema แบบ **เพิ่มเข้าไป** (คอลัมน์ nullable ใหม่ ตารางใหม่) แทนการไปแก้ของ มข. repository นี้ใช้นโยบายนี้กับตัวเองอยู่แล้ว ดู `docs/migration-policy.md` และสังเกต `scripts/migration-linter.ts` ที่ CI รันเพื่อจับ DDL ที่ทำลายข้อมูล

### จังหวะ merge ที่ใช้ได้จริง

merge upstream **ไตรมาสละครั้ง ไม่ใช่ต่อเนื่อง** การ merge ต่อเนื่องแปลว่าต้องมานั่งแก้ conflict ชุดเดิมทุกสัปดาห์ ไตรมาสละครั้งแปลว่าได้อ่านสิ่งที่เปลี่ยนใน `docs/` และหน้า `/changelog` (`apps/web/app/changelog/page.tsx` คือประวัติการปล่อยเวอร์ชันที่เป็นทางการ ส่วนบันทึกใน CLAUDE.md ระบุตัวเองไว้ชัดว่าเป็นแบบ best-effort และมีช่วงที่ขาดหาย) แล้วจัดการรวดเดียวอย่างตั้งใจ

## 5. รันครั้งแรก — จาก clone จนได้ instance ที่ทำงานได้

**เป้าหมาย:** แอปรันที่ `http://localhost:3000` พร้อมฐานข้อมูลที่ว่างแต่ถูกต้อง บนเครื่องของตัวเอง ครั้งแรกเผื่อเวลาไว้ครึ่งวัน

### สิ่งที่ต้องมีก่อน

- Node 20 ขึ้นไป (`.nvmrc` ตรึงเวอร์ชันไว้) และ pnpm 9 ขึ้นไป (repo ประกาศ `pnpm@10.33.1` เป็น packageManager)
- Docker + Docker Compose v2
- Linux, macOS หรือ Windows ที่มี WSL2 (Ubuntu) เครื่องพัฒนาหลักของ มข. คือ Windows/WSL2 มีวิธีตั้งค่าใน `prompts/WINDOWS-DEV.md` และโครงการนี้ **ไม่มี Makefile โดยเจตนา** ทุกอย่างเป็น pnpm script

### ลำดับขั้นตอน

```bash
# 1. Environment file. Start from the example and fill in what you have.
cp .env.example .env

# 2. Full setup — installs deps, links .env into each app, starts
#    postgres/redis/minio/gotenberg, runs migrations, seeds.
pnpm setup

# 3. Run all three services in parallel.
pnpm dev
```

`pnpm setup` คือคำสั่งลัดของ `pnpm install && node scripts/link-env.mjs && pnpm db:generate && pnpm db:up && pnpm minio:init && pnpm db:migrate && pnpm db:seed` ถ้าขั้นไหนพัง ให้รันทีละคำสั่งเพื่อหาว่าติดตรงไหน

เมื่อรันขึ้นแล้ว:

| URL | คืออะไร |
|---|---|
| `http://localhost:3000` | เว็บ (Next.js) |
| `http://localhost:4000/api/v1/healthz` | ตรวจว่าโปรเซส API ยังมีชีวิตอยู่ |
| `http://localhost:4000/api/v1/ready` | สุขภาพ dependency ของ API — ตรวจ Postgres, Redis, MinIO, Gotenberg และผู้ให้บริการ AI |
| `http://localhost:9001` | คอนโซล MinIO |
| `http://localhost:3001` | Gotenberg |

### การล็อกอินในวันแรก

ตั้ง `ENABLE_LOCAL_AUTH=true` และ `DEV_AUTH_PASSWORD=<something>` ใน `.env` จะได้ credentials provider ให้ล็อกอินได้โดยยังไม่ต้องมี OIDC identity provider และมีตัวกันพลาดไว้แล้ว — `assertLocalAuthSafe()` จะ throw ตั้งแต่ตอนโหลดโมดูลถ้า `ENABLE_LOCAL_AUTH=true` ขณะที่ `NODE_ENV=production` จึงหลุดขึ้น production โดยบังเอิญไม่ได้

การต่อ SSO ของมหาวิทยาลัยเป็นงานคนละก้อน `docs/auth/kku-sso.md` บันทึกการตั้งค่า OIDC ของ มข. ไว้เป็นตัวอย่างของรูปแบบที่ต้องทำ

### "ทำงานได้" ในขั้นนี้หน้าตาเป็นอย่างไร

หน้าจอเชิงวิเคราะห์ส่วนใหญ่จะ **ว่าง** และนั่นถูกต้องแล้ว seed ให้คณะ อนุกรมวิธานทักษะ ภาคเศรษฐกิจ และข้อมูลอ้างอิงมา แต่ไม่ได้ให้ข้อมูลนักศึกษา บุคลากร การเงิน หรือเอกสารหลักสูตร เพราะข้อมูลชุดนั้นเป็นของสถาบันคุณและยังไม่มีอยู่ ส่วนที่ว่างจะแสดงสถานะว่างพร้อมระบุชื่อ connector ที่ต้องรัน ถ้าเห็นตัวเลขที่ดูเหมือนถูกกุขึ้นมา แปลว่ามีอะไรผิด

### หากแอปคอมไพล์ผ่านแต่ทุก route ที่ต้องล็อกอินเด้งกลับไป `/signin`

### กฎการวางตัวสองข้อที่ช่วยประหยัดเวลา

**หัวใจเชิงวิเคราะห์อยู่ที่ `packages/db/src/` ไม่ใช่ `apps/api/`** ชั้น API บางมาก การให้คะแนนสุขภาพ การให้คะแนนความเสี่ยง การวิเคราะห์ช่องว่าง การเทียบเคียงคู่เทียบ ชุดคำสั่งค้นข้อมูลของหน้า deep-dive ตัวกรอง provenance ของคุณภาพข้อมูล — ทั้งหมดอยู่ใน `packages/db/src/*.ts` ในรูป exported function ที่ระบุ type ชัดเจน อยากรู้ว่า "ตัวเลขนี้คำนวณยังไง" ให้เริ่มที่นั่น ไม่ใช่ที่ controller

**`packages/shared/` ต้องไม่ import `packages/db/` เด็ดขาด** ทิศทางการพึ่งพาเป็นทางเดียว (`db` พึ่ง `shared`) ถ้าต้องการ implementation ที่ใช้ Prisma ของ interface ที่ประกาศไว้ใน `shared` ให้เอาคลาสจริงไปไว้ใน `db` แล้ว inject เข้ามา ตัวอย่างมาตรฐานของแพตเทิร์นนี้คือ `packages/db/src/ai-inference-recorder.ts`

### กฎความพร้อมสำหรับสภามหาวิทยาลัย

มีหกข้อ ใช้กับทุกโมดูล ทุก endpoint และทุกหน้าจอ ระบุไว้ใน `CLAUDE.md` และตรวจสอบด้วยเกตสิบสองข้อใน `docs/readiness-checklist.md`:

1. `<ProvenanceButton>` บนทุกกราฟ — เปิด drawer ที่บอกแหล่งข้อมูล ความสดของข้อมูล วิธีคำนวณ เวอร์ชันระเบียบวิธี และข้อควรระวัง
2. `<ConfidenceBadge>` พร้อมแหล่งข้อมูลที่คลิกได้ และปุ่ม "ไม่เห็นด้วย" บนทุกผลลัพธ์จาก AI
3. `<FreshnessBadge>` บนทุกจุดข้อมูล
4. `@AuditLog()` บนทุก mutation (`apps/api/src/common/decorators.ts`)
5. `@AiCall()` บนทุกการเรียก AI (ไฟล์เดียวกัน)
6. ทุกตัววัดต้องมี `methodologyVersion` และเอกสารระเบียบวิธีต้องกำกับเวอร์ชันไว้ใน git ใต้ `docs/methodologies/`

หน้าจอที่เพิ่มเข้ามาแล้วยังไม่มีครบหกข้อนี้ ถือว่ายังไม่เสร็จ นี่คือสิ่งที่ทำให้ผลลัพธ์ปกป้องได้ในห้องประชุมสภามหาวิทยาลัย และเป็นส่วนของ codebase ที่น่าข้ามที่สุดแต่แพงที่สุดเมื่อต้องกลับมาใส่ทีหลัง

## 7. การตั้งค่าและ environment

`.env.example` มีคีย์ที่ไม่ถูกคอมเมนต์อยู่ **104 คีย์** (บวกคีย์ทางเลือกที่คอมเมนต์ไว้อีกราว 20 คีย์) ส่วน `.env.prod.example` มีมากกว่านั้น พร้อมคำแนะนำเฉพาะ production ในคอมเมนต์ อ่านทั้งสองไฟล์ ทั้งคู่ไม่ใช่รายการที่ต้องกรอกให้ครบ — คีย์ส่วนใหญ่เป็นข้อมูลรับรองรายตัวของ connector ที่ยังไม่ต้องใช้จนกว่าจะต่อ connector ตัวนั้น

### คีย์ environment ที่สำคัญจริงในวันแรก

| คีย์ | หมายเหตุ |
|---|---|
| `DATABASE_URL` | ต้องสอดคล้องกับ `POSTGRES_*` เพราะระบบไม่ได้ประกอบค่านี้ขึ้นมาให้อัตโนมัติ |
| `NEXTAUTH_SECRET` | จำเป็น ถ้าขาดจะเกิดความล้มเหลวเงียบของ auth ดูกับดักที่ 4 |
| `NEXTAUTH_URL`, `AUTH_TRUST_HOST` | ตั้งเป็น URL สาธารณะของคุณเมื่อขึ้น production |
| `ENABLE_LOCAL_AUTH`, `DEV_AUTH_PASSWORD` | การล็อกอินสำหรับ dev จะ fail ทันทีถ้าเปิดใน production |
| `AI_PROVIDER` | `google` (ค่าตั้งต้น) / `anthropic` / `stub` การใช้ tool-use (AI Analyst) ต้องเป็น `anthropic` |
| `GOOGLE_AI_API_KEY` / `ANTHROPIC_API_KEY` | ต้องมีอย่างน้อยหนึ่งตัว ส่วน provider `stub` ทำงานได้โดยไม่ต้องมีคีย์เลย |
| `CONNECTOR_MODE` | โหมดตั้งต้นของ connector ทุกตัว ช่วงแรกปล่อยไว้ที่ `mocked` |
| `MINIO_*`, `REDIS_*`, `GOTENBERG_URL` | ค่าตั้งต้นสำหรับเครื่อง local ใน `.env.example` ใช้ได้เลยกับ `pnpm db:up` |

**ช่องว่างใน `.env.example` ที่จะเจอแน่ ๆ** คีย์ `AI_PROVIDER`, `GOOGLE_AI_API_KEY`, `UNICON_DS2001_DB_*` และ `UNICON_DS1001_DB_*` มีบันทึกไว้ใน `.env.prod.example` แต่ **ไม่มีใน `.env.example`** ไฟล์ตัวอย่างฝั่ง dev ตามฝั่ง prod ไม่ทัน เวลา connector รายงานว่าค่าตั้งค่าขาด ให้ไปดู `.env.prod.example` และ `configFromEnv('<PREFIX>')` ในตัว connector ก่อน อย่าเพิ่งสรุปว่าคีย์นั้นไม่มีอยู่จริง

### แต่ละแอปต้องมี `.env` ของตัวเอง — ข้อนี้ไม่ใช่ทางเลือก

`@next/env` ของ Next.js โหลด `.env` จาก **ไดเรกทอรีของโปรเจกต์ Next** (`apps/web/`) ไม่เคยโหลดจากรากของ monorepo กับดักเดียวกันนี้เล่นงาน `apps/api` และ `apps/ingestion` ด้วย

`scripts/link-env.mjs` (`pnpm link-env` และเป็นส่วนหนึ่งของ `pnpm setup`) จะ symlink `.env` ที่รากไปยังไดเรกทอรีแอปทั้งสาม และไปยัง `packages/db` ด้วย (Prisma CLI อ่าน `DATABASE_URL` จาก `packages/db/.env`) บน Windows ที่ไม่ได้เปิด Developer Mode สคริปต์จะถอยไปใช้การคัดลอกแทน — และสำเนา **จะไม่ตามการแก้ไข** `.env` ที่ราก ดังนั้นบน Windows ให้รัน `pnpm link-env` ซ้ำทุกครั้งหลังแก้ค่า env

อาการเมื่อขาดไฟล์นี้เงียบและชวนเข้าใจผิด ดู [กับดักที่ 4](#กับดักที่-4-ไฟล์-env-ประจำแต่ละแอป-และความล้มเหลวเงียบของ-edge-middleware)

### การจัดการ secret ใน production

production ใช้ secret แบบไฟล์ของ Docker Compose ใต้ `/opt/program-landscape/secrets/` (หนึ่งค่าต่อหนึ่งไฟล์ สิทธิ์ 0600) สำหรับข้อมูลรับรองของ Postgres และ MinIO ควบคู่กับ `.env.prod` ที่เป็นของ root สิทธิ์ 0600 เอกสารอ้างอิงคือ `DEPLOYMENT.md` หัวข้อ *One-time server setup* มีข้อสังเกตที่บันทึกไว้แล้วอยู่หนึ่งข้อ: `DATABASE_URL` ใน `.env.prod` ยังฝังรหัสผ่านไว้ในตัวมันเอง จึงต้องคอยไล่ให้ตรงกับไฟล์ secret ด้วยมือ

## 8. การเชื่อมต่อข้อมูล — สี่ระดับของภาระงานในการนำไปใช้

บทนี้คือบทที่กำหนดแผนงานทั้งโครงการ แคตตาล็อกแหล่งข้อมูลอยู่ที่ `packages/shared/src/ingestion/catalog.ts` — **39 รายการ เลิกใช้แล้ว 5 รายการ** ตัว connector อยู่ใต้ `apps/ingestion/src/connectors/sources/` และตารางสลับ mock↔real คือ `apps/ingestion/src/connectors/registry.ts`

การจัดระดับด้านล่างนี้เรียงแหล่งข้อมูลตามปริมาณงาน *ที่ตกกับคุณ* ไม่ใช่ตามความสำคัญ

### Tier 1 — ใช้ได้แทบทันที: ตระกูล MHESI UniCon DS

มหาวิทยาลัยไทยทุกแห่งส่งชุดข้อมูล UniCon DS ให้ อว. ด้วย **schema เดียวกัน** แปลว่าทั้ง SQL projection ความหมายของคอลัมน์ การจัดการวันที่แบบพุทธศักราช และวิธีจัดการข้อมูลส่วนบุคคลใน connector สี่ตัวนี้ ย้ายมาใช้ได้ตรง ๆ

| Slug | แหล่งข้อมูลในระบบของ มข. | จำนวนแถวใน snapshot ของ มข. |
|---|---|---|
| `unicon-ds1001` | `mysql://…/reg_unicon.view_ds1001` | 35,406 (ปีการศึกษา 2568 ภาค 2) |
| `unicon-ds2001` | `mysql://…/UNICON_STAFF_KKU.DS2001` | 11,325 |
| `unicon-ds2003` | `mysql://…/UNICON_STAFF_KKU.DS2003` | 18,060 |
| `unicon-ds2004` | `mysql://…/reg_unicon.ds2004_<YYSEM>` | หนึ่งแถวต่อ (บุคลากร × หลักสูตร × ประเภทการสอน) |

**สิ่งที่ต้องเปลี่ยน:** รายละเอียดการเชื่อมต่อ ผ่าน env prefix `UNICON_DS1001_DB_*` / `UNICON_DS2001_DB_*` / `UNICON_DS2003_DB_*` / `UNICON_DS2004_DB_*` ซึ่งอ่านผ่าน `configFromEnv()` ใน `apps/ingestion/src/lib/mysql-client.ts` สังเกตว่าในระบบของ มข. DS1001 จงใจใช้ข้อมูลรับรองชุดเดียวกับ DS2004 เพราะเป็น MySQL endpoint เดียวกัน ตรวจดูว่าที่สถาบันคุณเป็นแบบนั้นหรือไม่

**สิ่งที่คงต้องแตะเพิ่มอยู่ดี:**

- **ธรรมเนียมการตั้งชื่อตารางของ DS2004** ตาราง snapshot ของ มข. ชื่อ `ds2004_<YYSEM>` โดยใช้ พ.ศ. สองหลักท้ายบวกภาคการศึกษา (`682` = ปีการศึกษา 2568 ภาค 2) ตัว connector หา `MAX(suffix)` ตอน runtime ถ้าสำนักทะเบียนของคุณตั้งชื่อคนละแบบ ตรรกะส่วนนี้ต้องเปลี่ยน
- **การแปลงรหัสหน่วยงาน** `unicon-ds2001` จับคู่ `DEPARTMENT_ID` ห้าหลักของ DS2001 เข้ากับ `Faculty.id` ของคุณ โดย join ผ่าน `staff_program_assignment.fac_id` (ดู `buildDeptCodeToFacultyMap()` ในไฟล์นั้น) วิธีนี้ใช้ได้เพราะ DS2004 ลงข้อมูลสะพานเชื่อมนี้ด้วยรหัสคณะของ อว. ไว้ก่อนแล้ว ถ้ายังไม่ได้รัน DS2004 ตัว DS2001 จะโหลดเข้ามาโดย `facultyId = null` — connector จะรายงานจำนวนรหัสที่แปลงไม่ได้ไว้ใน metadata แทนที่จะล้มทั้งงาน
- **การแปลง `CURR_ID` เป็นหลักสูตร** DS1001 และ DS2004 แปลงรหัสหลักสูตรของ อว. เทียบกับ `Program.mhesiCode` (โดยมี `ProgramMhesiAlias` เป็นทางสำรอง) จึงต้อง seed หลักสูตรพร้อมรหัส อว. ให้ครบก่อน ดู [บทที่ 10](#10-เอกสารหลักสูตรและ-pipeline-การสรุปด้วย-ai)
- **แนวปฏิบัติด้านข้อมูลส่วนบุคคล** SQL projection ของ connector แต่ละตัวคือเส้นแบ่งความไว้วางใจ และบันทึกไว้ในส่วนหัวของไฟล์ — คอลัมน์ไหนถูกตัดทิ้งตั้งแต่ projection คอลัมน์ไหนถูก hash (`CITIZEN_ID` → `citizenIdHash` ผ่าน `hashCitizenId()`) คอลัมน์ไหนลดความละเอียดเหลือระดับปี ทั้งหมดนี้ผ่านความเห็นชอบของเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคลของ มข. แล้ว **เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคลของสถาบันคุณต้องพิจารณาเห็นชอบเองอีกครั้ง** ความเห็นชอบของ มข. โอนกันไม่ได้

**ประมาณการภาระงานตามจริง:** หนึ่งถึงสามวันต่อ connector หนึ่งตัว ถ้าตาราง DS อยู่ตรงที่คาดไว้และมีสิทธิ์อ่านแล้ว เวลาส่วนใหญ่หมดไปกับข้อมูลรับรองและการเปิดเครือข่าย ไม่ใช่การเขียนโค้ด

> **ข้อควรรู้:** สี่ตัวนี้ไม่มีไฟล์ข้อกำหนด `docs/data-sources/unicon-*.md` ไดเรกทอรีข้อกำหนดรายแหล่งครอบคลุมเฉพาะแหล่งข้อมูลรุ่นเก่า ส่วน connector ตระกูล UniCon อธิบายตัวเองไว้ในส่วนหัวของไฟล์แทน ให้อ่านจากโค้ด

### Tier 2 — แหล่งข้อมูลระดับชาติและภายนอกที่ใช้ร่วมกัน: เหมือนกันทุกสถาบัน

**กฎการระบุที่มาสองข้อที่ต่อรองไม่ได้** ข้อมูลจาก สจล. คือข้อมูล LinkedIn ที่ อว. เป็นผู้บอกรับ สจล. เป็นเพียงผู้ให้บริการ API เท่านั้น ห้ามนำเสนอต่อผู้ใช้ว่าเป็น "ข้อมูลของ สจล." เด็ดขาด และข้อสอง ข้อมูลจากฟีดนี้ในช่อง ไทย × ประกาศรับสมัครงาน เป็น **กลุ่มตัวอย่างที่บาง** (161 ประกาศใน snapshot ที่สังเกตได้ เทียบกับโปรไฟล์ LinkedIn ทั่วโลกราว 950,000 โปรไฟล์) หน้าจอใดที่เสนอต่อสภามหาวิทยาลัยแล้วใช้ข้อมูลชุดนี้ ต้องมีคำเตือนเรื่องขนาดกลุ่มตัวอย่างใน drawer ที่บอก provenance

**ประมาณการภาระงานตามจริง:** ตัวละไม่กี่ชั่วโมง ส่วนใหญ่คือเวลารอข้อมูลรับรอง ตัวที่คุ้มค่าที่สุดในกลุ่มนี้คือ `kmitl-skill-mapping` เพราะเป็นตัวที่ทำให้ฝั่งอุปสงค์ของ Gap Analyzer และตัวขับเคลื่อนด้านตลาดแรงงานในคะแนนสุขภาพมีข้อมูลขึ้นมา

### Tier 3 — ต้องเขียนใหม่ในแต่ละสถาบัน

กลุ่มนี้อ่านจากระบบปฏิบัติการของ มข. เอง *รูปแบบ* ผลลัพธ์ที่ผลิตออกมานำไปใช้ซ้ำได้ แต่ *ตัวแหล่งข้อมูล* ใช้ซ้ำไม่ได้

|---|---|---|

#### ตัวอย่างจริง — `kku-dq` แหล่งข้อมูล Tier 3 ที่ payload ห้ามเก็บลงฐานข้อมูล

ควรอ่าน `kku-dq` ก่อนลงมือเขียน connector ของตัวเอง เพราะเป็นตัวอย่างที่ชัดที่สุดในโครงการนี้ของแหล่งข้อมูลที่ **มีประโยชน์เมื่ออยู่ในรูปข้อมูลรวม แต่เป็นอันตรายเมื่ออยู่ในรูปรายคน**

API ประเมินสมรรถนะความฉลาดทางดิจิทัลของ มข. คืนข้อมูล **นักศึกษาทุกคนในการเรียกครั้งเดียว** — ประมาณ 24,800 ระเบียน ขนาด 13.7 MB ใช้เวลาราว 3.4 วินาที ไม่มี pagination ให้จัดการ และผลจะขยับก็ต่อเมื่อมีนักศึกษาเข้าสอบเพิ่ม จึงตั้งให้ทำงานสัปดาห์ละครั้ง ทั้งนี้ payload มีชื่อ นามสกุล และรหัสนักศึกษาติดมาด้วย

**ข้อมูลเหล่านั้นไม่มีชิ้นไหนไปถึงฐานข้อมูล log หรือดิสก์เลย** connector จับคู่นักศึกษาเข้ากับหลักสูตร *ในหน่วยความจำ* แล้วเขียนลงเฉพาะ cube สองชุดเท่านั้น ชุดหนึ่งต่อ (คณะ × หลักสูตร × รุ่น) อีกชุดเพิ่มมิติรายมอดูล นี่คือท่าทีแบบ aggregate-at-source เดียวกับ `kku-registry` และ `kku-hr` และเป็นท่าทีที่ควรลอกไปใช้ เพราะอธิบายต่อ DPO ได้ง่ายกว่าตารางรายคนที่ต้องพ่วงเรื่องการควบคุมสิทธิ์เข้าถึงมาด้วยมาก

การตัดสินใจออกแบบสามข้อใน connector ตัวนี้ใช้ได้ทั่วไป

- **เก็บ `scoreSum` กับ `takenCount` อย่าเก็บค่าเฉลี่ยสำเร็จรูป** นี่คือสิ่งที่ทำให้ตัวเลขระดับคณะหรือระดับมหาวิทยาลัยเป็นค่าเฉลี่ยถ่วงน้ำหนักจริง ไม่ใช่ค่าเฉลี่ยของค่าเฉลี่ย ถ้าเก็บเป็นค่าเฉลี่ยไปแล้วจะกู้น้ำหนักคืนไม่ได้อีก
- **สิ่งที่จับคู่ไม่ได้ อย่าทิ้ง** นักศึกษาที่จับคู่กับหลักสูตรไม่ได้จะไปอยู่ใต้ `programId` ที่เป็น null ซึ่งหน้าจอแสดงเป็น "Program not identified" ความครอบคลุมมีรูปร่างตามรุ่น — รุ่นใหม่จับคู่ได้ดี รุ่นเก่าจับคู่ได้น้อย เพราะตารางที่ใช้จับคู่เป็นภาพนิ่งของการลงทะเบียนปีปัจจุบัน ขณะที่ไฟล์ส่งออกเป็นข้อมูลสะสม ถ้าซ่อนแถวเหล่านั้นไป ยอดรวมของทุกคณะจะหดลงอย่างเงียบ ๆ
- **`ingestion_run_id` เป็น `onDelete: Restrict` และห้ามเป็น null** แถว cube ที่อยู่รอดพ้นอายุ run ของตัวเองจะไม่มีที่มา และ `realDataWhere()` จะตัดทิ้งอย่างเงียบ ๆ — ดูกับดักที่ 2 การกำหนดข้อจำกัดนี้ทำให้สภาพดังกล่าว *เป็นไปไม่ได้* แทนที่จะเป็นเพียงเรื่องที่ไม่แนะนำ

**วิธีลงมือเขียน Tier 3 ใหม่:**

1. อ่านส่วนหัวของไฟล์ connector ของ มข. ก่อนเป็นอันดับแรก ทุกตัวบันทึกกระบวนการสำรวจไว้ — ตารางไหนถูกลองสำรวจบ้าง คอลัมน์ไหนกลายเป็น NULL ทั้งคอลัมน์ คีย์ join ตัวไหนที่ขาดไม่ได้ ความไม่ตรงกันของ collation ตัวไหนที่เล่นงานเข้าให้ ต่อให้แหล่งข้อมูลต่างกัน *คำถาม* ก็ยังใช้ซ้ำได้
2. อ่านข้อกำหนดคู่กันที่ `docs/data-sources/<slug>.md` เอกสารเหล่านี้อธิบาย endpoint ข้อจำกัดอัตราการเรียก แนวปฏิบัติด้าน PDPA และปัญหาที่ทราบแล้ว
3. ทำตาม `prompts/14-integration-session-template.md` ดู [บทที่ 9](#9-สัญญาของ-connector-และวิธีเขียน-connector)
4. **รวมยอดตั้งแต่ต้นทาง** connector ของ มข. ผลัก `GROUP BY` และการปิดกั้นเซลล์ขนาดเล็ก (`HAVING COUNT(*) >= 5`) ลงไปใน SQL ข้อมูลรายบุคคลจึงไม่เคยถูกส่งออกมาจากเครื่องต้นทางเลย ให้รักษาแนวนี้ไว้ นี่คือการตัดสินใจเชิงออกแบบข้อเดียวที่ทำให้เรื่อง PDPA ปกป้องได้

**ประมาณการภาระงานตามจริง:** หนึ่งถึงสามสัปดาห์ต่อ connector หนึ่งตัว โดยเวลาส่วนใหญ่หมดไปกับการขอสิทธิ์อ่านระบบที่เจ้าของระบบไม่มีเหตุผลอะไรจะให้ ให้เริ่มคุยเรื่องสิทธิ์ก่อนเริ่มเขียนโค้ด ตัวที่ส่งผลต่อระบบปลายทางมากที่สุดคือ `kku-registry` และ `kku-hr` — ถ้าขาดสองตัวนี้ หน้า cockpit และ deep-dive จะว่างเป็นส่วนใหญ่

## 9. สัญญาของ connector และวิธีเขียน connector

### Interface

ประกาศไว้ใน `packages/shared/src/ingestion/types.ts` มีสี่เมธอด และ runner เรียกตามลำดับนี้:

```
healthCheck(ctx) → HealthStatus          // can we reach the source at all?
fetch(ctx)       → RawRecord[]           // pull, unchanged, from upstream
transform(ctx, raw) → NormalizedRecord[] // map to our schema; 0..n per raw
load(ctx, normalized) → LoadResult       // write, idempotently
```

ชนิดข้อมูลสามแบบ:

- `RawRecord` — `{ externalId, data: unknown, sourceTimestamp }` โดย `externalId` คือคีย์ที่ใช้ตัดข้อมูลซ้ำข้ามการรันแต่ละครั้ง
- `NormalizedRecord` — `{ target, externalId, payload, freshnessDate, sourcePdfId? }` โดย `target` ระบุตารางปลายทาง
- `LoadResult` — `{ recordsFetched, recordsLoaded, recordsFailed, metadata }` ก้อน `metadata` จะไปโผล่ที่ `/admin/data-sources/<slug>` และเป็นที่สำหรับใส่ตัวอย่างรหัสที่แปลงไม่ได้ จำนวนแถวแยกตามการกระจายตัว และอะไรก็ตามที่นักวิเคราะห์ต้องใช้คัดกรอง

### connector จริงหน้าตาเป็นอย่างไร

`apps/ingestion/src/connectors/sources/unicon-ds2001/connector.ts` ยาว 310 บรรทัด และเป็นไฟล์ที่คุ้มค่าแก่การอ่านมากที่สุด รูปธรรมคือ:

- `healthCheck` เปิดการเชื่อมต่อด้วย `configFromEnv('UNICON_DS2001_DB')` แล้วรัน `SELECT 1` จากนั้นส่งค่า `user@host:port/database` ที่ใช้เชื่อมต่อจริงกลับมาในข้อความ หน้า admin จะได้แสดงว่าต่อไปที่ไหนกันแน่
- `fetch` รัน projection คอลัมน์แบบเจาะจงชุดเดียว (คือเส้นแบ่งความไว้วางใจด้านข้อมูลส่วนบุคคล) แล้ว **ปฏิเสธที่จะไปต่อเมื่อได้ศูนย์แถว** — `throw new NonRetryableError('EMPTY_DATA', 'DS2001 returned 0 rows — refusing to wipe')` ข้อนี้สำคัญเพราะ `load` ใช้วิธีแทนที่ทั้ง snapshot การ fetch ที่ได้ค่าว่างจึงเท่ากับลบ snapshot ทิ้งทั้งก้อน ลอกกลไกป้องกันตัวนี้ไปใช้ด้วย
- `fetch` ยังเก็บยอดรวมรายการรันไว้ที่ `this.runState` (จำนวนแยกตามประเภทบุคลากร ตามสัญชาติ และแถวที่ hash ไม่ได้) ซึ่งไปจบที่ `LoadResult.metadata`
- `transform` hash `CITIZEN_ID` ตรงเส้นแบ่ง และคืน `[]` สำหรับแถวที่หาคีย์ไม่ได้ — จำนวนแถวที่ hash ไม่ได้ถูกนับไว้ ไม่ได้ถูกทิ้งเงียบ ๆ
- `load` ลบแถวเดิมที่อยู่ในขอบเขต `(academicYear, semester)` เดียวกัน แล้ว insert เป็นก้อนละ 1,000 แถวผ่าน `createMany` พร้อมประทับ `ingestionRunId: ctx.runId` ลงทุกแถว **การประทับนี้บังคับ** ดู [กับดักที่ 2](#กับดักที่-2-realdatawhere--ส่วนที่ว่างเปล่าทั้งที่ฐานข้อมูลมีข้อมูล)

### รูปแบบ mock → real

ทุก slug ในแคตตาล็อกมี connector แบบ mock ส่วน implementation จริงเพิ่มเข้ามาคู่กัน ไม่ใช่เขียนทับ ตารางจับคู่อยู่ใน `apps/ingestion/src/connectors/registry.ts`:

```ts
{
  slug: 'kku-registry',
  mock: () => new KkuRegistryConnector(),
  real: () => new KkuRegistryRealConnector(),
}
```

การเลือกโหมดอยู่ใน `packages/shared/src/ingestion/connector-mode.ts` เจอตัวไหนก่อนใช้ตัวนั้น:

1. `CONNECTOR_<SLUG>_MODE` — เอา slug มาแปลงเป็นตัวพิมพ์ใหญ่ อักขระที่ไม่ใช่ตัวอักษรหรือตัวเลขเปลี่ยนเป็น `_` (เช่น `CONNECTOR_KKU_REGISTRY_MODE=real`)
2. `CONNECTOR_MODE` — ค่าตั้งต้นของทั้งระบบ
3. ค่าตายตัวสุดท้ายคือ `mocked`

ถ้าตั้ง slug ไว้เป็น `real` แต่ยังไม่ได้ลงทะเบียน factory `real` ตัว registry จะ log คำเตือนไว้ให้เห็นชัด แล้ว **ถอยไปใช้ mock** การพลิก env โดยยังไม่ได้เขียนคลาสจึงไม่เคยทำให้ระบบ ingestion ล่ม

**การย้อนกลับคือ "ตั้ง env กลับเป็น `mocked`" แล้วรีสตาร์ต worker** ไม่ต้องย้ายข้อมูล ไม่ต้องแก้ schema รักษาคุณสมบัตินี้ไว้ในทุก connector ที่เขียนขึ้นใหม่ นี่คือเหตุผลเดียวที่เกตข้อ 11 ในรายการตรวจสอบความพร้อมทำได้จริง

### คู่มือปฏิบัติการต่อ connector หนึ่งตัว

`prompts/14-integration-session-template.md` (128 บรรทัด) คือคู่มือที่มีอยู่แล้ว ใช้ตามนั้นได้เลยทั้งฉบับ ข้อที่ต่อรองไม่ได้คือ:

- **หนึ่ง slug ต่อหนึ่ง session** ไม่ใช่สองตัว ไม่ใช่ครึ่งตัว connector สองตัวแปลว่าสอง session จะทำขนานกันก็ได้ แต่ห้ามมัดรวม
- **รายการตรวจสอบก่อน session ต้องเสร็จครบก่อนเขียนโค้ดบรรทัดแรก** ได้แก่ กรอกข้อกำหนดให้เกินระดับโครงร่าง เก็บข้อมูลรับรองไว้ใน secret store ของสภาพแวดล้อมปลายทาง commit ตัวอย่าง payload ไว้ที่ `apps/ingestion/test/fixtures/<slug>/` (อย่างน้อยหนึ่งเคสปกติและหนึ่งเคสขอบ) เจ้าของข้อมูลยืนยันว่า endpoint นิ่งแล้ว และถ้ามีข้อมูลส่วนบุคคลเข้ามาเกี่ยวข้อง ต้องมีลายมือชื่อกำกับของเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล
- **เกณฑ์ปิดงาน:** ต้องมีการรันสำเร็จ **อย่างน้อยสามครั้ง** ให้เห็นที่ `/admin/data-sources/<slug>` โดยไม่มีความล้มเหลวเลยตลอดสิบครั้งที่พยายาม พร้อมบันทึกค่าอ้างอิงสำหรับตรวจจับความเบี่ยงเบน (จำนวนแถวและการกระจายตัวของฟิลด์สำคัญ) ไว้ในข้อกำหนด
- **สิ่งที่อยู่นอกขอบเขตของ session แบบ connector อย่างชัดเจน:** การขยับเวอร์ชันระเบียบวิธี การเขียนข้อมูลลงตารางโดเมน และการแก้ UI แต่ละอย่างเป็น session ของตัวเอง

รัน connector โดยไม่ผ่าน BullMQ ด้วย `pnpm connector:run <slug>` เส้นทางโค้ดเดียวกับ worker แต่วนรอบพัฒนาได้เร็วกว่ามาก

### กฎเรื่องแฟล็ก `mocked` / `status`

ตอนพลิก connector ไปเป็น real แถวใน `data_sources` ต้องอัปเดต **ทั้ง** `status` และ `mocked` พร้อมกันในคราวเดียว สองคอลัมน์นี้เป็นอิสระต่อกัน และ `status='real'` ไม่ได้แปลว่า `mocked=false` ทำผิดข้อนี้แล้วจะได้ UI ที่ว่างเปล่าทั้งที่เห็นแถวข้อมูลอยู่ใน SQL ชัด ๆ `pnpm data-sources:audit` มีไว้จับความเบี่ยงเบนแบบนี้โดยเฉพาะ ให้รันทุกครั้งหลังพลิก connector และหลังรีเซ็ตฐานข้อมูล

## 10. เอกสารหลักสูตรและ pipeline การสรุปด้วย AI

ส่วนนี้คือกลไกที่เปลี่ยนกอง PDF หลักสูตรให้กลายเป็นข้อมูลหลักสูตรที่มีโครงสร้างและค้นได้ เป็นส่วนที่มีมูลค่าสูงที่สุดส่วนหนึ่งของแพลตฟอร์ม และย้ายไปใช้ที่สถาบันอื่นได้แทบไม่ต้องแก้

### ลำดับการทำงาน

```
Curriculum PDF  →  MinIO + PdfDocument row (content-hash deduped)
                →  AI digest (program-digest.v1)
                →  AiExtraction row, PENDING_REVIEW
                →  human approval
                →  materialised onto Program + ProgramSkill rows
                →  unmatched skill names → PROPOSED_SKILL queue
```

### คำสั่ง

| คำสั่ง | ใช้ทำอะไร |
|---|---|
| `pnpm pdf:bulk-load <manifest.jsonl>` | นำเข้าข้อมูลย้อนหลังครั้งเดียว ค่าตั้งต้นเป็น dry-run ใส่ `--commit` เพื่ออัปโหลดจริง |
| `pnpm programs:digest <code\|mhesi\|seq>` | สรุปหลักสูตรเดียว |
| `pnpm programs:digest-bulk [--limit N] [--level X]` | ทำเป็นชุด และทำต่อจากที่ค้างไว้ได้เอง |
| `pnpm programs:approve-pending` | อนุมัติและเขียนผลสรุปที่ค้างอยู่ทั้งหมดลงฐานข้อมูล |
| `pnpm programs:pipeline <code>` | pipeline เต็มรายหลักสูตร (อธิบายด้านล่าง) |
| `/admin/programs/from-pdf` | หน้าจอนำส่งสำหรับผู้ดูแล — หลักสูตรใหม่ *หรือ* ฉบับปรับปรุง |
| `/admin/programs/[id]?tab=files` | แนบ PDF ผ่านหน้าจอ |

ให้แนบ PDF ผ่านหน้าจอหรือผ่าน `pdf:bulk-load` เท่านั้น — มข. เคยมีตัวจับคู่ชื่อไฟล์แบบคลุมเครือเพื่อผูก PDF ที่ไม่มีเจ้าของเข้ากับหลักสูตร **แต่เลิกใช้ไปแล้วหลังจากมันผูกผิดไปราว 30 หลักสูตร** และต้องมาตรวจสอบด้วยเนื้อหาเพื่อแก้กลับทีหลัง อย่าสร้างขึ้นมาใหม่

### pipeline ฉบับเต็ม

`pnpm programs:pipeline <code|seq|id>` (หรือ `--all [--limit=N]`) รวบสิ่งที่เคยเป็นสคริปต์เก้าตัวที่ต้องรันมือไว้ด้วยกัน เรียงตามลำดับการพึ่งพา ฉบับที่เป็นทางการอยู่ในส่วนหัวของ `apps/ingestion/src/scripts/programs-pipeline.ts` สรุปคร่าว ๆ ได้ว่า:

| เฟส | ทำอะไร | หมายเหตุ |
|---|---|---|
| 1 | สกัดข้อมูลจาก PDF ด้วย AI — ผลสรุป อาจารย์ ทักษะ วิธีการสอน | รันขนานกัน |
| 2 | อนุมัติแล้วเขียนผลสรุปลง `ProgramSkill` | แตะเฉพาะฐานข้อมูล เร็ว |
| 2b | สกัดรหัสรายวิชาแบบเจาะจง | แทนที่รายการรายวิชาที่ถูกตัดสั้นในผลสรุป ด้วยรายการเต็ม 40–90 รายวิชา |
| 3 | จับคู่เส้นทางอาชีพ และจับคู่อุปสงค์ | ทำตามลำดับ |
| 4 | เชื่อมข้อมูลของสถาบัน — รุ่นนักศึกษา ศิษย์เก่า การเงิน | ขนานกัน และวิ่งไปที่ระบบสำนักทะเบียน/การเงินของคุณ |
| 6 | ประเมินความพร้อมด้าน AI | **รันก่อนเฟส 5** เพราะทั้งเฟส 5 และ 7 ใช้คะแนนจากเฟสนี้ |
| 5 | เลือกคู่เทียบ และทำ peer review | ทำตามลำดับ |
| RE | ความเชี่ยวชาญด้านการวิจัย | **insert อย่างเดียว** ถ้ามีอยู่แล้วให้ข้าม ไม่มีการสร้างใหม่อัตโนมัติ |
| 7 | เรื่องเล่าเชิงกลยุทธ์ | ใช้ผลจากทุกเฟสก่อนหน้า |
| 8 | วิเคราะห์ความเสี่ยง | การคำนวณแบบกำหนดผลได้แน่นอน บวกคำบรรยาย |

`--skip=phase4` คือแฟล็กที่ต้องใช้ตอนที่ connector ของสำนักทะเบียนยังไม่ได้ต่อ ส่วน `--only=phase5` รันเฟสเดียว

### ฉบับปรับปรุง — เมื่อ มคอ.2 ฉบับที่สองเข้ามา

กระบวนการข้างต้นคือการนำเข้าหลักสูตร *ครั้งแรก* เมื่อหลักสูตรมีอยู่ในระบบแล้ว มคอ.2 ฉบับใหม่ต้องไม่เขียนทับของเดิมดื้อ ๆ เพราะผลวิเคราะห์ที่สภามหาวิทยาลัยเห็นเมื่อเดือนก่อนจะเปลี่ยนไปใต้เท้าโดยไม่มีร่องรอยว่าเพราะอะไร แบบจำลองฉบับปรับปรุงมีไว้เพื่อการนี้ และเป็นส่วนของ pipeline นี้ที่คุ้มค่าแก่การลอกไปทั้งชุดที่สุด

`ProgramRevision` คือภาชนะพักงาน — มคอ.2 หนึ่งฉบับที่ผูกกับหลักสูตรหนึ่ง แล้วเดินผ่านสถานะ

```
DRAFT → ANALYSING → IN_REVIEW → APPROVED
                              ↘ REJECTED
(ฉบับที่อนุมัติแล้วแต่ถูกฉบับถัดไปแทนที่) → SUPERSEDED
```

`Program.activeRevisionId` ชี้ไปที่ฉบับที่ใช้งานจริง ผลวิเคราะห์ทุกชิ้นที่ pipeline สร้าง — บทวิเคราะห์เชิงยุทธศาสตร์ ความพร้อมด้าน AI การจัดการเรียนการสอน การทาบทานกับสถาบันเทียบเคียง ความเชี่ยวชาญด้านวิจัย ทักษะ รายวิชา และตัวการเปรียบเทียบฉบับปรับปรุงเอง — ล้วนมี `programRevisionId` กำกับ หน้าหลักสูตรจึงแสดงหลักสูตรที่สอดคล้องกันภายในชุดเดียว และผลของฉบับที่ถูกแทนที่ยังอยู่ครบและระบุที่มาได้ แทนที่จะถูกเขียนทับ

สามเรื่องที่ควรยกไปด้วยหากจะสร้างกลไกนี้เอง

- **ข้อมูลกำกับหลักสูตรถูก "เสนอ" ไม่ใช่ "เขียนทับ"** เมื่อผลสรุปของฉบับปรับปรุงขัดกับค่าปัจจุบันของหลักสูตร `metadataProposalJson` จะบันทึกทั้งค่าที่เสนอและค่าเดิมที่จะถูกแทนที่ แทนการเขียนทับอย่างเงียบ ๆ เมื่อรวมกับหลักการ skip-if-empty ของตัวสรุป การสรุปซ้ำจึงไม่มีทางลบค่าที่มนุษย์ดูแลไว้ให้กลายเป็นค่าว่าง
- **`programRevisionId` เป็น null ได้ และ null หมายถึงฐานตั้งต้นก่อนมีฟีเจอร์นี้** ซึ่งสอดคล้องโดยโครงสร้างกับการที่ `Program.activeRevisionId` เป็น null เช่นกัน **อย่าเติมย้อนหลัง** ด้วยฉบับปรับปรุงที่สร้างขึ้นมาลอย ๆ เพราะนั่นคือการกุที่มาให้ข้อมูลที่เกิดก่อนแนวคิดนี้จะมีอยู่
- **ผู้ดูแลเลือกว่า "ใหม่" หรือ "ปรับปรุง" ตั้งแต่ก่อนอัปโหลด** `/admin/programs/from-pdf` ถามข้อนี้เป็นอันดับแรก แล้วจึงให้อัปโหลด และสำหรับหลักสูตรใหม่จะตรวจความซ้ำจากรหัส ชื่อ และระดับปริญญา ก่อนบันทึกจริง การถามก่อนคือสิ่งที่ทำให้การตรวจความซ้ำมีความหมาย ถ้าไปถามหลังสกัดข้อมูลแล้ว ผู้ดูแลมีแนวโน้มจะคล้อยตามสิ่งที่ AI เดามาให้

ส่วนตัวการเปรียบเทียบเอง (`ProgramCurriculumRevision`) เป็นแถวเชิงวิเคราะห์ล้วน แยกต่างหาก คือคำอธิบายที่ AI สร้างขึ้นว่าหลักสูตรใหม่เปลี่ยนอะไรบ้าง ผ่านตัว **ตรวจกันการกุข้อมูล (anti-fabrication validator)** ที่ตัดข้อความอ้างซึ่งไม่มีหลักฐานรองรับในต้นฉบับออก โดยเก็บภาพนิ่งของข้อมูลนำเข้าแบบกำหนดผลได้และจำนวนข้ออ้างที่ถูกตัดไว้ข้างเคียง payload เพื่อให้ผู้อ่านตรวจสอบฐานที่มาได้โดยไม่ต้องคำนวณใหม่ พึงคาดว่าเนื้อหาจะสั้นและระมัดระวังกว่าบทสรุปที่มนุษย์เขียน — นั่นคือตัวตรวจทำงาน ไม่ใช่โมเดลทำได้ไม่ดี

### ตัว prompt

อยู่ที่ `packages/shared/src/ai/prompts/program-digest.ts` เวอร์ชัน `program-digest.v1` เป็นการเรียกครั้งเดียวบนข้อความ PDF ทั้งฉบับ ได้ผลสรุปแบบมีโครงสร้าง 15 ฟิลด์ ได้แก่ ข้อมูลหลักสูตร รายการรายวิชาพร้อมหน่วยกิตและผลลัพธ์การเรียนรู้ ทักษะทั้งหมดที่หลักสูตรสร้างพร้อมน้ำหนักและข้อความอ้างอิงตามตัวอักษร บทสรุปประชาสัมพันธ์ภาษาไทยที่พร้อมใช้ เส้นทางอาชีพ ระดับความเชื่อมั่นที่โมเดลประเมินตัวเอง และข้อควรระวัง

การเขียนผลลง (`packages/db/src/program-digest-materialize.ts`) ใช้หลัก **ว่างแล้วข้าม** — การสรุปซ้ำจะไม่เขียนค่าว่างทับค่าที่มนุษย์คัดสรรไว้ ชื่อทักษะที่สกัดได้จะจับคู่กับ `Skill.nameEn` (ตัวพิมพ์เล็กแบบตรงตัว) ก่อน แล้วจึง `Skill.nameTh` (ตรงตัว) **ไม่มีการจับคู่แบบคลุมเครือ** ชื่อที่จับคู่ไม่ได้จะกลายเป็นรายการ `PROPOSED_SKILL` ให้นักวิเคราะห์พิจารณา ซึ่งเป็นกลไกที่ทำให้อนุกรมวิธานทักษะโตขึ้นจากคำศัพท์ในหลักสูตรของคุณเอง แทนที่จะติดอยู่กับรายการ ESCO ชุดที่ seed มา

### ต้นทุนที่ มข. จ่ายไป เอาไว้ตั้งงบ

สรุปไปได้ 228 จาก 297 หลักสูตร ตกราว **$0.04 ต่อหลักสูตร รวมประมาณ $8.10** ผ่านการรันซ้ำหกรอบ บน Gemini อีก 69 หลักสูตรที่เหลือไม่มี PDF ให้ใช้ ส่วนใหญ่เป็นหลักสูตรแพทย์เฉพาะทางและหลักสูตรที่เพิ่งเปิดใหม่ ให้เผื่อใจว่าจะขาดความครอบคลุมในสัดส่วนใกล้เคียงกัน และวางแผนงานจัดหาเอกสารแยกออกจากงานวิศวกรรม

### การออก PDF ภาษาไทยต้องใช้ TH Sarabun New

PDF ที่ระบบ *ผลิตออกมา* ทั้งหมด (เอกสารประกอบการประชุมสภามหาวิทยาลัย บทสรุป บันทึกมติ) เรนเดอร์ผ่าน Gotenberg โดยฝังฟอนต์ TH Sarabun New ไฟล์ `.ttf` ทั้งสี่ไฟล์ **จงใจไม่เก็บใน git** และต้องวางไว้ที่ `infra/gotenberg/fonts/` ก่อนรัน `docker compose build gotenberg` วิธีหาไฟล์อยู่ใน `infra/gotenberg/README.md`

มีสองเรื่องที่จะสะดุด:

- การ build Docker จะ **ล้มเหลวทันทีและเห็นชัด** ถ้าไม่มีฟอนต์ — ทั้ง `COPY` ที่หยุดการ build และการตรวจนับจำนวน face ของ Sarabun ที่ลงทะเบียนแล้วหลัง `fc-cache` ตรงนี้จงใจ เพราะทางเลือกอีกทางคือเรนเดอร์เป็นกล่องสี่เหลี่ยมเงียบ ๆ ในเอกสารราชการ
- **"Sarabun" ของ Google Fonts เป็นฟอนต์คนละตัว** (ของ Cadson Demak) ไม่ใช่ TH Sarabun New และไม่เข้าเงื่อนไขที่คณะรัฐมนตรีกำหนดสำหรับเอกสารราชการ อย่าเอามาใช้แทน

ห้ามสร้าง PDF ในกระบวนการของแอปเอง ไม่ puppeteer ไม่ react-pdf ไม่ html-pdf — โดยเฉพาะ `@react-pdf/renderer` จัดวางวรรณยุกต์ภาษาไทยผิด และห้ามใช้ใน codebase นี้อย่างชัดเจน ทุกอย่างต้องวิ่งผ่าน `PdfGenerationService` → Gotenberg สัญญาฉบับเต็มอยู่ใน `docs/pdf-generation.md`

## 11. การปรับแบรนด์และ UI

### ระบบ token

design token เก็บเป็น **ค่าสามตัวแบบ OKLCH** ใน `packages/design/src/css/tokens.css` แยกขอบเขตด้วย `[data-theme='light']` และ `[data-theme='dark']` โดยมี utility ของ Tailwind ครอบไว้ ตัวปรับความโปร่งใสจึงใช้ได้ (`bg-surface-1/80`)

`packages/design/src/tailwind-preset.ts` **แทนที่** สเกลสี ระยะห่าง ความมน ขนาดตัวอักษร และเงาของ Tailwind ไม่ใช่ขยายเพิ่ม `bg-slate-500` จึงเป็น error ตอนคอมไพล์โดยตั้งใจ นอกจากนี้ ESLint ยังห้ามเขียนค่าสีฐานสิบหกตรง ๆ และห้ามเรียก `rgb()`/`oklch()` ด้วยตัวเลขดิบ ผ่านกฎ `no-restricted-syntax` ใน `eslint.config.mjs` ส่วนการเขียนครอบตัวแปร CSS นั้นอนุญาต

การสลับธีมใช้แอตทริบิวต์ `data-theme` ไม่ใช่คลาส `dark` ผ่าน `next-themes` ที่ตั้งค่าให้ปลอดภัยกับ SSR หน้าจึงไม่กะพริบเป็นธีมผิดตอนโหลด

**การตั้งชื่อ token สำคัญกว่าที่เห็น** ธรรมเนียมคือ `--color-<family>-default` ไม่ใช่ `--color-<family>` เปล่า ๆ ชื่อผิดจะไม่มีค่าสำรองให้ — จะเรนเดอร์เป็นกล่องดำใน SVG หรือดำสนิทใน HTML grep `tokens.css` ก่อนจะตั้งชื่อ token ขึ้นมาเอง เรื่องที่เกี่ยวข้องกัน: ใน SVG ให้ลงสี `<text>` ผ่านแอตทริบิวต์ `fill=` ไม่ใช่ `style.fill`

### กฎสามข้อสำหรับการเปลี่ยนระเบียบวิธี

1. **ขยับเลขเวอร์ชันเสมอ** `HEALTH_SCORE_VERSION = 'health-score.v4.0'` ใน `packages/db/src/health-score.ts` ถูกประทับลงทุกแถวคะแนน การเปลี่ยนสูตรโดยไม่ขยับเวอร์ชันทำให้การเปรียบเทียบย้อนหลังผิดแบบเงียบ ๆ และทำลายร่องรอยการตรวจสอบที่ทำให้กรรมการสภามหาวิทยาลัยถามได้ว่า "ทำไมคะแนนหลักสูตรนี้เปลี่ยนไป"
2. **อัปเดตเอกสารใน commit เดียวกัน** เอกสารใต้ `docs/methodologies/` คือฉบับที่ใช้อ้างอิงว่าตัวเลขหมายถึงอะไร เอกสารที่คลาดเคลื่อนแย่กว่าไม่มีเอกสารเลย
3. **ค่าว่างไม่ใช่ศูนย์** กฎรากฐานของคะแนนสุขภาพ: ตัววัดที่ขาดหายต้อง **ถูกตัดออกจากการเฉลี่ย** ห้ามแทนด้วย 0 หรือ 50 ทุกคะแนนพก `dataCompletenessPct` มาด้วย และหน้าจอแสดงค่าที่ขาดหายเป็น `—` อย่าไป "แก้" ข้อนี้ การแทนด้วยศูนย์คือการลงโทษหลักสูตรเพราะช่องว่างข้อมูลของคุณเอง ซึ่งเป็นรูปแบบความล้มเหลวที่ทำลายความเชื่อถือของสภามหาวิทยาลัยได้ตรงที่สุด

### จุดที่น้ำหนักของคุณจะต่างออกไป

คะแนนสุขภาพของ มข. ประกอบด้วยมิติหลายมิติ (อุปสงค์ การเงิน คุณภาพ ความสอดคล้อง ขีดความสามารถ) โดยแต่ละมิติมีตัวขับเคลื่อนย่อยอยู่ข้างใน บางตัวถ่วงน้ำหนักตามวิจารณญาณเชิงกลยุทธ์ของ มข. อย่างชัดเจน เช่น ตัวขับเคลื่อนด้านอุปสงค์ที่ถ่วงน้ำหนักเพื่อสะท้อน "การเคลื่อนไปสู่การพัฒนากำลังคนแบบไม่รับปริญญา ซึ่งบีบหลักสูตรระดับบัณฑิตศึกษา" สิ่งเหล่านี้เป็น **จุดยืนของสภามหาวิทยาลัยขอนแก่น ไม่ใช่สัจธรรมสากล** และควรเผื่อใจว่าจะต้องเปลี่ยน

แพตเทิร์นที่ปลอดภัยคือเพิ่มน้ำหนักของคุณเป็นเวอร์ชันใหม่วางคู่กับของ มข. แทนการแก้ทับ วิธีนี้ยังคงรับ merge การเปลี่ยน *โครงสร้าง* ของสูตรจาก upstream ได้ ขณะที่ *ค่าพารามิเตอร์* เป็นของคุณเอง

**ก่อนเปลี่ยนอะไรที่ข้ามโมดูล ให้อ่าน `docs/evaluation-pipeline.md`** เอกสารนั้นทำแผนที่ว่าคะแนนสุขภาพ วงจรชีวิต ความเสี่ยง KKU matrix และการจัดกลุ่มแบบ BCG เกี่ยวพันกันอย่างไร ผ่าน prompt ของ AI 22 ตัวและชุด cross-join การเปลี่ยนน้ำหนักตัวเดียวโดด ๆ อาจดันหลักสูตรข้ามเส้นแบ่งควอดรันต์ BCG ไปโดยไม่ได้ตั้งใจ

### การจัดสรรต้นทุนยังไม่เสร็จ — ที่ มข. ก็เช่นกัน

`docs/methodologies/cost-allocation.md` ยังเป็น **ร่าง v0** รอความเห็นชอบจากคณะกรรมการการเงิน เอกสารนี้วางกลุ่มต้นทุนไว้ห้ากลุ่มพร้อมสูตรแบบอิงกิจกรรม และ connector ก็ป้อนข้อมูลดิบเข้ามาให้แล้ว แต่ยังไม่มีตัวเลขต้นทุนรายหลักสูตรตัวไหนที่เสนอต่อสภามหาวิทยาลัยได้ ถ้าการวิเคราะห์ความยั่งยืนทางการเงินเป็นเรื่องเร่งด่วนของคุณ นี่คืองานที่ยังไม่เสร็จจริง ๆ ที่รับสืบทอดมา ไม่ใช่แค่ขั้นตอนการตั้งค่า

## 13. ชั้น AI

### ทุกอย่างวิ่งผ่าน `AiService`

`packages/shared/src/ai/` คือชั้นนามธรรม โมดูลต่าง ๆ ไม่ import `@google/genai` หรือ `@anthropic-ai/sdk` โดยตรง การเลือก provider ทำผ่าน `AI_PROVIDER`:

| ค่า | สถานะ |
|---|---|
| `google` | Gemini — ค่าตั้งต้น และเป็นตัวที่ pipeline หลักสูตรถูกปรับจูนมาให้ใช้ |
| `anthropic` | Claude — **จำเป็นสำหรับโมดูล AI Analyst** ที่ใช้ tool-use แบบเนทีฟ |
| `stub` | ค่าตอบแบบกำหนดผลได้แน่นอน ทำงานได้โดยไม่ต้องมี API key มีประโยชน์ตอนพัฒนาบนเครื่องตัวเอง |
| `openrouter`, `intelsphere` | เป็น stub ที่ throw ตอนถูกเรียก จงใจให้ดัง ไม่ใช่ถอยไปใช้อย่างอื่นเงียบ ๆ |

Gemini มี embeddings แต่ Claude ไม่มี ตอนตั้ง `AI_PROVIDER=anthropic` ตัว factory จึงส่งงาน `embed()` ต่อไปให้ Google เองโดยที่ผู้เรียกไม่ต้องรู้ ถ้าใช้ Claude ให้ตั้งคีย์ทั้งสองตัว

### prompt คือโค้ดที่กำกับเวอร์ชัน

`packages/shared/src/ai/prompts/` มีโมดูล prompt อยู่ราวสามสิบตัว แต่ละตัว export ค่าคงที่ของเวอร์ชัน schema ผลลัพธ์แบบ Zod และตัวสร้างข้อความ กฎข้อนี้เด็ดขาด: **เปลี่ยนพฤติกรรมเมื่อไร ต้องเป็นเวอร์ชันใหม่ ห้ามแก้เวอร์ชันที่เผยแพร่แล้วทับลงไป** `AiExtraction.methodVersion` บันทึกว่าแถวนั้นผลิตด้วยเวอร์ชันไหน ผลลัพธ์เก่าจึงยังแยกแยะออก และการรันซ้ำยังตรวจสอบย้อนหลังได้

ทุก prompt ต้องเป็นไปตาม `docs/prompt-standard.md` ซึ่งประกาศใช้เมื่อ 2026-08-16 และ **บังคับด้วย ratchet test** ที่ `packages/shared/test/prompt-standard-conformance.test.ts` (ไฟล์ที่ยังไม่ได้เขียนใหม่อยู่ในรายการยกเว้นที่ระบุไว้ชัด และรายการนั้นมีแต่หดลง) กฎสำคัญของมาตรฐานนี้คือ:

- **ผลวิเคราะห์ที่เป็นข้อความอิสระต้องเป็นภาษาอังกฤษทั้งหมด** ข้อนี้กลับทิศจากกลยุทธ์เดิมที่ให้ภาษาไทยเป็นหลัก ภาษาไทยเหลืออยู่เฉพาะในรายการยกเว้นที่ปิดรายการแล้ว ได้แก่ `recruitmentSummaryTh` ใน `program-digest` (เป็นข้อความประชาสัมพันธ์ ไม่ใช่บทวิเคราะห์) ฟิลด์สกัดตระกูล `nameTh` และทั้งไฟล์ `evaluation-question-translate`
- **การอ้างอิงกลับได้:** ตัวเลขในผลลัพธ์ต้องสืบกลับไปยัง snapshot ข้อมูลที่ส่งให้โมเดลในการเรียกครั้งนั้นได้ ห้ามเป็นตัวเลขที่โมเดล "รู้มา" เกี่ยวกับมหาวิทยาลัยของคุณหรือเกี่ยวกับอุดมศึกษาไทยโดยรวม
- **ข้อมูลนำเข้าที่ขาดหายห้ามเดา** ให้แสดงว่า "ไม่มีข้อมูล" หรือคืน `null` อย่างชัดเจน ห้ามใส่ค่าที่ฟังดูสมเหตุสมผลแทน และห้ามใช้ศูนย์แทนค่าที่ไม่ทราบ

### ธรรมาภิบาล

`@AiCall()` บนทุก endpoint ที่เรียก AI จะเขียนแถว `AiInference` ส่วน `@AuditLog()` บนทุก mutation จะเขียนแถว `AuditLog` decorator ทั้งสองตัวอยู่ใน `apps/api/src/common/decorators.ts` ต้นทุนถูกติดตามรายการเรียก (`AiInference.costEstimateUsd`) และมีตัวคุมโควตาเป็นดอลลาร์ต่อผู้ใช้ต่อวัน (`AiQuotaGuard`) ปรับได้ผ่าน `AI_QUOTA_*_USD` ซึ่งเมื่อฐานข้อมูลมีปัญหาจะ *ปล่อยผ่าน* เพราะโควตาเป็นเรื่องธรรมาภิบาล ไม่ใช่เรื่องความมั่นคงปลอดภัย

มีชุดประเมินด้วยคำถามมาตรฐาน 25 ข้อ (`pnpm ai:eval`) และชุดวัดความแม่นยำ (`pnpm ai:eval-accuracy`) พร้อมฉลากใต้ `gold-labels/` นโยบายฉบับเต็มอยู่ใน `docs/ai-governance.md` รวมถึงกฎการถอยไปใช้โมเดลสำรอง (เฉพาะข้อผิดพลาดชั่วคราวเท่านั้น — 429/5xx/timeout ส่วนความล้มเหลวแบบกำหนดผลได้แน่นอนให้ throw ต่อ) และตัวกรองผลลัพธ์ที่ลบเลขประจำตัวประชาชน หมายเลขโทรศัพท์ และอีเมลที่ไม่ใช่ของสถาบัน ออกจากคำตอบของโมเดล

## 14. กับดักที่จะกินเวลาไปหลายวัน

ทุกข้อในบทนี้ได้มาด้วยราคาแพง แต่ละข้อเคยเป็นข้อบกพร่องจริงใน repository นี้

### กับดักที่ 1: สเกลระยะห่างของ Tailwind ในโครงการนี้เล็กเป็นครึ่งหนึ่ง และคีย์ที่ขาดหายจะไม่ออก CSS เลย

`packages/design/src/tokens/spacing.ts` **แทนที่** สเกลระยะห่างของ Tailwind และค่า `1` ของมันคือ **2px ไม่ใช่ 4px** อ่านไฟล์นั้น คอมเมนต์ส่วนหัวคือคำอธิบายที่ดีที่สุดเท่าที่จะหาได้

ผลที่ตามมามีสองข้อ แยกจากกัน:

- **ทุก utility ระยะห่างเล็กเป็นครึ่งหนึ่งของที่นักพัฒนาที่ชิน Tailwind คาดไว้** `h-4 w-4` บนไอคอน lucide เรนเดอร์ออกมา **8px** ไม่ใช่ 16px
- **utility ที่คีย์ไม่มีในสเกล จะไม่ออก CSS เลยแม้แต่บรรทัดเดียว** ไม่ใช่ถอยไปใช้ค่าสำรอง แต่คือไม่มีอะไรเลย `pl-9` คือ padding ศูนย์ `gap-1.5` เคยเป็น gap ศูนย์แบบเงียบ ๆ จนกระทั่งมีการเพิ่มคีย์ `1.5` เข้าไป ส่วน `h-3.5 w-3.5` ไม่ออกอะไรเลย ไอคอนเหล่านั้นจึงตกกลับไปใช้ขนาดในตัวของ SVG ที่ 24×24

คีย์ `3.5` **จงใจไม่มี และห้าม "เติมให้ครบ"** จาก 338 จุดที่ใช้คีย์นี้ มี 333 จุดเป็น `h-3.5 w-3.5` บนไอคอน การนิยามคีย์นี้จะย่อองค์ประกอบราว 167 ชิ้นให้เหลือ 7×7 ใน commit เดียว

ทางแก้สำหรับไอคอนคือสเกล `iconSize` ที่แยกไว้ต่างหากใน `packages/design/src/tokens/icon.ts` เปิดใช้เป็น utility คลาสเดียว `size-icon-xs` … `size-icon-xl` (12/14/16/20/24px) **ใช้ `size-icon-*` กับไอคอน และใช้สเกลระยะห่างกับกล่องเลย์เอาต์เท่านั้น**

เรื่องของ preset อีกสองข้อ:

- **ไม่ hot-reload** เปลี่ยน token แล้วต้องรีสตาร์ต dev server
- **Next แคช CSS ที่คอมไพล์แล้วไว้ใน `.next/cache/webpack` ข้ามการรีสตาร์ต** ถ้าเปลี่ยน token แล้วเหมือนไม่มีอะไรเกิดขึ้น ให้ล้างไดเรกทอรีนั้นก่อนจะไปไล่หาสาเหตุอื่น ไม่อย่างนั้นจะเสียเวลาไล่หาสาเหตุที่ไม่มีอยู่จริงไปทั้งบ่าย

### กับดักที่ 2: `realDataWhere()` — ส่วนที่ว่างเปล่าทั้งที่ฐานข้อมูลมีข้อมูล

`packages/db/src/data-quality.ts` export `realDataWhere()` ปัจจุบันคือ `data-quality.v2` ในโหมด **STRICT** แถวตัววัดจะนับว่าเป็นข้อมูลจริงก็ต่อเมื่อ `DataSource` ของ `IngestionRun` ที่ผูกอยู่มีค่า `mocked = false` เท่านั้น ส่วนแถวที่ `ingestion_run_id IS NULL` ถือว่าน่าสงสัยและ **ถูกตัดออก**

ดังนั้นส่วนของ UI จะว่างเปล่าทั้งที่เห็นแถวใน SQL ได้จากสองสาเหตุที่แยกจากกัน:

1. `data_sources.mocked = true` — และสังเกตว่า `mocked` เป็น **คนละคอลัมน์กับ `status`** ค่า `status='real'` ไม่ได้แปลว่า `mocked=false` ให้พลิกทั้งคู่เสมอ ในคราวเดียว
2. `ingestion_run_id IS NULL` — มีเส้นทางการเขียนข้อมูลที่ลืมส่ง `ctx.runId` ต่อไป

SQL สำหรับคัดกรอง:

```sql
SELECT COUNT(*) FILTER (WHERE t.ingestion_run_id IS NOT NULL) AS tagged,
       COUNT(*) FILTER (WHERE ds.mocked = false)              AS pass
  FROM <table> t
  LEFT JOIN ingestion_runs ir ON ir.id = t.ingestion_run_id
  LEFT JOIN data_sources  ds ON ds.id = ir.data_source_id
 WHERE t.program_id = '...';
```

`pnpm provenance:backfill` (ค่าตั้งต้นเป็น dry-run) รายงานจำนวนแถวกำพร้าต่อตาราง ส่วน `pnpm data-sources:audit` จับความเบี่ยงเบนระหว่าง `status` กับ `mocked` รันทั้งสองตัวหลังพลิก connector ทุกครั้ง และหลังรีเซ็ตฐานข้อมูลทุกครั้ง

### กับดักที่ 3: บัญชี Oracle จะถูกล็อกเมื่อเปิดการเชื่อมต่อถี่เกินไป

บัญชี Oracle ของสำนักทะเบียน มข. จะล็อกผู้ใช้ทันทีถ้าสคริปต์เปิดการเชื่อมต่อใหม่ทุกครั้งที่เรียกภายในลูป ให้ใช้หนึ่ง session ต่อหนึ่งการรัน — codebase มี `OracleSession` ไว้เพื่อการนี้โดยเฉพาะ และ `apps/ingestion/src/lib/oracle-client.ts` ครอบวงจรชีวิตไว้ให้แล้ว อย่าใช้ `withConnection` ในลูป

หลักการนี้ใช้ได้กับที่อื่นด้วย: ฐานข้อมูลของสถาบันทุกตัวที่ไปแตะ ล้วนมีนโยบายจำกัดอัตราการเชื่อมต่อ ที่เราจะรู้ก็ต่อเมื่อละเมิดมันไปแล้ว "ลุยก่อนแล้วค่อยถามทีหลัง" เป็นลำดับที่ผิดสำหรับเรื่องนี้ เพราะบัญชีบริการที่ถูกล็อกแปลว่าต้องไปคุยกับทีมโครงสร้างพื้นฐาน ไม่ใช่แค่ retry

### กับดักที่ 4: ไฟล์ `.env` ประจำแต่ละแอป และความล้มเหลวเงียบของ Edge middleware

Next.js โหลด `.env` จาก `apps/web/` **ไม่เคย** โหลดจากรากของ monorepo เมื่อไฟล์นั้นหายไป bundle ของ middleware ที่รันบน Edge runtime จะคอมไพล์โดยที่ `NEXTAUTH_SECRET` เป็น undefined และ **ทุก route ที่ต้องล็อกอินจะ 307 กลับไปที่ `/signin`** ขณะที่ฝั่ง Node runtime ซึ่งเป็นที่ที่การล็อกอินทำงานจริง กลับทำงานปกติ อาการดูเหมือนบั๊กของ auth แต่จริง ๆ เป็นบั๊กของการโหลด env

วิธีแก้: `pnpm link-env` และบน Windows ที่สคริปต์คัดลอกแทนการ symlink ให้รันซ้ำทุกครั้งหลังแก้ `.env` ที่ราก

ข้อจำกัดเชิงสถาปัตยกรรมที่เกี่ยวข้อง: `apps/web/middleware.ts` ตรวจสอบ session cookie ด้วย `jose` โดยตรง และ **ต้องไม่ import `@/lib/auth`** (ซึ่งลาก Prisma เข้ามา และใช้ได้เฉพาะบน Node) การใส่การเรียก Prisma ลงใน middleware จะทำให้ build ฝั่ง Edge พัง

### กับดักที่ 5: คะแนน 0 ไม่ได้แปลว่าได้ศูนย์

ในไฟล์ส่งออกของ DQ คะแนนมอดูลที่เป็น `0` หมายถึง **ไม่ได้เข้าสอบมอดูลนั้น** ถ้าตีความเป็นศูนย์จริง ค่าเฉลี่ยของทุกมอดูลจะถูกถ่วงลงโดยนักศึกษาที่ไม่เคยสอบมอดูลนั้นเลย ซึ่งหน้าตาเหมือนปัญหาสมรรถนะของจริงทุกประการ และจะรอดสายตาผู้ตรวจไปได้เพราะตัวเลขดูสมเหตุสมผล

โครงการนี้ป้องกันด้วยฟังก์ชันตรวจตัวเดียวที่ export ออกมาใช้ร่วมกัน คือ `dqScoreWasTaken()` เพื่อไม่ให้แต่ละที่ไปเขียน `> 0` กันเอง แล้วสุดท้ายมีที่หนึ่งเขียนเป็น `>= 0` ค่าศูนย์ถูกตัดออกจากทั้ง `scoreSum` และ `takenCount`

บทเรียนกว้าง ๆ ที่ไม่ได้จำกัดอยู่แค่ DQ คือ เมื่อใดที่แหล่งข้อมูลเข้ารหัส *สถานะ* ไว้ในตัว *ค่าที่วัด* ให้แปลงมันที่ขอบระบบ แล้ว export ฟังก์ชันตรวจออกมาหนึ่งตัวให้ทั้งระบบใช้ร่วมกัน อย่าปล่อยให้การเข้ารหัสนั้นเดินทางต่อเข้าไปข้างใน

มีกฎการรายงานอีกสองข้อที่มาคู่กัน — ช่องที่มีนักศึกษาที่มีคะแนนน้อยกว่า **6 คน** จะถูกปิดไว้ และนับเฉพาะหลักสูตรระดับปริญญาตรีเท่านั้น ช่องว่างจึงหมายถึง "จำนวนน้อยเกินกว่าจะรายงาน" ส่วนการที่ไม่มีแถวของระดับบัณฑิตศึกษาไม่ใช่ข้อมูลขาด ทั้งสองข้อจะถูกเข้าใจผิดว่าเป็นข้อบกพร่องเสมอ หากหน้าจอไม่บอกไว้ ฉะนั้นต้องบอกไว้ในหน้าจอ

### กับดักที่ 6: barrel ของ `@kku/shared` ทำให้ `node:crypto` รั่วออกมา

`packages/shared/src/index.ts` re-export subpath ที่ import `node:crypto` (`pdf/hash.ts`, `ingestion/kmitl-token.ts`, `ai/providers/google-ai.ts`) client component จึง **ต้องใช้ `import type` เท่านั้น** เมื่อดึงจาก `@kku/shared` การ import แบบ runtime จะทำให้ build พัง

ถ้าต้องใช้ค่าจริงตอน runtime ใน client component ให้ import จาก subpath ที่เจาะจง แทนการดึงผ่าน barrel หรือย้ายค่านั้นไปไว้ในโมดูลที่ปลอดภัยกับฝั่ง client

### กับดักที่ 7: dev server ค้างข้อมูลเก่า สองแบบซ้อนกัน

บั๊กข้อมูลค้างเก่าสองตัวที่คนละเรื่องกัน แต่แสดงอาการเหมือนกันเป๊ะ — "สคริปต์ `tsx` ทำงานได้ แต่แอปที่รันอยู่ไม่ได้":

- **`next dev` ยังถือ Prisma client ตัวเก่าไว้หลังแก้ schema** ถ้าคิวรีผ่าน `pnpm tsx` ใหม่ ๆ สำเร็จ แต่ route บน dev พัง ให้รีสตาร์ต dev server อย่าไล่หาสาเหตุต่อ
- **`nest start --watch` เฝ้าดูแค่ `apps/api/src`** การแก้ `packages/db`, `packages/shared` และอื่น ๆ ไม่ทำให้โหลดใหม่ ให้รีสตาร์ต API

ทั้งสองกรณี สัญชาตญาณที่อยากไล่หาสาเหตุต่อนี่แหละคือสิ่งที่กินเวลา

### กับดักที่ 8: อิมเมจคอนเทนเนอร์ที่ไม่ได้รันเป็น root กับสิทธิ์ความเป็นเจ้าของ volume

MinIO บน production รันด้วย UID 65532 (อิมเมจที่ Chainguard สร้างใหม่ เพราะ `minio/minio` ต้นทางหมดอายุการสนับสนุนแล้ว) volume ข้อมูลต้อง chown เป็น 65532 **บนโฮสต์** เพราะการรัน `chown` จากใน compose จะโดน EPERM ภายใต้ `cap_drop` ส่วน secret แบบไฟล์ต้องมีสิทธิ์ 0644 ไม่งั้น MinIO จะวนล่มพร้อมข้อความ "Invalid credentials" ฝั่ง dev ไม่มีวันเจออาการนี้ เพราะ dev ใช้ข้อมูลรับรองผ่านตัวแปร env และ volume ก็ตั้งค่าถูกอยู่แล้ว `scripts/deploy.sh` จัดการให้ทั้งสองเรื่อง อ่านไฟล์นั้นก่อนจะเขียนเส้นทาง deploy ของตัวเอง

อีกเรื่องหนึ่งแยกจากกัน: คอนเทนเนอร์ ingestion รันด้วย UID **1010** ขณะที่ web และ api รันด้วย 1001 คำสั่ง `user:` ระดับ compose ของ ingestion จึงต้องระบุ `1010:1010`

### การทดสอบเหล่านี้ปกป้องอะไรอยู่จริง ๆ

ชุดทดสอบนี้เอนไปทาง **ฟังก์ชันบริสุทธิ์ที่บรรจุนโยบายไว้ข้างใน** มากกว่าการทดสอบเชิงบูรณาการอย่างเห็นได้ชัด ได้แก่ กราฟการเปลี่ยนสถานะและการกั้นตามบทบาท การจัดการค่าว่างของคะแนนสุขภาพ การจับคู่ใน transform ของ connector เคสขอบเรื่องลำดับ prefix ในการจับคู่ตำแหน่งทางวิชาการ ratchet test ของมาตรฐาน prompt โครงสร้างเกณฑ์ AUN-QA และรูปแบบการปฏิเสธคำถามที่ไม่ปลอดภัย นี่เป็นการเลือกโดยตั้งใจ เพราะจุดเหล่านี้คือจุดที่การถดถอยแบบเงียบ ๆ จะเปลี่ยนสิ่งที่สภามหาวิทยาลัยได้รับฟัง

ตอนเขียน connector ของตัวเอง ให้ทำตามแพตเทิร์นเดิม: วาง fixture ไว้ที่ `apps/ingestion/test/fixtures/<slug>/` และเขียน transform test ที่ยืนยันว่าทุกรหัสใน fixture มีการจับคู่ ตัวอย่างที่ควรยึดคือ test ที่ครอบคลุมการจับคู่สถานะของ `kku-registry` ซึ่งกันไม่ให้สำนักทะเบียนเพิ่มรหัสสถานะใหม่เข้ามาแบบเงียบ ๆ

### CI

`.github/workflows/` มี workflow สี่ตัว: `pr.yml`, `release.yml`, `e2e.yml`, `load.yml`

`pr.yml` ทำตามลำดับนี้: รัน migration linter เพื่อหา DDL ที่ทำลายข้อมูล, lint **เฉพาะไฟล์ที่เปลี่ยน**, ตรวจ type, รัน Prisma generate, ยก Postgres พร้อม pgvector ขึ้นมา, apply migration ลงฐานข้อมูลทดสอบ แล้วจึงรันชุดทดสอบ

**สถานะที่รับสืบทอดมา:** `PR checks` เขียวทั้งชุด ส่วน `Release bundle` (ตอน push tag) รัน `pnpm lint` ทั้ง repo และ **แดงเพราะหนี้ lint ที่ค้างอยู่ก่อนแล้ว** ไม่ใช่เพราะการเปลี่ยนแปลงชิ้นใดชิ้นหนึ่ง ตัว tarball แบบ pack-and-ship ที่สร้างบนเครื่องคือ artifact จริงของการปล่อยเวอร์ชัน ควรเคลียร์หนี้ก้อนนั้นแต่เนิ่น ๆ เพื่อให้ป้าย CI สีแดงใน fork ของคุณมีความหมาย

## 16. การ deploy และการกำหนดขนาดโครงสร้างพื้นฐาน

### รูปแบบ: pack-and-ship

เครื่อง production **ไม่เคยดึงอิมเมจจาก registry** วิธีคือ build อิมเมจบนเครื่องพัฒนา มัดรวมเป็น tarball ไฟล์เดียว โอนไปที่เครื่องปลายทาง แล้ว `docker load` บนเครื่องนั้น

```bash
# On the dev machine (inside WSL2 if on Windows)
pnpm build:release <version>
# → dist/program-landscape-<version>.tar.gz  (~2.5 GB)
# → dist/program-landscape-<version>.tar.gz.sha256
```

ในไฟล์มัดรวมนี้มี `images.tar` (4 อิมเมจ ทั้งหมดเป็น `linux/amd64`) ไฟล์ compose ไฟล์ตั้งค่า nginx สคริปต์ deploy ไฟล์ systemd unit และเทมเพลต env ไม่ต้องส่งอะไรไปเพิ่มอีก

**อิมเมจ production ทุกตัวเป็น `linux/amd64`** ถ้าเครื่องพัฒนาเป็น Mac สถาปัตยกรรม ARM การ build ต้องใส่ `--platform linux/amd64`

**จุดที่ต้องระวังของกระบวนการ build:** `docker buildx` รัน `COPY` ของแต่ละอิมเมจตอนที่ stage นั้นทำงาน commit ที่ลงมากลางคันจึงเข้าไปอยู่ในบางอิมเมจแต่ไม่เข้าอีกบางอิมเมจ ถ้ามี fix ที่ต้องอยู่ในชุดนี้แน่ ๆ ให้ฆ่า build ทิ้ง เคลียร์ แล้วเริ่มใหม่

บนเครื่องปลายทาง `scripts/deploy.sh` รันซ้ำได้โดยผลลัพธ์ไม่เปลี่ยน และใช้การสลับ symlink แบบอะตอมมิก (`/opt/program-landscape/current → releases/<ver>`) เป็นจุดที่ย้อนกลับไม่ได้ ทุกอย่างก่อนหน้านั้นจะถูกย้อนคืนอัตโนมัติเมื่อล้มเหลว migration รันใน **คอนเทนเนอร์ที่ใช้แล้วทิ้ง** (`docker compose run --rm --entrypoint "" api node node_modules/.bin/prisma migrate deploy`) ไม่ใช่รันจากคอนเทนเนอร์ API ตัวยืนพื้น ซึ่งจะไปแย่งกับ ingestion ตอนเริ่มระบบ

สคริปต์ที่ใช้คู่กัน: `rollback.sh`, `backup.sh`, `restore.sh`, `smoke-test.sh`, `pre-deploy-snapshot.mjs`, `generate-self-signed-cert.sh`

การย้อนกลับ **ค่าตั้งต้นคือย้อนเฉพาะโค้ด** `rollback.sh` จะถามว่าจะกู้ snapshot ฐานข้อมูลก่อน deploy ด้วยหรือไม่ ซึ่งคำตอบตามปกติคือไม่ เพราะ migration เดินหน้าอย่างเดียว และโค้ดที่ย้อนกลับไปก็ยังเข้ากับ schema ได้

### โครงสร้าง TLS

รูปแบบที่ มข. ใช้ ซึ่งมหาวิทยาลัยไทยส่วนใหญ่ทำตามได้:

```
public → university reverse proxy (terminates public cert)
       → re-encrypts, forwards to our host on :8443 (self-signed)
       → our internal nginx (TLS + path routing)
       → web / api over plain HTTP inside the docker network
```

proxy ต้นทางตั้งค่าไว้ที่ `proxy_ssl_verify off` (หรือปักหมุดใบรับรองด้วย SHA-256) มีรายละเอียดของ nginx อยู่ข้อหนึ่งที่จะเล่นงานคนที่รื้อไฟล์ตั้งค่าใหม่: `next-auth` อยู่ที่ `/api/auth/*` บนแอปเว็บ ขณะที่ prefix ของ NestJS คือ `/api/v1` จึงต้องมีกฎ `location /api/auth/` → web แยกไว้ชัดเจน ไม่งั้น auth จะ 404 เพราะไปชนกับ router ของ Nest

security header ตั้งที่ **ชั้นแอปพลิเคชัน** ไม่ใช่ที่ nginx ค่าจึงถูกต้องเสมอไม่ว่าคำขอจะเดินผ่าน proxy เส้นทางไหน

`DEPLOYMENT.md` คือคู่มือปฏิบัติการ ส่วน `docs/deployment/kku-network-integration.md` คือเอกสารที่ส่งให้ทีมเครือข่าย

### การกำหนดขนาด

ตัวเลขต่อไปนี้มาจาก `docs/production-infrastructure.md` เป็นตัวเลขจริงจากระบบของ มข. ไม่ใช่ตัวเลขที่คิดขึ้นเอง:

| ทรัพยากร | ขั้นต่ำ | ที่แนะนำ | เพราะอะไร |
|---|---|---|---|
| CPU | 4 คอร์ | **8 คอร์** | Gotenberg เปิด Chromium แบบ headless หนึ่งตัวต่อการเรนเดอร์หนึ่งครั้ง ขณะที่ worker ของ ingestion และการเรียก AI ทำงานพร้อมกัน |
| RAM | 16 GB | **32 GB** | shared buffer ของ Postgres (4 GB) + แคชของ MinIO + จุดพีคของ Chromium (เรนเดอร์เอกสารประชุมสภาพร้อมกัน 4–8 งาน) + heap ของ Node อีก 3 บริการ |
| ดิสก์ | SSD 500 GB | **NVMe SSD 1 TB** | Postgres + MinIO + snapshot ก่อน deploy 90 วัน + backup รายคืน 30 วัน + เลเยอร์ของ Docker + คลัง PDF หลักสูตร (ราว 5 GB ที่ 297 หลักสูตร) |
| ระบบปฏิบัติการ | Ubuntu 22.04 LTS | Ubuntu 24.04 LTS | x86_64 เท่านั้น |
| GPU | ไม่ต้องมี | ไม่ต้องมี | การอนุมานทั้งหมดเรียกผ่าน API ของผู้ให้บริการ |

อ่านส่วนที่เหลือของเอกสารนั้นเพื่อดูตารางข้อกำหนดเครือข่ายขาเข้าและขาออก ซึ่งไล่ปลายทางทุกแห่งที่เครื่องต้องติดต่อได้ และเป็นสิ่งที่ทีมเครือข่ายจะถามหาพอดี

**เรื่องพื้นที่ดิสก์เป็นปัญหาปฏิบัติการจริง ไม่ใช่รายละเอียดปลีกย่อย** เครื่องพัฒนาของ มข. เคยแตะ 92% ระหว่างรอบ build หลายรอบติดกัน (tarball รอบละราว 2.5 GB บวกไดเรกทอรี staging อีกราว 6 GB บวกแคช build ที่เรียกคืนได้อีก 14 GB) และเครื่อง production เคยแตะ 100% ระหว่าง deploy เพราะ backup เก่าสะสม กฎคร่าว ๆ คือ เก็บ tarball สามรุ่นล่าสุดไว้บนเครื่องพัฒนา และรัน `docker builder prune -af` หลังจบรอบการปล่อยเวอร์ชันทุกครั้ง เก็บไดเรกทอรีรุ่น backup และอิมเมจสามชุดล่าสุดไว้บน production และเช็ก `df -h /` **ก่อน** รัน `deploy.sh` เสมอ เพราะ snapshot ก่อน deploy ต้องการที่ว่างราว 3 GB

การสำรองข้อมูลตั้งเวลาด้วย systemd (ทุกคืนเวลา 02:00 ตามเวลาไทย) ไม่ใช่ cron ไฟล์ unit มาพร้อมในชุดติดตั้งใต้ `infra/systemd/` การเก็บรักษาคือ รายวัน 30 วัน ก่อน deploy 90 วัน รายเดือน 365 วัน

## 17. PDPA และธรรมาภิบาลข้อมูล

**ระบบนี้เก็บข้อมูลส่วนบุคคลของนักศึกษาและบุคลากร** ไม่ใช่แค่ข้อมูลรวมยอด แต่เป็นระเบียนรายบุคคล ได้แก่ เลขประจำตัวประชาชนที่ผ่านการ hash ชื่อ ปีเกิด ประวัติการจ้างงาน คุณวุฒิการศึกษา และผลการประเมินการสอน

### ความเห็นชอบของ มข. ไม่ได้โอนมาถึงคุณ

แนวปฏิบัติด้าน PDPA ที่บันทึกไว้ทั่ว codebase นี้ — ทั้งการ projection คอลัมน์ในแต่ละ connector การ hash ตรงเส้นแบ่ง การปิดกั้นเซลล์ขนาดเล็กด้วย `HAVING COUNT(*) >= 5` และการวิเคราะห์ฐานทางกฎหมายใน `docs/pdpa.md` — ผ่านความเห็นชอบของ **เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคลของ มข.** สำหรับการประมวลผล **ของ มข.** เท่านั้น สถาบันของคุณเป็น **ผู้ควบคุมข้อมูลส่วนบุคคล** คนละรายตามพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 จึงต้องมีความเห็นชอบจากเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคลของสถาบันเอง โดยพิจารณาจากบัญชีรายการข้อมูลของสถาบันเอง ก่อนเริ่มประมวลผลสิ่งใด

`docs/pdpa.md` และ `docs/dsar-workflow.md` เป็น **จุดตั้งต้น** ไม่ใช่ความเห็นชอบที่โอนต่อกันได้ ให้อ่านในความหมายว่า "นี่คือแบบที่เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคลของมหาวิทยาลัยไทยแห่งหนึ่งเคยรับได้ พร้อมเหตุผลประกอบ" แล้วจึงให้เจ้าหน้าที่ของสถาบันคุณพิจารณาเทียบกับสิ่งที่กำลังจะทำจริง

### เอกสารสองฉบับนี้มีอะไรอยู่บ้าง

`docs/pdpa.md`: บทบาท (ผู้ควบคุมข้อมูลส่วนบุคคล / ผู้ประมวลผลข้อมูลส่วนบุคคล) บัญชีรายการข้อมูลส่วนบุคคล การวิเคราะห์ฐานทางกฎหมายแยกตามประเภทข้อมูล วิธีรองรับสิทธิของเจ้าของข้อมูลส่วนบุคคลตามมาตรา 30–36 การวิเคราะห์การส่งข้อมูลออกนอกราชอาณาจักร (เกี่ยวข้องเพราะการเรียก AI ส่งข้อมูลออกนอกประเทศ) ระยะเวลาเก็บรักษา audit log จุดตรวจการลดปริมาณข้อมูล การรับมือเหตุละเมิด และการทบทวนประจำปี

`docs/dsar-workflow.md`: ขั้นตอนปฏิบัติเมื่อมีคำขอใช้สิทธิเข้าถึงข้อมูล — การรับเรื่อง เส้นทางการส่งออกข้อมูลสำหรับผู้ดูแลระบบ การพิสูจน์ตัวตน การขอแก้ไขข้อมูล การขอลบข้อมูล การคัดค้านการตัดสินใจโดยระบบอัตโนมัติ และการเก็บบันทึกหลักฐาน

### การตัดสินใจเชิงออกแบบที่แบกน้ำหนักด้าน PDPA ไว้

รักษาข้อเหล่านี้ไว้ตอนเขียน connector ของตัวเอง:

- **รวมยอดตั้งแต่ต้นทาง** ประโยค `GROUP BY` และ `HAVING` ใน SQL ทำงานบนเครื่องต้นทาง ข้อมูลรายบุคคลจึงไม่เคยถูกส่งออกมาจากที่นั่นเลย
- **hash ตรงเส้นแบ่ง** `hashCitizenId()` ทำงานใน `transform()` เลขประจำตัวประชาชนดิบจึงไม่เคยถูกบันทึกลงฐานข้อมูล
- **ลดความละเอียดของวันที่** วันเกิดถูกลดเหลือปีเกิด
- **projection แบบเจาะจง** ทุก connector ระบุคอลัมน์ของตัวเองไว้ครบ ไม่มี `SELECT *` ที่ไหน การ projection *คือ* เส้นแบ่งความไว้วางใจ และคอมเมนต์ส่วนหัวของแต่ละ connector ก็ระบุไว้ตรง ๆ อย่างนั้น
- **ใช้บัญชีบริการแบบอ่านอย่างเดียว** ไม่ใช้บัญชีระดับ superuser

การส่งข้อมูลออกนอกราชอาณาจักรเป็นเรื่องที่ต้องดูเป็นพิเศษ: การเรียก AI ทุกครั้งส่งข้อมูลไปยัง Google หรือ Anthropic ซึ่งอยู่นอกประเทศไทย `docs/pdpa.md` หัวข้อ *Cross-border data transfer* บันทึกการวิเคราะห์ของ มข. ไว้ เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคลของสถาบันคุณอาจได้ข้อสรุปต่างออกไป และถ้ากำหนดว่าการอนุมานต้องเกิดขึ้นในประเทศ ชั้นนามธรรม `AiService` คือจุดที่จะสลับ provider ได้ — แต่ให้ทราบว่า provider อีกสองตัวใน factory ที่ไม่ใช่ Google/Anthropic เป็น stub ที่ throw ทั้งคู่ งานส่วนนี้จึงเป็นงานจริง

### เกตความพร้อม

`docs/readiness-checklist.md` กำหนดเกตไว้สิบสองข้อ ที่ผลลัพธ์ใด ๆ ต้องผ่านก่อนจะนำเสนอต่อสภามหาวิทยาลัยได้ การไม่ผ่านเกตจะบล็อกผลลัพธ์นั้นและขึ้นแบนเนอร์ในระบบ แทนที่จะปล่อยตัวเลขที่มีข้อแม้ออกไปเงียบ ๆ **เกตข้อ 11** คือข้อที่สถาบันผู้นำไปใช้มักข้ามมากที่สุด: connector ตัวจริงต้องมี **ประวัติการรันเขียวติดต่อกัน 30 วัน** ก่อนจะขับเคลื่อนตัวเลขที่เสนอสภามหาวิทยาลัยได้ ให้วางแผนเผื่อเวลานี้ไว้ อย่าไปค้นพบเอาสัปดาห์ก่อนการนำเสนอครั้งแรก

## 18. การต่อยอดแพลตฟอร์มด้วย Claude Code

codebase นี้สร้างขึ้นด้วย Claude Code และข้อเท็จจริงนั้นกำหนดวิธีที่ควรต่อยอดมัน ถ้าจะใช้ผู้ช่วย AI ที่นี่ การตั้งค่าด้านล่างคือสิ่งที่ทำให้ผลลัพธ์ของมันสอดคล้องกับโค้ดที่มีอยู่ แทนที่จะได้โค้ดที่ดูดีแต่ใช้งานจริงไม่ได้

### `CLAUDE.md` คือสัญญา

`CLAUDE.md` ที่รากของ repository ถูกอ่านตอนเริ่มทุก session ของ Claude Code นี่คือเหตุผลที่ AI ผลิตโค้ดที่สอดคล้องกันใน repository นี้ ไฟล์นี้เข้ารหัสคำถามเชิงกลยุทธ์ รายการโมดูล กลยุทธ์ด้านภาษา ธรรมเนียมการเขียนโค้ด กฎความพร้อมสำหรับสภามหาวิทยาลัย รูปแบบการ deploy และบันทึกการตัดสินใจยาว ๆ ที่อธิบายว่า *ทำไม* ทุกอย่างจึงเป็นแบบที่เป็น

**fork ไฟล์นี้แล้วเขียนส่วนที่เป็นเรื่องเฉพาะสถาบันใหม่ก่อน session แรก** โดยเฉพาะ:

| หัวข้อ | สิ่งที่ต้องทำ |
|---|---|
| คำอธิบายโครงการ กลุ่มเป้าหมาย | เขียนใหม่ให้เป็นของสถาบันคุณ |
| คำถามเชิงกลยุทธ์แปดข้อ | เขียนใหม่ — เป็นคำถามของสภามหาวิทยาลัยขอนแก่น และเป็นกรอบที่กำหนดทุกการตัดสินใจเชิงวิเคราะห์ที่ตามมา |
| แปดโมดูล | คงไว้ เว้นแต่จะตัดโมดูลใดออก |
| กลยุทธ์ด้านภาษา | ทบทวน — UI เป็นภาษาอังกฤษล้วน ผลวิเคราะห์เป็นภาษาอังกฤษล้วน โดยมีรายการยกเว้นภาษาไทยแคบ ๆ |
| ชื่อคณะ จำนวนหลักสูตร | แทนที่ |
| สถานะปัจจุบัน / บันทึกการตัดสินใจ | **ตัดให้เหลือแค่ตัวชี้ไปที่ประวัติของ มข. แล้วเริ่มบันทึกของตัวเอง** อย่าลากบันทึก session ของ มข. ขนาด 170 KB มาด้วย เพราะมันจะเบียดพื้นที่บริบทของคุณเอง |
| ธรรมเนียมการเขียนโค้ด รายการสิ่งที่ห้ามทำ | คงไว้ทุกตัวอักษร นี่คือส่วนที่ทำให้ผลลัพธ์ของ AI สอดคล้องกัน |
| คำสั่ง run/test/lint และหัวข้อแพลตฟอร์ม | อัปเดต path และชื่อโฮสต์ |

`prompts/CLAUDE.md.template` คือเทมเพลตดั้งเดิมที่ใช้สร้างไฟล์นี้ และเป็นจุดตั้งต้นที่สะอาดกว่าไฟล์ปัจจุบันขนาด 170 KB

ข้อสังเกตเรื่องบันทึกการตัดสินใจ: `CLAUDE.md` ของ มข. มีหมายเหตุที่ยอมรับเองว่าบันทึกกระโดดจาก v1.1.3 ไป v1.6.1 และงานช่วง v1.2–v1.6 ปล่อยออกไปแล้วแต่ไม่ได้บันทึกไว้ ให้ถือเป็นบันทึกแบบ best-effort และถือว่า `apps/web/app/changelog/page.tsx` คือประวัติการปล่อยเวอร์ชันที่เป็นทางการ

### `prompts/` คือคู่มือการสร้างฉบับดั้งเดิม

ไดเรกทอรี `prompts/` บรรจุ prompt ตามลำดับที่ใช้สร้างแพลตฟอร์มนี้ ตั้งแต่ prompt 00 (bootstrap) ถึง prompt 13b (การ deploy) บวก prompt 14 (การเชื่อมข้อมูลจริง) ที่ยังดำเนินอยู่ โอกาสที่จะได้รันซ้ำมีน้อย แต่นี่คือคำอธิบายที่ดีที่สุดเท่าที่มีว่า *ทำไม* แต่ละระบบย่อยจึงมีรูปร่างแบบนี้ อ่านตัวที่ตรงกับสิ่งที่กำลังจะแก้

`prompts/14-integration-session-template.md` คือเทมเพลต session รายตัว connector ที่ยังใช้งานอยู่ ให้ใช้กับทุก connector ที่เขียน ส่วน `prompts/GLOBAL-UPDATES.md` บรรจุข้อกำหนดที่ตัดข้ามทุกโมดูล และ `prompts/TROUBLESHOOTING.md` รวบรวมรูปแบบความล้มเหลวที่รู้จักแล้ว

### กฎประจำบ้านที่ทำให้ผลลัพธ์ของ AI สอดคล้องกัน

กฎเหล่านี้อยู่ใน `CLAUDE.md` และเป็นสิ่งที่ผู้ช่วย AI จะทำตามถ้าปล่อยไว้ และจะละเมิดเงียบ ๆ ถ้าลบทิ้ง:

- TypeScript strict **ห้าม `any`**
- ตรวจสอบด้วย Zod ที่ทุกเส้นแบ่ง I/O — request, response, ingestion, การสกัดด้วย AI
- ใช้ design token เท่านั้น ห้ามเขียนสี ฟอนต์ หรือระยะห่างตรง ๆ (ESLint บังคับ)
- `@AuditLog()` บนทุก mutation และ `@AiCall()` บนทุกการเรียก AI
- ใช้ server component เป็นค่าตั้งต้น ใช้ client component เฉพาะเมื่อต้องมีการโต้ตอบ
- ใช้ conventional commit (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`)
- รัน `pnpm check` ก่อน commit
- กำกับเวอร์ชันระเบียบวิธีบนทุกตัววัด
- ห้ามใช้ SQL ดิบ ยกเว้นผ่าน `$queryRaw` ของ Prisma พร้อมผลลัพธ์ที่ตรวจสอบด้วย Zod
- ใช้เครื่องมือที่ทำงานข้ามแพลตฟอร์มเท่านั้น — ไม่มี Makefile ไม่ใช้ `rm -rf` (ให้ใช้ `rimraf`) และไม่ต่อ path ด้วยสตริง (ให้ใช้ `path.join()`)

### ชุด prompt สำหรับเริ่มต้น

**หมายเหตุสำคัญเรื่องภาษาในส่วนนี้:** ข้อความ prompt ทั้งแปดชุดด้านล่าง **คงไว้เป็นภาษาอังกฤษโดยเจตนา** เพราะเป็นข้อความที่จะคัดลอกไปวางในเครื่องมือจริง และโมเดลทำงานได้ดีกว่ากับต้นฉบับ ส่วนคำอธิบายรอบ ๆ เป็นภาษาไทย ในแต่ละชุด:

- ย่อหน้าที่ขึ้นต้นด้วย **สิ่งที่ prompt นี้ทำ** คือคำอธิบายภาษาไทย อ่านเพื่อทำความเข้าใจ **อย่าคัดลอก**
- บล็อกอ้างอิงที่ขึ้นต้นด้วยเครื่องหมาย `>` คือ **ข้อความ prompt ภาษาอังกฤษที่ต้องคัดลอกไปวางทั้งบล็อก**
- ย่อหน้าที่ขึ้นต้นด้วย **เสร็จเมื่อ** คือคำแปลภาษาไทยของบรรทัด "Done when" ในบล็อกด้านบน มีไว้เพื่อความเข้าใจเท่านั้น

prompt เหล่านี้เขียนไว้ให้คัดลอกไปรันตามลำดับนี้ โดยแยกเป็นคนละ session ให้แทนที่ `<YOUR UNIVERSITY>` และรายละเอียดในวงเล็บเหลี่ยมด้วยข้อมูลของสถาบันคุณ

### จุดที่การใช้ AI ช่วยจะพลาดในโครงการนี้ — เรื่องนี้ต้องพูดให้เจาะจง

ผู้ช่วย AI เก่งจริงกับงานเชิงกลใน codebase นี้ ทั้งการเขียน connector โดยเทียบเคียงตัวที่มีอยู่ การกวาดเปลี่ยนชื่อข้ามร้อยไฟล์ การเขียน transform test จาก fixture และการร่างเอกสาร ใช้มันกับงานเหล่านั้น

แต่มัน **เชื่อถือไม่ได้ และมักผิดแบบมั่นใจเต็มร้อย กับสิ่งที่คู่มือนี้ระบุไว้ว่าเป็นกับดักพอดี**:

- **สเกลระยะห่าง** AI ที่ฝึกมากับ Tailwind จะเขียน `h-4 w-4` บนไอคอน และเขียน `pl-9` เป็น padding โดยไม่ลังเล ทั้งคู่ผิดในโครงการนี้ในแบบที่ไม่เกิด error ขึ้นมาเลย ได้แค่ผลลัพธ์ที่ขนาดผิด ข้อบกพร่องสองรายการใน repository นี้เกิดจากสาเหตุนี้ตรง ๆ ให้สั่งมันอ่าน `packages/design/src/tokens/spacing.ts` และ `icon.ts` ก่อนแตะ utility ใดที่เกี่ยวกับระยะห่างหรือขนาด
- **การประทับ provenance** `ingestionRunId: ctx.runId` บนทุกแถวที่ insert เป็นสิ่งที่ลืมง่ายมาก และผลของการลืมคือ UI ว่างเปล่าเงียบ ๆ ไม่ใช่ error ให้กำหนดเป็นเกณฑ์ยอมรับที่ระบุชัดในทุก prompt ที่เกี่ยวกับ connector
- **การตัดสินใจเรื่อง schema** ฟิลด์ใหม่ควรเป็นคอลัมน์ เป็นก้อน JSONB หรือเป็นตารางใหม่ migration นี้เป็นแบบเพิ่มเข้าไปหรือทำลายข้อมูล unique constraint ทำงานอย่างไรกับความหมายของ NULL ใน Postgres — เรื่องเหล่านี้ต้องให้มนุษย์ตัดสิน codebase มีคำตอบที่ได้มาด้วยราคาแพงอยู่แล้ว (เช่น การ upsert ด้วย `findFirst → update | create` เขียนมือ ในกรณีที่ compound unique key มี NULL อยู่ด้วย) ซึ่ง AI จะคิดขึ้นมาเองไม่ได้
- **น้ำหนักในระเบียบวิธี** สิ่งเหล่านี้เข้ารหัสการตัดสินคุณค่าเชิงสถาบัน ว่าหลักสูตรใดสำคัญและเพราะอะไร AI จะผลิตน้ำหนักที่ฟังดูสมเหตุสมผลออกมาได้ทันที และ "ฟังดูสมเหตุสมผล" คือสิ่งที่ผิดที่สุดสำหรับตัวเลขที่จะใช้ปิดหลักสูตร
- **แนวปฏิบัติด้าน PDPA** AI จะเขียน `SELECT *` ให้อย่างเต็มใจ ทุก projection คือเส้นแบ่งความไว้วางใจที่ต้องมีลายมือชื่อของมนุษย์ และของเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล ไม่ใช่ของโมเดล
- **การ "แก้" สิ่งที่จงใจไม่ใส่ไว้** ทั้งคีย์ระยะห่าง `3.5` ที่หายไป กฎค่าว่างไม่ใช่ศูนย์ และรายการในแคตตาล็อกที่เลิกใช้แล้วแต่ยังเก็บไว้ — ทุกอย่างดูเหมือนบั๊กแต่ไม่ใช่ คอมเมนต์ในโค้ดอธิบายเหตุผลไว้แล้ว ทำให้แน่ใจว่า AI ได้อ่าน

กฎที่ใช้ได้จริงคือ ปล่อยให้ AI เขียน แล้วอ่านสิ่งที่มันเขียนในหกหมวดข้างต้นด้วยตาตัวเองทุกครั้ง

- **รายการเกณฑ์ AUN-QA ยังไม่ได้ตรวจสอบ** `packages/shared/src/aunqa/criteria.ts` มีคำเตือนเรื่องที่มาระบุไว้ในส่วนหัวของตัวเอง: เกณฑ์ชุดนี้เขียนขึ้นจากความรู้ของผู้ช่วย AI เกี่ยวกับ AUN-QA v4 **ไม่มีคู่มือ AUN-QA อยู่ใน repository** และยังไม่มีการตรวจสอบเทียบกับเอกสารที่เผยแพร่จริงเลย เกณฑ์สองข้อ (Student Support Services และ Facilities & Infrastructure) ไม่มีข้อมูลรองรับในแพลตฟอร์มเลย จึงแยกรายการไว้ต่างหากเพื่อไม่ให้ผู้อ่านเข้าใจผิดว่าหกเกณฑ์คือทั้งกรอบ ยิ่งกว่านั้น จากหลักสูตรของ มข. สามหลักสูตรที่สุ่มดู กรอบประกันคุณภาพที่แต่ละหลักสูตรประกาศไว้คือ WFME หรือ TQF — **ไม่มีหลักสูตรใดระบุ AUN-QA** การจัดเรียงหลักฐานตามแนว AUN-QA จึงเป็นชั้นการวิเคราะห์ที่แพลตฟอร์มวางทับลงไปเอง ไม่ใช่สิ่งที่เอกสารต้นทางกล่าวอ้าง **ต้องตรวจสอบเทียบกับคู่มือฉบับทางการก่อนนำไปใช้กับการขอรับรองคุณภาพใด ๆ**
- **การจัดสรรต้นทุนยังเป็น v0** และไม่มีตัวเลขต้นทุนรายหลักสูตรตัวใดที่เสนอต่อสภามหาวิทยาลัยได้ ดู [บทที่ 12](#12-ระเบียบวิธี--การปรับการให้คะแนนให้เข้ากับสถาบันของคุณ)
- **`kku-alumni` ยังไม่มี connector ตัวจริง** ผลลัพธ์บัณฑิตและอุปทานระดับจังหวัดจึงยังไม่ได้ต่อที่ มข. เช่นกัน การวิเคราะห์ช่องว่างเชิงภูมิภาคจึงแสดงหมายเหตุชัดเจนว่าฝั่งอุปทานยังรอข้อมูล
- **แผนที่ประเทศไทยเป็นแบบแผนผัง ไม่ใช่ choropleth จริง** — เป็นบล็อกหกภูมิภาคที่ไล่ความเข้มสี เพราะยังไม่มีข้อมูลบัณฑิตระดับจังหวัด
- **CI ตัว `Release bundle` แดงอยู่** เพราะหนี้ lint ทั้ง repo ที่ค้างมาก่อน
- **มีรายการในแคตตาล็อกที่เลิกใช้แล้วห้ารายการ** (`kku-tcas-funnel`, `jobthai`, `jobsdb`, `scopus`, `openalex`) เก็บไว้เพียงเพื่อไม่ให้แถว `IngestionRun` ในอดีตกลายเป็นแถวกำพร้า อย่าไปต่อมันเข้ากับอะไร
- **Storybook ตั้งค่าไว้แล้วแต่ยังไม่มี story** หน้า `/styleguide` ในแอปเว็บทำหน้าที่เป็นสัญญาเชิงภาพแทน
- **กล่องโต้ตอบขอเหตุผลการส่งออกข้อมูลรายเทมเพลต** — decorator `@RequireExportReason` และ `DataExportGuard` วางโครงไว้แล้ว แต่ยังไม่มี route ที่ใช้งานจริง (เกตข้อ 8 ของรายการตรวจสอบความพร้อมผ่านในระดับโครงสร้างพื้นฐาน แต่ยังไม่ผ่านในระดับหน้าจอ)

## 20. ลำดับงานที่แนะนำ พร้อมประมาณการภาระงาน

ประมาณการนี้ตั้งอยู่บนสมมติฐานว่ามีนักพัฒนา full-stack ที่มีฝีมือหนึ่งถึงสองคน ซึ่งยังไม่เคยเห็น codebase นี้ และรวมเวลารอสิทธิ์เข้าถึงระบบของสถาบันไว้แล้ว ซึ่งตามปกติคือเส้นทางวิกฤต

| ระยะ | งาน | ประมาณการ |
|---|---|---|
| 0 | **ขอคำยืนยันเป็นลายลักษณ์อักษรจาก มข. ว่าการใช้งานที่ตั้งใจไว้อยู่ในเงื่อนไข NonCommercial ของ CC BY-NC-SA** เป็นงานที่บล็อกทุกอย่างถ้าการใช้งานเข้าใกล้เชิงพาณิชย์ | หลายวันถึงหลายสัปดาห์ และไม่ได้อยู่ในการควบคุมของคุณ |
| 1 | ตั้ง instance บนเครื่องให้รันได้ ตั้ง fork พร้อม upstream อ่าน `CLAUDE.md`, `architecture.md`, `evaluation-pipeline.md` | 3–5 วัน |
| 2 | ปรับแบรนด์ fork `CLAUDE.md` seed คณะและภาควิชา | 1 สัปดาห์ |
| 3 | seed รายการหลักสูตรพร้อมรหัส อว. | 1–2 สัปดาห์ (ส่วนใหญ่คือการรวบรวมข้อมูล ไม่ใช่โค้ด) |
| 4 | เริ่มขอสิทธิ์เข้าถึงระบบของสถาบัน **ทุกระบบพร้อมกัน** — สำนักทะเบียน บุคคล การเงิน UniCon การประเมิน | เริ่มตั้งแต่วันแรก คาดว่าใช้เวลา 4–12 สัปดาห์ |
| 5 | connector UniCon ตัวแรก (DS2001 หรือ DS2004) | 1–3 วันหลังได้สิทธิ์แล้ว |
| 6 | connector UniCon อีกสามตัวที่เหลือ | 1 สัปดาห์ |
| 7 | แหล่งข้อมูลภายนอก Tier 2 — สจล. TCAS ธนาคารโลก ฟีดรายงานนโยบาย | 1–2 สัปดาห์ ขึ้นกับข้อมูลรับรอง |
| 8 | จัดหา PDF หลักสูตร และรัน pipeline การสรุป | 2–4 สัปดาห์ โดยการจัดหาเอกสารกินเวลาส่วนใหญ่ |
| 9 | เขียน Tier 3 ตัวแรกใหม่ (สำนักทะเบียน ส่งผลมากที่สุด) | 2–4 สัปดาห์ |
| 10 | connector Tier 3 ที่เหลือ ตามลำดับความสำคัญ | ตัวละ 2–4 สัปดาห์ |
| 11 | ปรับระเบียบวิธีร่วมกับสภามหาวิทยาลัยหรือองค์กรเทียบเท่า | 2–4 สัปดาห์ ส่วนใหญ่เป็นเรื่องเชิงสถาบัน ไม่ใช่เชิงเทคนิค |
| 12 | เชื่อม SSO deploy ขึ้น production และประสานทีมเครือข่าย | 2–3 สัปดาห์ |
| 13 | การทบทวนและให้ความเห็นชอบโดยเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล | ทำคู่ขนานไปกับทุกอย่าง เริ่มแต่เนิ่น ๆ |
| 14 | ช่วงรอประวัติการรันเขียว 30 วันต่อ connector ก่อนใช้กับสภามหาวิทยาลัย | 30 วัน เลี่ยงไม่ได้ วางแผนเผื่อไว้ |

**หมุดหมายที่สมจริงสำหรับผลลัพธ์ที่ใช้งานได้ครั้งแรกคือสี่ถึงหกเดือน** โดยเวลาส่วนใหญ่หมดไปกับการเข้าถึงข้อมูลและการจัดหาเอกสาร ไม่ใช่งานวิศวกรรม งานวิศวกรรมส่วนใหญ่ทำเสร็จไปแล้ว สิ่งที่ codebase นี้ช่วยประหยัดให้คือเวลาในส่วนของงานวิศวกรรม ไม่ใช่เวลาในส่วนของการขอสิทธิ์เข้าถึงข้อมูลและการจัดหาเอกสาร

**คำแนะนำเรื่องลำดับงานที่สำคัญกว่าตัวเลขประมาณการ:** เริ่มยื่นขอสิทธิ์เข้าถึงทุกระบบตั้งแต่สัปดาห์แรก ก่อนเขียนโค้ดบรรทัดใด connector หนึ่งตัวคืองานหนึ่งถึงสามวัน บวกการรอบัญชีบริการอีกแปดสัปดาห์ ให้จัดคิวงานตามข้อเท็จจริงข้อนี้
