## 1. อ่านส่วนนี้ก่อน

**ข้อเท็จจริงที่มีประโยชน์ที่สุดข้อเดียวสำหรับมหาวิทยาลัยไทยที่จะนำแพลตฟอร์มนี้ไปใช้:** connector สี่ตัวอ่านข้อมูลจาก **ชุดข้อมูลมาตรฐานระดับชาติ MHESI UniCon** ซึ่งเป็นชุดข้อมูลชุดเดียวกับที่สถาบันของท่านส่งให้กระทรวงอยู่แล้ว และใช้ schema เดียวกัน connector ทั้งสี่ตัวนี้แทบจะใช้ได้ทันที เปลี่ยนเพียง host และชื่อฐานข้อมูล อย่าไปเปลี่ยนโครงสร้างตาราง

| Connector | ชุดข้อมูล | ข้อมูลที่บรรจุอยู่ |
|---|---|---|
| `unicon-ds1001` | DS1001 | ข้อมูลนักศึกษา หนึ่งแถวต่อ (นักศึกษา × ปีการศึกษา × ภาคการศึกษา) |
| `unicon-ds2001` | DS2001 | ทะเบียนหลักบุคลากร — ตำแหน่งทางวิชาการ สัญญาจ้าง แหล่งงบประมาณ สถานะการปฏิบัติงาน |
| `unicon-ds2003` | DS2003 | คุณวุฒิการศึกษาของบุคลากรทุกคน |
| `unicon-ds2004` | DS2004 | อาจารย์ประจำหลักสูตร (การเป็นกรรมการบริหารหลักสูตร) |

ตรวจสอบได้จากคอมเมนต์ส่วนหัวของ `apps/ingestion/src/connectors/sources/unicon-ds2001/connector.ts` — ทั้ง URL ของแหล่งข้อมูล การ projection คอลัมน์ที่แน่นอน และแนวปฏิบัติด้าน PDPA ล้วนบันทึกไว้ในไฟล์นั้น

ส่วนที่เป็นเรื่องเฉพาะของแต่ละสถาบัน — คลังข้อมูลสำนักทะเบียน ระบบทรัพยากรบุคคล ระบบการเงิน การประเมินการสอน คะแนนสมรรถนะดิจิทัล — ล้วนสร้างขึ้นเฉพาะสำหรับระบบของ มข. และต้องเขียนใหม่ให้ตรงกับระบบเทียบเท่าของท่าน [บทที่ 8](#8-การเชื่อมต่อข้อมูล--สี่ระดับของภาระงานในการนำไปใช้) จัดแหล่งข้อมูลทั้ง 39 รายการในแค็ตตาล็อกออกเป็นระดับตามปริมาณงานที่ต้องลง

**สามเรื่องที่ต้องเข้าใจให้ขึ้นใจก่อนเริ่ม:**

- ระบบนี้เป็น **ระบบสนับสนุนการตัดสินใจสำหรับการตัดสินใจที่มีเดิมพันสูง** — การปิดหลักสูตร การควบรวม และชีวิตความเป็นอยู่ของอาจารย์ codebase นี้สร้างขึ้นรอบแนวคิดเรื่อง provenance (การสืบค้นที่มาของข้อมูล) การบันทึก audit log การกำกับเวอร์ชันระเบียบวิธี และการเปิดเผยระดับความเชื่อมั่น สิ่งเหล่านี้ไม่ใช่ของประดับ หากท่านถอดมันออก สิ่งที่เหลือคือ dashboard ที่ไม่มีใครในสภามหาวิทยาลัยของท่านจะเชื่อถือ
- **ไม่มีทางลัดให้ใช้ข้อมูลปลอม — นี่เป็นนโยบาย** กติกาของโครงการคือแหล่งข้อมูลที่ยังติดขัดจะต้อง *ว่างเปล่า* ไม่ใช่กรอกข้อมูลปลอม ส่วนที่ว่างจะแสดงสถานะชัดเจนว่า "ไม่มีข้อมูล — ให้รัน connector ตัวนี้" จงต้านความรู้สึกอยากใส่ตัวเลขที่ดูสมเหตุสมผลลงไป เพราะห่วงโซ่ provenance ทั้งเส้น (ดู [`realDataWhere()`](#กับดักที่-2-realdatawhere--ส่วนที่ว่างเปล่าทั้งที่ฐานข้อมูลมีข้อมูลอยู่)) ออกแบบมาเพื่อจับพฤติกรรมแบบนี้โดยเฉพาะ
- **โค้ดนี้เผยแพร่ภายใต้ CC BY-NC-SA 4.0 ซึ่งมีภาระผูกพันจริง** — การแสดงที่มา การอนุญาตแบบเดียวกัน และการใช้เพื่อวัตถุประสงค์ที่มิใช่การค้า — และ *ไม่ได้* อนุญาตให้ใช้เครื่องหมายการค้าของ มข. ไม่ครอบคลุมชุด dependency และไม่ครอบคลุมข้อมูลใด ๆ ของ มข. ให้อ่านบทถัดไปก่อนที่ท่านจะนำโค้ดนี้ไปทำอะไรที่เป็นสาธารณะ

**สิ่งที่หมายความสำหรับท่าน แยกเป็นภาระผูกพันสี่ข้อ:**

- **แสดงที่มา** ท่านต้องให้เครดิต มข. ระบุชื่อสัญญาอนุญาต และใส่ลิงก์ไปยังสัญญาอนุญาต ทั้งใน repository ของท่าน ในเอกสารประกอบ และในหน้าจอ "เกี่ยวกับ" หรือหน้าจอแสดงเครดิตที่ผู้ใช้มองเห็นได้ ส่วนหัวของ `LICENSE` ให้ข้อความที่ต้องคัดลอกไว้ตรง ๆ แล้ว — ให้ใช้ข้อความนั้น อย่าคิดถ้อยคำขึ้นเอง
- **อนุญาตแบบเดียวกัน (ShareAlike)** หากท่านดัดแปลงงานนี้ ฉบับดัดแปลงของท่านต้องเผยแพร่ภายใต้ CC BY-NC-SA 4.0 เช่นกัน และท่านต้องระบุว่าท่านเปลี่ยนแปลงอะไรไปบ้าง
- **ไม่ใช้เพื่อการค้า (NonCommercial)** ท่านจะใช้งานนี้โดยมุ่งประสงค์เป็นสำคัญต่อประโยชน์ทางการค้าหรือค่าตอบแทนอันเป็นตัวเงินมิได้ ความหมายของข้อนี้ในบริบทของมหาวิทยาลัยยังคลุมเครืออยู่จริง — ดูรายละเอียดด้านล่าง
- **คงข้อความแจ้งต่าง ๆ ไว้ครบถ้วน** ให้คงข้อความแสดงลิขสิทธิ์ ข้อความแสดงที่มา และข้อความแจ้งสัญญาอนุญาต ไว้ในทุกสิ่งที่ท่านเผยแพร่ต่อ

**สามสิ่งที่สัญญาอนุญาตนี้ไม่ได้ให้ท่าน ซึ่งแต่ละข้อจะทำให้สมาชิกในทีมของท่านพลาดได้:**

- **เครื่องหมายของ มข. ไม่ได้อยู่ภายใต้สัญญาอนุญาต** "Khon Kaen University", "มหาวิทยาลัยขอนแก่น", "KKU", ตราสัญลักษณ์ประจำมหาวิทยาลัย และแฟ้มโลโก้ใน `apps/web/public/brand/` สงวนไว้โดยชัดแจ้ง สัญญาอนุญาตทางลิขสิทธิ์ไม่ได้ให้สิทธิในเครื่องหมายการค้า และข้อ 2(b)(2) ของสัญญาอนุญาตครีเอทีฟคอมมอนส์ระบุเรื่องนี้ไว้โดยชัดแจ้ง ท่านต้องนำเครื่องหมายเหล่านี้ออกหรือเปลี่ยนเป็นของท่านเองในระบบที่ท่านติดตั้ง — [บทที่ 11](#11-การปรับแบรนด์และ-ui) คือรายการตรวจสอบ และมีไฟล์ประมาณ 101 ไฟล์ภายใต้ `apps/web` ที่กล่าวถึงชื่อ มข.

## 4. การขอสิทธิ์เข้าถึง การ fork และการรับ fix จาก upstream ในอนาคต

### การขอสิทธิ์เข้าถึง

repository ที่เป็นต้นฉบับคือ `https://github.com/khon-kaen-university/program-landscape` การให้สิทธิ์เข้าถึงเป็นอำนาจของสำนักงานรองอธิการบดีฝ่ายการศึกษาและดิจิทัล มข. ท่านจะได้รับเพียง repository เท่านั้น ไม่มีข้อมูลรับรองการเข้าถึงระบบ ไม่มีข้อมูล และไม่มีฟอนต์ (ดู [บทที่ 19](#19-สิ่งที่ท่านจะไม่ได้รับ))

### ให้ fork อย่าแยกทาง

ให้นำไปใช้ในรูปแบบ **git fork ที่ตั้งค่า `upstream` ไว้** ไม่ใช่การคัดลอกครั้งเดียวจบ ท่านจะต้องการ bug fix ของ มข. เพราะ codebase นี้ยังอยู่ระหว่างการพัฒนาอย่างต่อเนื่อง และหลายระบบย่อย (มาตรฐาน prompt, ระเบียบวิธีคะแนนสุขภาพหลักสูตร, ห่วงโซ่ provenance ของคุณภาพข้อมูล) เปลี่ยนแปลงไปมากในไม่กี่เดือนที่ผ่านมา

```bash
git clone git@github.com:<your-university>/program-landscape.git
cd program-landscape
git remote add upstream https://github.com/khon-kaen-university/program-landscape.git
git fetch upstream
```

### จัดโครงสร้างการแก้ไขของท่านเพื่อให้ merge ได้ถูก

ปัจจัยเดียวที่กำหนดมากที่สุดว่าอีกหนึ่งปีข้างหน้าท่านจะยัง merge จาก upstream ได้หรือไม่ คือ **ท่านวางโค้ดเฉพาะสถาบันของท่านไว้ตรงไหน** ข้อแนะนำ เรียงจากผลตอบแทนสูงไปต่ำ:

| ประเภทการแก้ไข | ให้ทำแบบนี้ | อย่าทำแบบนี้ |
|---|---|---|
| connector ของท่าน | สร้างไดเรกทอรีใหม่ใต้ `apps/ingestion/src/connectors/sources/<your-slug>/` แล้วเพิ่มเป็นรายการใหม่ใน `SOURCE_CATALOG` และแถวใหม่ใน registry | แก้ไฟล์ connector ของ มข. ทับลงไป |
| ข้อมูลคณะ/ภาควิชา/หลักสูตรของท่าน | สร้างโมดูล seed ของท่านเอง แล้ว import จาก `packages/db/prisma/seed.ts` | แก้อาร์เรย์คณะของ มข. แบบ inline |
| แบรนด์ | เปลี่ยนไฟล์สินทรัพย์และ *ค่า* ของ token แต่คง *ชื่อ* token ไว้ | เปลี่ยนชื่อ token หรือรื้อโครงสร้าง `tailwind-preset.ts` |
| น้ำหนักในระเบียบวิธี | เพิ่มค่าคงที่เวอร์ชันใหม่และเพิ่มตัวแปรของท่านคู่ขนานไป ดู [บทที่ 12](#12-ระเบียบวิธี--การปรับการให้คะแนนให้เข้ากับสถาบันของท่าน) | แก้สูตรของ มข. ทับลงไป |
| `CLAUDE.md` ของท่าน | เขียนใหม่ได้ตามใจ — ไฟล์นี้ *ตั้งใจ* ให้แยกทางกัน | — |

ไฟล์ที่ท่านควรคาดหมายว่าจะเกิด conflict ทุกครั้งที่ merge จึงควรรวมการแก้ไขของท่านให้อยู่ในจำนวน hunk น้อยที่สุด:

- `packages/shared/src/ingestion/catalog.ts` (ให้ต่อรายการของท่านไว้ท้ายอาร์เรย์)
- `apps/ingestion/src/connectors/registry.ts` (เช่นเดียวกัน)
- `packages/db/prisma/seed.ts`
- `packages/design/src/tokens/*.ts`
- `.env.example`

### migration จะชนกัน และนี่คือจุดที่คมที่สุด

Prisma migrations เป็นไดเรกทอรีที่ตั้งชื่อด้วย timestamp ใต้ `packages/db/prisma/migrations/` หากท่านเพิ่ม migration และ มข. ก็เพิ่ม migration ทั้งสองตัวจะถูก apply — แต่หากทั้งสองฝ่ายแก้ *ตารางเดียวกัน* ท่านจะต้องประสานความต่างด้วยมือ มีสองวิธีบรรเทา:

- ตั้งชื่อ migration ของท่านให้มีคำนำหน้าที่แยกแยะได้ชัด (`20260901120000_yourthuni_registrar_bridge`) เพื่อให้ประวัติอ่านรู้เรื่อง
- ให้เลือกการเปลี่ยน schema แบบ **เพิ่มเข้าไป** (คอลัมน์ใหม่ที่เป็น nullable ตารางใหม่) แทนการไปแก้ของ มข. repository นี้ใช้นโยบายนี้กับตัวเองอยู่แล้ว ดู `docs/migration-policy.md` และสังเกต `scripts/migration-linter.ts` ซึ่ง CI รันเพื่อตรวจจับ DDL ที่เป็นการทำลายข้อมูล

### จังหวะการ merge ที่ใช้ได้จริง

ให้ merge จาก upstream **ทุกไตรมาส ไม่ใช่ตลอดเวลา** การ merge ต่อเนื่องหมายถึงการมานั่งตัดสิน conflict เดิม ๆ ทุกสัปดาห์ ส่วนการทำทุกไตรมาสหมายถึงท่านได้อ่านการเปลี่ยนแปลงใน `docs/` ที่เกิดขึ้นระหว่างนั้น และอ่านหน้า `/changelog` (`apps/web/app/changelog/page.tsx` คือประวัติการปล่อยเวอร์ชันฉบับที่เป็นทางการ — ส่วนบันทึกใน CLAUDE.md ระบุไว้ชัดเจนว่าเป็นการบันทึกเท่าที่ทำได้และมีช่องโหว่ที่ทราบอยู่) แล้วจึงลงมือรอบเดียวอย่างตั้งใจ

## 5. รันครั้งแรก — จาก clone จนได้ instance ที่ทำงานได้

**เป้าหมาย:** แอปรันอยู่ที่ `http://localhost:3000` พร้อมฐานข้อมูลที่ว่างเปล่าแต่ถูกต้อง บนเครื่องของท่านเอง ครั้งแรกให้เผื่อเวลาไว้ครึ่งวัน

### สิ่งที่ต้องมีก่อน

- Node 20+ (`.nvmrc` ตรึงเวอร์ชันไว้), pnpm 9+ (repository ประกาศ `pnpm@10.33.1` ไว้เป็น packageManager)
- Docker + Docker Compose v2
- Linux, macOS หรือ Windows ที่มี WSL2 (Ubuntu) เครื่องพัฒนาหลักของ มข. คือ Windows/WSL2 โดย `prompts/WINDOWS-DEV.md` อธิบายการตั้งค่านั้นไว้ โครงการนี้ **ไม่มี Makefile** โดยเจตนา — ทุกอย่างเป็น pnpm script

### ลำดับขั้นตอน

```bash
# 1. Environment file. Start from the example and fill in what you have.
cp .env.example .env

# 2. Full setup — installs deps, links .env into each app, starts
#    postgres/redis/minio/gotenberg, runs migrations, seeds.
pnpm setup

# 3. Run all three services in parallel.
pnpm dev
```

`pnpm setup` ขยายเป็น `pnpm install && node scripts/link-env.mjs && pnpm db:up && pnpm minio:init && pnpm db:migrate && pnpm db:seed` หากขั้นตอนใดล้มเหลว ให้รันทีละขั้นเพื่อระบุจุดที่มีปัญหา

เมื่อรันได้แล้ว:

| URL | คืออะไร |
|---|---|
| `http://localhost:3000` | Web (Next.js) |
| `http://localhost:4000/healthz` | ตรวจว่า API ยังมีชีวิตอยู่ |
| `http://localhost:4000/api/v1/ready` | ตรวจสุขภาพของ dependency ของ API — ตรวจ Postgres, Redis, MinIO, Gotenberg และผู้ให้บริการ AI |
| `http://localhost:9001` | คอนโซล MinIO |
| `http://localhost:3001` | Gotenberg |

### การล็อกอินในวันแรก

ตั้งค่า `ENABLE_LOCAL_AUTH=true` และ `DEV_AUTH_PASSWORD=<something>` ใน `.env` การตั้งค่านี้จะเปิด credentials provider ให้ท่านล็อกอินได้โดยไม่ต้องมีผู้ให้บริการอัตลักษณ์ OIDC และมีการป้องกันไว้ — `assertLocalAuthSafe()` จะ throw ตั้งแต่ตอนโหลดโมดูลหาก `ENABLE_LOCAL_AUTH=true` ในขณะที่ `NODE_ENV=production` ท่านจึงเผลอส่งขึ้น production ไม่ได้

การเชื่อมต่อ SSO ของมหาวิทยาลัยท่านเป็นงานแยกต่างหาก โดย `docs/auth/kku-sso.md` บันทึกการตั้งค่า OIDC ของ มข. ไว้เป็นตัวอย่างของรูปแบบที่ท่านต้องทำ

### "ทำงานได้" ในขั้นนี้หน้าตาเป็นอย่างไร

หน้าจอเชิงวิเคราะห์ส่วนใหญ่จะ **ว่างเปล่า** และนั่นถูกต้องแล้ว ตัว seed ให้ข้อมูลคณะ อนุกรมวิธานทักษะ กลุ่มอุตสาหกรรม และข้อมูลอ้างอิงมาให้ แต่ไม่ได้ให้ข้อมูลนักศึกษา บุคลากร การเงิน หรือเอกสารหลักสูตร เพราะข้อมูลเหล่านั้นเป็นของท่านและยังไม่มีอยู่ ส่วนที่ว่างจะแสดงสถานะว่างพร้อมระบุชื่อ connector ที่ท่านต้องรัน หากท่านเห็นตัวเลขที่ดูเหมือนถูกกุขึ้น แสดงว่ามีอะไรผิดปกติ

### กฎการวางตัวสองข้อที่ช่วยประหยัดเวลา

**`packages/db/src/` คือหัวใจเชิงวิเคราะห์ ไม่ใช่ `apps/api/`** ชั้น API นั้นบาง การให้คะแนนสุขภาพ การให้คะแนนความเสี่ยง การวิเคราะห์ช่องว่าง การเทียบเคียงคู่เทียบ query ของหน้า deep-dive และตัวกรอง provenance ด้านคุณภาพข้อมูล ทั้งหมดอยู่ใน `packages/db/src/*.ts` ในรูปฟังก์ชันที่ export ออกมาพร้อมประเภทที่ระบุไว้อย่างชัดเจน เมื่อท่านอยากรู้ว่า "ตัวเลขนี้คำนวณมาอย่างไร" ให้เริ่มที่นั่น ไม่ใช่ที่ controller

**`packages/shared/` ต้องไม่ import `packages/db/` เด็ดขาด** ทิศทางของ dependency เป็นทางเดียว (`db` ขึ้นกับ `shared`) หากท่านต้องการ implementation ที่ใช้ Prisma สำหรับ interface ที่นิยามไว้ใน `shared` ให้วางคลาสจริงไว้ใน `db` แล้ว inject เข้าไป — `packages/db/src/ai-inference-recorder.ts` คือตัวอย่างต้นแบบของรูปแบบนี้

### กฎความพร้อมสำหรับสภามหาวิทยาลัย

มีกฎหกข้อที่ใช้กับทุกโมดูล ทุก endpoint และทุกหน้าจอ กฎเหล่านี้ระบุไว้ใน `CLAUDE.md` และถูกตรวจสอบด้วยเกตสิบสองข้อใน `docs/readiness-checklist.md`:

1. `<ProvenanceButton>` บนทุกแผนภูมิ — เปิดลิ้นชักแสดงแหล่งข้อมูล ความสดของข้อมูล วิธีคำนวณ เวอร์ชันระเบียบวิธี และข้อควรระวัง
2. `<ConfidenceBadge>` พร้อมแหล่งข้อมูลที่คลิกได้ และช่องทางกด "ไม่เห็นด้วย" บนทุกผลลัพธ์จาก AI
3. `<FreshnessBadge>` บนทุกจุดข้อมูล
4. `@AuditLog()` บนทุกการเปลี่ยนแปลงข้อมูล (`apps/api/src/common/decorators.ts`)
5. `@AiCall()` บนทุกการเรียกใช้ AI (ไฟล์เดียวกัน)
6. ทุกตัววัดต้องมี `methodologyVersion` กำกับ และเอกสารระเบียบวิธีต้องกำกับเวอร์ชันไว้ใน git ใต้ `docs/methodologies/`

## 7. การตั้งค่าและ environment

`.env.example` มีคีย์ที่ไม่ได้ comment ไว้ **104 คีย์** (บวกกับคีย์ทางเลือกที่ comment ไว้อีกราว 20 คีย์) ส่วน `.env.prod.example` มีมากกว่านั้น พร้อมคำแนะนำเฉพาะสำหรับ production ในคอมเมนต์ ให้อ่านทั้งสองไฟล์ ทั้งสองไฟล์ไม่ใช่รายการที่ท่านต้องกรอกให้ครบ — คีย์ส่วนใหญ่เป็นข้อมูลรับรองรายตัวของ connector ซึ่งท่านจะยังไม่ต้องใช้จนกว่าจะเชื่อมต่อ connector ตัวนั้น

### คีย์ environment ที่สำคัญจริงในวันแรก

| คีย์ | หมายเหตุ |
|---|---|
| `DATABASE_URL` | ต้องสอดคล้องกับ `POSTGRES_*` เพราะระบบไม่ได้ประกอบค่าให้อัตโนมัติ |
| `NEXTAUTH_SECRET` | จำเป็นต้องมี หากไม่มี → auth จะล้มเหลวแบบเงียบ ดูกับดักที่ 4 |
| `NEXTAUTH_URL`, `AUTH_TRUST_HOST` | ตั้งเป็น URL สาธารณะของท่านใน production |
| `ENABLE_LOCAL_AUTH`, `DEV_AUTH_PASSWORD` | การล็อกอินสำหรับ dev จะ fail ทันทีใน production |
| `AI_PROVIDER` | `google` (ค่าตั้งต้น) / `anthropic` / `stub` การใช้ tool-use (AI Analyst) ต้องใช้ `anthropic` |
| `GOOGLE_AI_API_KEY` / `ANTHROPIC_API_KEY` | ต้องมีอย่างน้อยหนึ่งอย่าง ส่วน provider `stub` ทำงานได้โดยไม่ต้องมีทั้งคู่ |
| `CONNECTOR_MODE` | โหมดตั้งต้นของ connector ทั้งระบบ ช่วงแรกให้คงไว้ที่ `mocked` |
| `MINIO_*`, `REDIS_*`, `GOTENBERG_URL` | ค่าตั้งต้นสำหรับเครื่องท้องถิ่นใน `.env.example` ใช้งานได้กับ `pnpm db:up` |

**ช่องโหว่ที่ทราบแล้วใน `.env.example` ซึ่งท่านจะเจอแน่** `AI_PROVIDER`, `GOOGLE_AI_API_KEY`, `UNICON_DS2001_DB_*` และ `UNICON_DS1001_DB_*` มีบันทึกไว้ใน `.env.prod.example` แต่ **ไม่มีใน `.env.example`** ไฟล์ตัวอย่างฝั่ง dev ตามหลังฝั่ง prod อยู่ เมื่อ connector รายงานว่าไม่พบค่าตั้งค่า ให้ตรวจ `.env.prod.example` และ `configFromEnv('<PREFIX>')` ในตัว connector ก่อนที่จะสรุปว่าคีย์นั้นไม่มีอยู่

### แต่ละแอปต้องมี `.env` ของตัวเอง — ข้อนี้ไม่ใช่ทางเลือก

`@next/env` ของ Next.js โหลด `.env` จาก **ไดเรกทอรีของโปรเจกต์ Next** (`apps/web/`) เท่านั้น ไม่เคยโหลดจากรากของ monorepo กับดักเดียวกันนี้เกิดกับ `apps/api` และ `apps/ingestion` ด้วย

`scripts/link-env.mjs` (`pnpm link-env` ซึ่งเป็นส่วนหนึ่งของ `pnpm setup` ด้วย) สร้าง symlink ของ `.env` ที่รากไปยังไดเรกทอรีของแอปทั้งสาม บน Windows ที่ไม่ได้เปิด Developer Mode สคริปต์จะถอยไปใช้การคัดลอกแทน และไฟล์ที่คัดลอกไว้จะ **ไม่ตรงกัน** เมื่อท่านแก้ `.env` ที่ราก ดังนั้นบน Windows ให้รัน `pnpm link-env` ใหม่ทุกครั้งหลังแก้ค่า environment

รูปแบบความล้มเหลวเมื่อขาดสิ่งนี้จะเงียบและชวนให้เข้าใจผิด ดู [กับดักที่ 4](#กับดักที่-4-ไฟล์-env-ประจำแต่ละแอป-และความล้มเหลวเงียบของ-edge-middleware)

### ความลับใน production

Production ใช้ Docker Compose secrets แบบอิงไฟล์ใต้ `/opt/program-landscape/secrets/` (หนึ่งค่าต่อหนึ่งไฟล์ สิทธิ์ 0600) สำหรับข้อมูลรับรองของ Postgres และ MinIO ควบคู่กับไฟล์ `.env.prod` ที่ root เป็นเจ้าของและมีสิทธิ์ 0600 โดย `DEPLOYMENT.md` § *One-time server setup* คือเอกสารที่ใช้อ้างอิง ให้สังเกตข้อควรระวังที่บันทึกไว้ว่า `DATABASE_URL` ใน `.env.prod` ยังฝังรหัสผ่านไว้ในตัว จึงต้องคอยทำให้ตรงกับไฟล์ secret ด้วยมือ

## 8. การเชื่อมต่อข้อมูล — สี่ระดับของภาระงานในการนำไปใช้

บทนี้คือบทที่กำหนดแผนงานของโครงการท่าน แค็ตตาล็อกแหล่งข้อมูลอยู่ที่ `packages/shared/src/ingestion/catalog.ts` — **39 รายการ โดย 5 รายการเลิกใช้แล้ว** ตัว connector อยู่ใต้ `apps/ingestion/src/connectors/sources/` และตารางกำหนดเส้นทาง mock↔real คือ `apps/ingestion/src/connectors/registry.ts`

ระดับด้านล่างจัดเรียงทุกแหล่งข้อมูลตามปริมาณงานที่ *ท่าน* ต้องลง ไม่ใช่ตามความสำคัญ

### Tier 1 — ใช้ได้แทบทันที: ตระกูล MHESI UniCon DS

มหาวิทยาลัยไทยทุกแห่งส่งชุดข้อมูล UniCon DS ให้ อว. โดยใช้ **schema เดียวกัน** นั่นหมายความว่า SQL projection ความหมายของคอลัมน์ การจัดการวันที่แบบพุทธศักราช และแนวปฏิบัติต่อข้อมูลส่วนบุคคลใน connector ทั้งสี่ตัวนี้ ถ่ายโอนมาใช้ได้โดยตรง

| Slug | แหล่งข้อมูลในระบบของ มข. | จำนวนแถวใน snapshot ของ มข. |
|---|---|---|
| `unicon-ds1001` | `mysql://…/reg_unicon.view_ds1001` | 35,406 (ปีการศึกษา 2568 ภาคเรียนที่ 2) |
| `unicon-ds2001` | `mysql://…/UNICON_STAFF_KKU.DS2001` | 11,325 |
| `unicon-ds2003` | `mysql://…/UNICON_STAFF_KKU.DS2003` | 18,060 |
| `unicon-ds2004` | `mysql://…/reg_unicon.ds2004_<YYSEM>` | หนึ่งแถวต่อ (บุคลากร × หลักสูตร × ประเภทการสอน) |

**สิ่งที่ท่านต้องเปลี่ยน:** รายละเอียดการเชื่อมต่อ ผ่านคำนำหน้าตัวแปร environment `UNICON_DS1001_DB_*` / `UNICON_DS2001_DB_*` / `UNICON_DS2003_DB_*` / `UNICON_DS2004_DB_*` ซึ่งอ่านผ่าน `configFromEnv()` ใน `apps/ingestion/src/lib/mysql-client.ts` โปรดสังเกตว่าในระบบของ มข. DS1001 จงใจใช้ข้อมูลรับรองของ DS2004 ซ้ำ เพราะเป็น MySQL endpoint เดียวกัน — ให้ตรวจสอบว่าที่สถาบันของท่านเป็นเช่นนั้นหรือไม่

**สิ่งที่ท่านอาจยังต้องแตะอยู่ดี:**

- **ธรรมเนียมการตั้งชื่อตารางของ DS2004** ตาราง snapshot ของ มข. ตั้งชื่อว่า `ds2004_<YYSEM>` โดยใช้เลขสองหลักท้ายของปี พ.ศ. ตามด้วยภาคการศึกษา (`682` = ปีการศึกษา 2568 ภาคเรียนที่ 2) ตัว connector หา `MAX(suffix)` ตอน runtime หากสำนักทะเบียนของท่านตั้งชื่อต่างออกไป ตรรกะการหาชื่อตารางนี้ต้องเปลี่ยน
- **การแปลงรหัสหน่วยงาน** `unicon-ds2001` แปลง `DEPARTMENT_ID` ห้าหลักของ DS2001 ไปเป็น `Faculty.id` ของท่าน โดย join ผ่าน `staff_program_assignment.fac_id` (ดู `buildDeptCodeToFacultyMap()` ในไฟล์นั้น) วิธีนี้ทำงานได้เพราะ DS2004 ได้เติมตารางเชื่อมนั้นด้วยรหัสคณะของ อว. ไว้แล้ว หากท่านยังไม่ได้รันการโหลด DS2004 ตัว DS2001 จะโหลดเข้ามาโดยมี `facultyId = null` — ตัว connector จะรายงานจำนวนรหัสที่แปลงไม่ได้ไว้ใน metadata แทนที่จะล้มเหลวไปเลย
- **การแปลง `CURR_ID` เป็นหลักสูตร** DS1001 และ DS2004 แปลงรหัสหลักสูตรของ อว. เทียบกับ `Program.mhesiCode` (โดยมี `ProgramMhesiAlias` เป็นทางสำรอง) ท่านต้อง seed หลักสูตรของท่านพร้อมรหัสหลักสูตร อว. เพื่อให้กลไกนี้ทำงาน ดู [บทที่ 10](#10-เอกสารหลักสูตรและ-pipeline-การสรุปด้วย-ai)
- **แนวปฏิบัติต่อข้อมูลส่วนบุคคล** SQL projection ของ connector แต่ละตัวคือเส้นแบ่งความไว้วางใจ และมีบันทึกไว้ในส่วนหัวของไฟล์ ว่าคอลัมน์ใดถูกตัดออกตั้งแต่ตอน projection คอลัมน์ใดถูก hash (`CITIZEN_ID` → `citizenIdHash` ผ่าน `hashCitizenId()`) และคอลัมน์ใดถูกลดความละเอียดเหลือระดับปี แนวปฏิบัติเหล่านี้ผ่านความเห็นชอบของเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) ของ มข. แล้ว **DPO ของท่านต้องให้ความเห็นชอบด้วยตนเองอีกครั้ง** อย่าถือว่าความเห็นชอบของ มข. โอนมาถึงท่านได้

**ประมาณการภาระงานตามจริง:** หนึ่งถึงสามวันต่อ connector หนึ่งตัว หากตาราง DS ของท่านอยู่ในที่ที่ท่านคาดไว้และท่านมีสิทธิ์อ่าน เวลาส่วนใหญ่หมดไปกับเรื่องข้อมูลรับรองและการเข้าถึงเครือข่าย ไม่ใช่การเขียนโค้ด

> **ข้อควรทราบ:** ไม่มีไฟล์ข้อกำหนด `docs/data-sources/unicon-*.md` สำหรับทั้งสี่ตัวนี้ ไดเรกทอรีข้อกำหนดรายแหล่งครอบคลุมเฉพาะแหล่งข้อมูลรุ่นเก่า ส่วน connector ตระกูล UniCon บันทึกตัวเองไว้ในส่วนหัวของไฟล์แทน ให้อ่านจากโค้ด

### Tier 2 — แหล่งข้อมูลระดับชาติและภายนอกที่ใช้ร่วมกัน: เหมือนกันทุกสถาบัน

แหล่งข้อมูลกลุ่มนี้อ่านจากแหล่งที่เหมือนกันไม่ว่าท่านจะเป็นมหาวิทยาลัยใด จึงต้องการเพียงข้อมูลรับรองหรือการบอกรับของสถาบัน ไม่ต้องเขียนใหม่

| Slug | คืออะไร | งานของท่าน |

## 9. สัญญาของ connector และวิธีเขียน connector

### Interface

นิยามไว้ใน `packages/shared/src/ingestion/types.ts` มีสี่เมธอด ซึ่ง runner เรียกตามลำดับนี้:

```
healthCheck(ctx) → HealthStatus          // can we reach the source at all?
fetch(ctx)       → RawRecord[]           // pull, unchanged, from upstream
transform(ctx, raw) → NormalizedRecord[] // map to our schema; 0..n per raw
load(ctx, normalized) → LoadResult       // write, idempotently
```

ประเภทของ record สามแบบ:

- `RawRecord` — `{ externalId, data: unknown, sourceTimestamp }` โดย `externalId` คือค่าที่ใช้เป็น key ในการตัดข้อมูลซ้ำข้ามการรันแต่ละครั้ง
- `NormalizedRecord` — `{ target, externalId, payload, freshnessDate, sourcePdfId? }` โดย `target` ระบุชื่อตารางปลายทาง
- `LoadResult` — `{ recordsFetched, recordsLoaded, recordsFailed, metadata }` โดยก้อน `metadata` จะไปแสดงที่ `/admin/data-sources/<slug>` และเป็นที่ที่ท่านใส่ตัวอย่างรหัสที่แปลงไม่ได้ จำนวนการกระจายตัว และอะไรก็ตามที่นักวิเคราะห์ต้องใช้ในการตรวจสอบ

### connector จริงหน้าตาเป็นอย่างไร

`apps/ingestion/src/connectors/sources/unicon-ds2001/connector.ts` มีความยาว 310 บรรทัด และเป็นไฟล์เดียวที่ควรอ่านที่สุด โดยรูปธรรม:

- `healthCheck` เปิดการเชื่อมต่อด้วย `configFromEnv('UNICON_DS2001_DB')` แล้วรัน `SELECT 1` จากนั้นคืนค่า `user@host:port/database` ที่แปลงแล้วไว้ในข้อความ เพื่อให้หน้า admin แสดงว่าระบบต่อไปยังที่ใดจริง ๆ
- `fetch` รัน projection คอลัมน์แบบระบุชัดหนึ่งชุด (ซึ่งคือเส้นแบ่งความไว้วางใจด้านข้อมูลส่วนบุคคล) แล้ว **ปฏิเสธที่จะทำงานต่อเมื่อได้ศูนย์แถว** — `throw new NonRetryableError('EMPTY_DATA', 'DS2001 returned 0 rows — refusing to wipe')` เรื่องนี้สำคัญเพราะ `load` ทำการแทนที่ snapshot ทั้งชุด การ fetch ที่ได้ข้อมูลว่างจึงจะลบ snapshot ทั้งก้อนทิ้ง ให้คัดลอกการ์ดตัวนี้ไปใช้
- `fetch` ยังเก็บค่าสรุปรายการรันไว้ที่ `this.runState` (จำนวนแยกตามประเภทบุคลากร ตามสัญชาติ และแถวที่ hash ไม่ได้) ซึ่งไปปรากฏใน `LoadResult.metadata`
- `transform` ทำการ hash `CITIZEN_ID` ที่เส้นแบ่ง และคืนค่า `[]` สำหรับแถวที่ทำ key ไม่ได้ โดยนับจำนวนแถวที่ hash ไม่ได้ไว้แทนที่จะทิ้งเงียบ ๆ
- `load` ลบแถวเดิมที่อยู่ในขอบเขต `(academicYear, semester)` เดียวกัน แล้ว insert เป็นก้อนละ 1,000 แถวผ่าน `createMany` พร้อมประทับ `ingestionRunId: ctx.runId` ลงทุกแถว **การประทับนี้เป็นสิ่งที่ต้องทำ** — ดู [กับดักที่ 2](#กับดักที่-2-realdatawhere--ส่วนที่ว่างเปล่าทั้งที่ฐานข้อมูลมีข้อมูลอยู่)

### รูปแบบ mock → real

ทุก slug ในแค็ตตาล็อกมี connector แบบ mock ส่วน implementation จริงจะถูกเพิ่มเข้าไปคู่กัน ไม่ใช่เขียนทับ โดย `apps/ingestion/src/connectors/registry.ts` เก็บตารางจับคู่ไว้:

```ts
{
  slug: 'kku-registry',
  mock: () => new KkuRegistryConnector(),
  real: () => new KkuRegistryRealConnector(),
}
```

การตัดสินโหมดอยู่ใน `packages/shared/src/ingestion/connector-mode.ts` โดยเงื่อนไขแรกที่ตรงเป็นผู้ชนะ:

1. `CONNECTOR_<SLUG>_MODE` — slug ตัวพิมพ์ใหญ่ อักขระที่ไม่ใช่ตัวอักษรหรือตัวเลขเปลี่ยนเป็น `_` (เช่น `CONNECTOR_KKU_REGISTRY_MODE=real`)
2. `CONNECTOR_MODE` — ค่าตั้งต้นทั้งระบบ
3. ค่าตั้งต้นสุดท้ายคือ `mocked`

หาก slug ใดถูกตั้งเป็น `real` แต่ไม่มี factory ชื่อ `real` ลงทะเบียนไว้ registry จะบันทึกคำเตือนเสียงดังและ **ถอยไปใช้ตัว mock แทน** ดังนั้นการเผลอเปลี่ยนค่า environment โดยยังไม่ได้เขียนคลาสจริง จะไม่ทำให้ระบบ ingestion ล่ม

**การ rollback คือ "ตั้งค่า environment กลับไปเป็น `mocked`" แล้วรีสตาร์ต worker** ไม่ต้องย้ายข้อมูล ไม่ต้องแก้ schema ให้รักษาคุณสมบัตินี้ไว้ในทุก connector ที่ท่านเขียน เพราะเป็นเหตุผลเดียวที่ทำให้เกตข้อ 11 ของรายการตรวจสอบความพร้อมผ่านได้เลย

### คู่มือปฏิบัติการต่อ connector หนึ่งตัว

`prompts/14-integration-session-template.md` (128 บรรทัด) คือคู่มือปฏิบัติการที่มีอยู่แล้ว และท่านควรใช้ตามนั้นทุกประการ ข้อที่ต่อรองไม่ได้ในคู่มือนั้นคือ:

- **หนึ่ง slug ต่อหนึ่ง session** ไม่ใช่สอง ไม่ใช่ครึ่งเดียว connector สองตัวหมายถึงสอง session ซึ่งอาจทำขนานกันได้ แต่ห้ามรวบเป็นครั้งเดียว
- **รายการตรวจสอบก่อนเริ่ม session ต้องให้เจ้าของข้อมูลทำให้เสร็จ** ก่อนเขียนโค้ดใด ๆ ได้แก่ ข้อกำหนดของแหล่งข้อมูลที่กรอกเกินกว่าแบบร่าง ข้อมูลรับรองอยู่ในที่เก็บความลับของ environment ปลายทางแล้ว ตัวอย่าง payload commit ไว้ใต้ `apps/ingestion/test/fixtures/<slug>/` (อย่างน้อยหนึ่งกรณีปกติและหนึ่งกรณีขอบ) เจ้าของข้อมูลยืนยันว่า endpoint เสถียร และมีลายเซ็นกำกับของ DPO หากเกี่ยวข้องกับข้อมูลส่วนบุคคล
- **เกณฑ์ผ่าน:** มีการรันสำเร็จอย่างน้อย **สามครั้ง** ที่มองเห็นได้ที่ `/admin/data-sources/<slug>` โดยไม่มีความล้มเหลวเลยตลอดสิบครั้งที่พยายาม พร้อมกับบันทึกลายนิ้วมือของการเบี่ยงเบน (จำนวนแถวและการกระจายตัวของฟิลด์สำคัญ) ไว้ในเอกสารข้อกำหนด
- **สิ่งที่อยู่นอกขอบเขตของ session แบบ connector อย่างชัดเจน:** การปรับเวอร์ชันระเบียบวิธี การเขียนข้อมูลลงตารางเชิงธุรกิจ และการแก้ UI แต่ละเรื่องเป็น session แยกต่างหาก

รัน connector โดยไม่ต้องผ่าน BullMQ ได้ด้วย `pnpm connector:run <slug>` — เป็นเส้นทางโค้ดเดียวกับที่ worker ใช้ แต่วนรอบพัฒนาได้เร็วกว่ามาก

### กฎเรื่องแฟล็ก `mocked` / `status`

เมื่อท่านเปลี่ยน connector ไปเป็นของจริง แถวใน `data_sources` ต้องอัปเดต **ทั้ง** `status` และ `mocked` พร้อมกันในคราวเดียว ทั้งสองเป็นคอลัมน์อิสระต่อกัน และ `status='real'` ไม่ได้แปลว่า `mocked=false` การทำผิดข้อนี้จะได้ UI ที่ว่างเปล่าทั้งที่เห็นแถวข้อมูลอยู่ใน SQL ชัด ๆ `pnpm data-sources:audit` มีไว้เพื่อจับความคลาดเคลื่อนแบบนี้โดยเฉพาะ ให้รันหลังการเปลี่ยน connector ทุกครั้ง และหลังการรีเซ็ตฐานข้อมูลทุกครั้ง

## 10. เอกสารหลักสูตรและ pipeline การสรุปด้วย AI

นี่คือวิธีที่กอง PDF เล่มหลักสูตรกลายเป็นข้อมูลหลักสูตรที่มีโครงสร้างและ query ได้ เป็นส่วนที่มีคุณค่าที่สุดส่วนหนึ่งของแพลตฟอร์ม และถ่ายโอนไปยังสถาบันของท่านได้แทบไม่ต้องแก้อะไร

### กระแสการทำงาน

```
Curriculum PDF  →  MinIO + PdfDocument row (content-hash deduped)
                →  AI digest (program-digest.v1)
                →  AiExtraction row, PENDING_REVIEW
                →  human approval
                →  materialised onto Program + ProgramSkill rows
                →  unmatched skill names → PROPOSED_SKILL queue
```

### คำสั่ง

| คำสั่ง | วัตถุประสงค์ |
|---|---|
| `pnpm pdf:bulk-load <manifest.jsonl>` | การนำเข้าข้อมูลย้อนหลังครั้งเดียว ค่าตั้งต้นเป็น dry-run ใช้ `--commit` เพื่ออัปโหลดจริง |
| `pnpm programs:digest <code\|mhesi\|seq>` | สรุปหลักสูตรหนึ่งหลักสูตร |
| `pnpm programs:digest-bulk [--limit N] [--level X]` | ทำเป็นชุด พร้อมการทำงานต่อจากจุดเดิมอัตโนมัติ |
| `pnpm programs:approve-pending` | อนุมัติและเขียนข้อมูลของทุกรายการสรุปที่รออยู่ |
| `pnpm programs:pipeline <code>` | pipeline รายหลักสูตรฉบับเต็ม (ดูด้านล่าง) |
| `/admin/programs/[id]?tab=files` | แนบ PDF ผ่านหน้า UI |

ให้แนบ PDF ผ่านหน้า UI หรือผ่าน `pdf:bulk-load` ก่อนหน้านี้ มข. เคยมีตัวจับคู่ชื่อไฟล์แบบ fuzzy สำหรับเชื่อม PDF ที่ไม่มีเจ้าของเข้ากับหลักสูตร **แต่ถูกเลิกใช้ไปหลังจากมันเชื่อมผิดไปราว 30 หลักสูตร** ซึ่งต้องมาไล่แก้ด้วยการตรวจสอบจากเนื้อหาในภายหลัง อย่าสร้างมันขึ้นมาใหม่

### pipeline ฉบับเต็ม

`pnpm programs:pipeline <code|seq|id>` (หรือ `--all [--limit=N]`) ประกอบสิ่งที่เคยเป็นสคริปต์ที่ต้องรันเองเก้าตัวเข้าด้วยกัน ตามลำดับการพึ่งพา ให้อ่านส่วนหัวของ `apps/ingestion/src/scripts/programs-pipeline.ts` เพื่อดูฉบับที่เป็นทางการ โดยสรุปคือ:

| เฟส | ทำอะไร | หมายเหตุ |
|---|---|---|
| 1 | การสกัดข้อมูลจาก PDF ด้วย AI — สรุปเล่ม อาจารย์ ทักษะ รูปแบบการสอน | ทำงานขนานกัน |
| 2 | อนุมัติและเขียนข้อมูลสรุปลง `ProgramSkill` | ทำเฉพาะในฐานข้อมูล เร็ว |
| 2b | การสกัดรหัสรายวิชาแบบเจาะจง | แทนที่รายการรายวิชาที่ถูกตัดทอนในตัวสรุป ด้วยรายการเต็ม 40–90 วิชา |
| 3 | การจับคู่เส้นทางอาชีพ การจับคู่อุปสงค์ | ทำตามลำดับ |
| 4 | การเชื่อมโยงข้อมูลสถาบัน — นักศึกษาแต่ละรุ่น ศิษย์เก่า ข้อมูลการเงิน | ขนานกัน และเรียกใช้แหล่งข้อมูลสำนักทะเบียน/การเงินของท่าน |
| 6 | การประเมินความพร้อมด้าน AI | **ทำงานก่อนเฟส 5** เพราะทั้งเฟส 5 และ 7 ใช้คะแนนจากเฟสนี้ |
| 5 | การเลือกคู่เทียบและการทบทวนโดยคู่เทียบ | ทำตามลำดับ |
| RE | ความเชี่ยวชาญด้านการวิจัย | **เพิ่มอย่างเดียว** ข้ามหากมีอยู่แล้ว ไม่มีการสร้างใหม่อัตโนมัติ |
| 7 | เรื่องเล่าเชิงกลยุทธ์ | ใช้ผลจากทุกเฟสก่อนหน้า |
| 8 | การวิเคราะห์ความเสี่ยง | คณิตศาสตร์เชิงกำหนดบวกกับเรื่องเล่า |

`--skip=phase4` คือแฟล็กที่ท่านต้องใช้เมื่อยังไม่ได้เชื่อมต่อ connector สำนักทะเบียน ส่วน `--only=phase5` ใช้รันเฟสเดียว

### ตัว prompt

อยู่ที่ `packages/shared/src/ai/prompts/program-digest.ts` เวอร์ชัน `program-digest.v1` เป็นการเรียกครั้งเดียวบนข้อความ PDF ทั้งเล่ม เพื่อผลิตข้อมูลสรุปที่มีโครงสร้าง 15 ฟิลด์ ได้แก่ ข้อมูลพื้นฐานของหลักสูตร รายการรายวิชาพร้อมหน่วยกิตและผลลัพธ์การเรียนรู้ ทักษะทั้งหมดที่หลักสูตรสร้างพร้อมน้ำหนักและข้อความอ้างอิงตามต้นฉบับ ข้อความประชาสัมพันธ์ภาษาไทยที่พร้อมใช้ เส้นทางอาชีพ ระดับความเชื่อมั่นที่โมเดลประเมินตนเอง และข้อควรระวัง

การเขียนข้อมูลลงฐานข้อมูล (`packages/db/src/program-digest-materialize.ts`) ใช้หลัก **ข้ามหากค่าที่ได้ว่าง** นั่นคือการสรุปซ้ำจะไม่เขียนทับค่าที่มนุษย์คัดกรองไว้ด้วยค่าว่าง ชื่อทักษะที่สกัดได้จะถูกจับคู่กับ `Skill.nameEn` (ตรงทุกตัวอักษรแบบไม่สนตัวพิมพ์) แล้วจึงกับ `Skill.nameTh` (ตรงทุกตัวอักษร) โดย **ไม่มีการจับคู่แบบ fuzzy** ชื่อที่จับคู่ไม่ได้จะกลายเป็นรายการสกัดชนิด `PROPOSED_SKILL` ให้นักวิเคราะห์ทบทวน ซึ่งเป็นวิธีที่ทำให้อนุกรมวิธานทักษะเติบโตขึ้นจากคำศัพท์ในหลักสูตรของท่านเอง แทนที่จะติดอยู่กับรายการ ESCO ที่มาจาก seed

### ต้นทุนที่ มข. จ่ายไป เพื่อให้ท่านตั้งงบได้

สรุปหลักสูตรไปแล้ว 228 จาก 297 หลักสูตร ต้นทุนราว **0.04 ดอลลาร์สหรัฐต่อการสรุปหนึ่งครั้ง รวมประมาณ 8.10 ดอลลาร์สหรัฐ** ตลอดหกรอบการลองใหม่ บนโมเดล Gemini อีก 69 หลักสูตรที่เหลือไม่มี PDF ให้ใช้ ส่วนใหญ่เป็นหลักสูตรแพทย์เฉพาะทางและหลักสูตรที่เพิ่งเพิ่มเข้ามา ให้คาดหมายว่าท่านจะมีช่องว่างความครอบคลุมในลักษณะเดียวกัน และวางแผนงานจัดหาเอกสารแยกออกจากงานวิศวกรรม

### การออก PDF ภาษาไทยต้องใช้ TH Sarabun New

การ *ออก* PDF ทั้งหมด (Council Pack เอกสารสรุป บันทึกมติ) เรนเดอร์ผ่าน Gotenberg โดยฝังฟอนต์ TH Sarabun New ไฟล์ `.ttf` ทั้งสี่ไฟล์ **จงใจไม่เก็บไว้ใน git** และต้องนำไปวางไว้ที่ `infra/gotenberg/fonts/` ก่อนรัน `docker compose build gotenberg` ให้อ่าน `infra/gotenberg/README.md` เรื่องการจัดหาไฟล์ฟอนต์

สองเรื่องที่จะเล่นงานท่าน:

- การ build ด้วย Docker จะ **ล้มเหลวเสียงดัง** หากไม่มีฟอนต์ ทั้งจากการที่ `COPY` ยกเลิกการทำงาน และจากการตรวจนับจำนวนหน้าฟอนต์ Sarabun ที่ลงทะเบียนแล้วหลัง `fc-cache` นี่เป็นความตั้งใจ เพราะทางเลือกอีกทางคือการเงียบ ๆ แล้วเรนเดอร์เป็นกล่องสี่เหลี่ยมในเอกสารราชการ
- ฟอนต์ชื่อ **"Sarabun" บน Google Fonts เป็นคนละแบบอักษร** (ของ Cadson Demak) ไม่ใช่ TH Sarabun New และไม่เป็นไปตามข้อกำหนดของคณะรัฐมนตรีสำหรับเอกสารราชการ อย่านำมาใช้แทน

อย่าสร้าง PDF ในกระบวนการของแอปเองเป็นอันขาด ไม่ puppeteer ไม่ react-pdf ไม่ html-pdf — โดยเฉพาะ `@react-pdf/renderer` จัดการการวางรูปวรรณยุกต์ภาษาไทยผิดพลาด และถูกห้ามไว้อย่างชัดเจนใน codebase นี้ ทุกอย่างต้องผ่าน `PdfGenerationService` → Gotenberg โดย `docs/pdf-generation.md` มีสัญญาฉบับเต็ม

## 11. การปรับแบรนด์และ UI

### ระบบ token

Design token เก็บเป็น **ค่าสามตัวแบบ OKLCH** ใน `packages/design/src/css/tokens.css` โดยกำหนดขอบเขตไว้ใต้ `[data-theme='light']` และ `[data-theme='dark']` ส่วน utility ของ Tailwind ห่อค่าเหล่านี้ไว้เพื่อให้ตัวปรับค่าความโปร่งใสทำงานได้ (`bg-surface-1/80`)

`packages/design/src/tailwind-preset.ts` **แทนที่** สเกลสี ระยะห่าง ความมน ขนาดตัวอักษร และเงาของ Tailwind ทั้งชุด ไม่ใช่การขยายเพิ่ม ดังนั้น `bg-slate-500` จึงเป็น error ตอนคอมไพล์โดยเจตนา นอกจากนี้ ESLint ยังห้ามค่าสีแบบ hex ตรง ๆ และการเรียก `rgb()`/`oklch()` ด้วยตัวเลขตรง ๆ ผ่านกฎ `no-restricted-syntax` ใน `eslint.config.mjs` โดยอนุญาตเฉพาะการห่อรอบตัวแปร CSS

การสลับธีมทำผ่านแอตทริบิวต์ `data-theme` (ไม่ใช่คลาส `dark`) ผ่าน `next-themes` ที่ตั้งค่าให้ปลอดภัยกับ SSR จึงไม่มีอาการธีมผิดวาบขึ้นมาตอนโหลด

**การตั้งชื่อ token สำคัญกว่าที่เห็น** ธรรมเนียมคือ `--color-<family>-default` ไม่ใช่ `--color-<family>` เปล่า ๆ ชื่อที่ผิดจะไม่ถอยไปใช้ค่าสำรอง แต่จะเรนเดอร์เป็นกล่องดำใน SVG หรือเป็นสีดำใน HTML ให้ grep ดู `tokens.css` ก่อนคิดชื่อ token ขึ้นมาเอง เรื่องที่เกี่ยวข้องกัน: ใน SVG ให้ระบายสี `<text>` ผ่านแอตทริบิวต์ `fill=` แทนที่จะใช้ `style.fill`

### รายการตรวจสอบการปรับแบรนด์

| สินทรัพย์ | Path |
|---|---|

| Favicon | `apps/web/app/icon.png` — สร้างใหม่ด้วย `pnpm tsx scripts/build-favicon.ts` หลังเปลี่ยนโลโก้ |

**มีไฟล์ราว 101 ไฟล์ใต้ `apps/web` (`.ts`/`.tsx`) ที่อ้างถึง "KKU" หรือ "Khon Kaen"** ซึ่งมากกว่าที่ท่านจะเดา และรวมถึงข้อความบนหน้าจอ ข้อความสถานะว่าง ส่วนหัวของเทมเพลต PDF ข้อความ system prompt ของ AI และคอมเมนต์ ให้วางแผนกวาดล้างอย่างตั้งใจ และทำ *แต่เนิ่น ๆ* ก่อนที่ท่านจะเขียนโค้ดของตัวเองทับลงไป เพื่อให้ diff ยังตรวจทานได้

ขอแนะนำให้เปลี่ยนชื่อ `brand-cardinal` เป็นชื่อ token ที่เป็นกลาง (`brand-primary`) เป็นการปรับแบรนด์อย่างแรก เพราะจะทำให้การตัดสินใจเรื่องสีทุกครั้งหลังจากนั้นไม่ผูกกับสถาบันใด และตอนนี้ยังเป็นแค่การค้นหาแล้วแทนที่แบบกลไก ต่างจากการขุดค้นย้อนหลังในภายหลัง

### ชื่อผลิตภัณฑ์

ชื่อผลิตภัณฑ์ที่เป็นทางการคือ **"Program Landscape — KKU Curriculum Intelligence Platform"** (รูปแบบสั้น: *Program Landscape*) มีชื่อเก่าสามชื่อที่เลิกใช้แล้วและถูกกวาดออกจากข้อความที่ผู้ใช้มองเห็นทั้งหมด ได้แก่ *Curriculum Compass* และ *ทักษทัศน์* (ชื่อรหัสภายในเดิม โดยชื่อหลังไม่ใช่คำไทยที่มีความหมาย) และ *KKU Curriculum Landscape* (ชื่อผลิตภัณฑ์เดิม) ให้ถือว่าทั้งสามชื่อตายแล้ว หากท่านพบชื่อเหล่านี้ในคอมเมนต์หรือใน prompt เชิงประวัติศาสตร์ใต้ `prompts/` ให้ปล่อยไว้ในฐานะบันทึกทางประวัติศาสตร์ แต่อย่านำมาแสดงต่อผู้ใช้เป็นอันขาด ข้อความภาษาไทยไม่แปลชื่อผลิตภัณฑ์ แต่ใช้วิธีห่อชื่อภาษาอังกฤษไว้ในนามวลีภาษาไทย เช่น *แพลตฟอร์ม Program Landscape*

### กฎสามข้อสำหรับการเปลี่ยนระเบียบวิธี

1. **ปรับค่าคงที่เวอร์ชันเสมอ** `HEALTH_SCORE_VERSION = 'health-score.v4.0'` ใน `packages/db/src/health-score.ts` ถูกประทับลงบนแถวคะแนนทุกแถว การเปลี่ยนสูตรโดยไม่ปรับเวอร์ชันจะทำให้การเปรียบเทียบย้อนหลังผิดพลาดแบบเงียบ ๆ และทำลายร่องรอยการตรวจสอบที่ทำให้สมาชิกสภามหาวิทยาลัยถามได้ว่า "ทำไมคะแนนของหลักสูตรนี้ถึงเปลี่ยนไป"
2. **อัปเดตเอกสารใน commit เดียวกัน** เอกสารใต้ `docs/methodologies/` คือฉบับที่ใช้อ้างอิงว่าตัวเลขนั้นหมายถึงอะไร เอกสารที่ไม่ตรงกับโค้ดแย่กว่าการไม่มีเอกสารเลย
3. **ค่าว่างไม่เท่ากับศูนย์** กฎรากฐานของคะแนนสุขภาพหลักสูตร: ตัววัดที่ขาดหายไปจะถูก **ตัดออกจากการหาค่าเฉลี่ย** ไม่ใช่แทนที่ด้วย 0 หรือ 50 คะแนนทุกตัวมี `dataCompletenessPct` กำกับ และ UI แสดงค่าที่ขาดหายเป็น `—` อย่า "แก้" เรื่องนี้ เพราะการแทนที่ด้วยศูนย์คือการลงโทษหลักสูตรจากช่องว่างข้อมูลของท่านเอง ซึ่งเป็นรูปแบบความล้มเหลวที่ทำลายความเชื่อถือของสภามหาวิทยาลัยโดยตรง

### จุดที่น้ำหนักของท่านจะต่างออกไป

คะแนนสุขภาพหลักสูตรของ มข. ประกอบด้วยมิติต่าง ๆ (อุปสงค์ การเงิน คุณภาพ ความสอดคล้อง ขีดความสามารถ) โดยมีตัวขับอยู่ภายในแต่ละมิติ ตัวขับบางตัวถูกถ่วงน้ำหนักตามวิจารณญาณเชิงกลยุทธ์ของ มข. อย่างชัดเจน เช่น ตัวขับด้านอุปสงค์ที่ถ่วงน้ำหนักไว้สำหรับ "การเคลื่อนไปสู่การพัฒนากำลังคนแบบไม่รับปริญญา ซึ่งบีบหลักสูตรระดับบัณฑิตศึกษา" น้ำหนักเหล่านี้เป็น **จุดยืนของสภามหาวิทยาลัยขอนแก่น มิใช่ความจริงสากล** และท่านควรคาดหมายว่าจะต้องเปลี่ยน

รูปแบบการปรับที่ปลอดภัยคือ เพิ่มน้ำหนักของท่านเป็นเวอร์ชันใหม่คู่ขนานไปกับของ มข. แทนที่จะไปแก้ของเขาทับลงไป ท่านจะยังคงความสามารถในการ merge การเปลี่ยนแปลง *โครงสร้าง* ของสูตรจาก upstream ในขณะที่เป็นเจ้าของ *ค่าพารามิเตอร์* เอง

**ก่อนเปลี่ยนอะไรที่ข้ามโมดูล ให้อ่าน `docs/evaluation-pipeline.md`** เอกสารนั้นทำแผนที่ว่าคะแนนสุขภาพ วงจรชีวิต ความเสี่ยง KKU matrix และการให้คะแนน BCG มีปฏิสัมพันธ์กับ prompt ของ AI จำนวน 22 ตัวและชุดการ cross-join อย่างไร การเปลี่ยนน้ำหนักตัวเดียวโดด ๆ อาจทำให้หลักสูตรหนึ่งข้ามเส้นแบ่งควอดรันต์ BCG ไปในแบบที่ท่านไม่ได้ตั้งใจ

### การจัดสรรต้นทุนยังไม่เสร็จ — ที่ มข. ก็เช่นกัน

`docs/methodologies/cost-allocation.md` เป็น **ร่าง v0** ที่รอการอนุมัติจากคณะกรรมการการเงิน เอกสารนั้นวางกลุ่มต้นทุนห้ากลุ่มและสูตรแบบอิงกิจกรรมไว้แล้ว และ connector ก็ป้อนข้อมูลดิบเข้าไปแล้ว แต่ยังไม่มีตัวเลขต้นทุนรายหลักสูตรตัวใดที่นำเสนอต่อสภามหาวิทยาลัยได้ หากการวิเคราะห์ความยั่งยืนทางการเงินเป็นเรื่องเร่งด่วนของท่าน นี่คืองานที่ยังไม่เสร็จจริง ๆ ที่ท่านรับสืบทอดมา ไม่ใช่แค่ขั้นตอนการตั้งค่า

## 13. ชั้น AI

### ทุกอย่างวิ่งผ่าน `AiService`

`packages/shared/src/ai/` คือชั้นนามธรรม โมดูลต่าง ๆ จะไม่ import `@google/genai` หรือ `@anthropic-ai/sdk` โดยตรงเป็นอันขาด การเลือกผู้ให้บริการทำผ่าน `AI_PROVIDER`:

| ค่า | สถานะ |
|---|---|
| `google` | Gemini — ค่าตั้งต้น และเป็นตัวที่ pipeline หลักสูตรถูกปรับจูนไว้ให้ |
| `anthropic` | Claude — **จำเป็นสำหรับโมดูล AI Analyst** ซึ่งใช้ tool-use แบบเนทีฟ |
| `stub` | ค่าตัวแทนแบบกำหนดตายตัว ใช้ได้โดยไม่ต้องมี API key มีประโยชน์สำหรับการพัฒนาบนเครื่องท้องถิ่น |
| `openrouter`, `intelsphere` | เป็นโครงเปล่าที่ throw ตอนถูกเรียก — จงใจให้เสียงดัง ไม่ใช่ถอยไปใช้อย่างอื่นแบบเงียบ ๆ |

Gemini มี embeddings แต่ Claude ไม่มี ดังนั้นเมื่อ `AI_PROVIDER=anthropic` ตัว factory จะส่งต่อ `embed()` ไปยัง Google ให้โดยอัตโนมัติ หากท่านใช้ Claude ให้ตั้งค่า key ทั้งสองตัว

### prompt คือโค้ดที่กำกับเวอร์ชัน

`packages/shared/src/ai/prompts/` มีโมดูล prompt อยู่ราวสามสิบตัว แต่ละตัว export ค่าคงที่เวอร์ชัน Zod output schema และตัวสร้างข้อความ กฎข้อนี้เด็ดขาด: **การเปลี่ยนพฤติกรรมหมายถึงต้องมีเวอร์ชันใหม่ ห้ามแก้เวอร์ชันที่เผยแพร่แล้วทับลงไป** โดย `AiExtraction.methodVersion` บันทึกว่าเวอร์ชันใดผลิตแถวนั้นขึ้นมา ผลลัพธ์เก่าจึงยังแยกแยะได้ และการรันซ้ำยังตรวจสอบย้อนกลับได้

prompt ทุกตัวต้องเป็นไปตาม `docs/prompt-standard.md` ซึ่งประกาศใช้เมื่อ 2026-08-16 และ **บังคับใช้ด้วย ratchet test** ที่ `packages/shared/test/prompt-standard-conformance.test.ts` (ไฟล์ที่ยังไม่ได้เขียนใหม่อยู่ในรายการยกเว้นที่ระบุชัด ซึ่งมีแต่จะสั้นลง) กฎสำคัญของมาตรฐานนี้คือ:

- **ผลลัพธ์การวิเคราะห์ที่เป็นข้อความอิสระทั้งหมดต้องเป็นภาษาอังกฤษเท่านั้น** ข้อนี้กลับทิศจากกลยุทธ์เดิมที่ให้ภาษาไทยเป็นหลัก ภาษาไทยเหลืออยู่เฉพาะในรายการยกเว้นที่สรุปแล้ว ได้แก่ `recruitmentSummaryTh` ใน `program-digest` (เพราะเป็นข้อความประชาสัมพันธ์ ไม่ใช่บทวิเคราะห์) ฟิลด์สกัดข้อมูลตระกูล `nameTh` และทั้งหมดของ `evaluation-question-translate`
- **การอ้างอิงหลักฐาน:** ตัวเลขในผลลัพธ์ต้องสืบย้อนไปถึง snapshot ข้อมูลนำเข้าที่ส่งให้โมเดลในการเรียกครั้งนั้นได้ ห้ามใช้ตัวเลขที่โมเดล "รู้มา" เกี่ยวกับมหาวิทยาลัยของท่านหรือเกี่ยวกับอุดมศึกษาไทยโดยทั่วไป
- **ข้อมูลนำเข้าที่ขาดหายไปต้องไม่ถูกเดา** ให้แสดงว่า "ไม่มีข้อมูล" หรือ `null` อย่างชัดเจน ห้ามใส่ค่าตัวแทนที่ฟังดูสมเหตุสมผล และห้ามใช้ศูนย์แทนค่าที่ไม่ทราบ

### ธรรมาภิบาล

`@AiCall()` บนทุก endpoint ที่เรียกใช้ AI จะเขียนแถวลงตาราง `AiInference` ส่วน `@AuditLog()` บนทุกการเปลี่ยนแปลงข้อมูลจะเขียนแถวลง `AuditLog` decorator ทั้งสองตัวอยู่ใน `apps/api/src/common/decorators.ts` ต้นทุนถูกติดตามรายการเรียก (`AiInference.costEstimateUsd`) และมีตัวป้องกันโควตาค่าใช้จ่ายรายวันต่อผู้ใช้เป็นดอลลาร์สหรัฐ (`AiQuotaGuard`) ซึ่งตั้งค่าได้ผ่าน `AI_QUOTA_*_USD` และจะ *เปิดผ่าน* เมื่อเกิดข้อผิดพลาดกับฐานข้อมูล เพราะโควตาเป็นเรื่องธรรมาภิบาล ไม่ใช่เรื่องความมั่นคงปลอดภัย

มีชุดประเมินด้วยคำถามมาตรฐาน 25 ข้อ (`pnpm ai:eval`) และชุดวัดความแม่นยำ (`pnpm ai:eval-accuracy`) พร้อมป้ายกำกับใต้ `gold-labels/` ให้อ่าน `docs/ai-governance.md` เพื่อดูนโยบายฉบับเต็ม รวมถึงกฎการถอยไปใช้โมเดลสำรอง (เฉพาะข้อผิดพลาดชั่วคราว — 429/5xx/timeout ส่วนความล้มเหลวแบบกำหนดตายตัวจะ throw ต่อ) และตัวขัดกรองผลลัพธ์ที่ปกปิดเลขประจำตัวประชาชนไทย หมายเลขโทรศัพท์ และอีเมลที่ไม่ใช่ของสถาบัน ออกจากคำตอบของโมเดล

## 14. กับดักที่จะทำให้ท่านเสียเวลาหลายวัน

กับดักเหล่านี้ได้มาด้วยราคาแพง แต่ละข้อเคยก่อให้เกิดข้อบกพร่องจริงใน repository นี้

### กับดักที่ 1: สเกลระยะห่างของ Tailwind ในโครงการนี้เล็กเป็นครึ่งหนึ่ง และคีย์ที่ขาดหายจะไม่ออก CSS เลย

`packages/design/src/tokens/spacing.ts` **แทนที่** สเกลระยะห่างของ Tailwind และค่า `1` ของมันคือ **2px ไม่ใช่ 4px** ให้อ่านไฟล์นั้น คอมเมนต์ส่วนหัวของไฟล์คือคำอธิบายที่ดีที่สุดที่ท่านจะหาได้

ผลที่ตามมาสองข้อซึ่งเป็นอิสระต่อกัน:

- **ทุก utility ที่เกี่ยวกับระยะห่างจะได้ค่าครึ่งหนึ่งของที่นักพัฒนาที่คุ้นเคยกับ Tailwind คาดไว้** `h-4 w-4` บนไอคอน lucide จะเรนเดอร์ที่ **8px ไม่ใช่ 16px**
- **utility ที่มีคีย์ไม่อยู่ในสเกลจะไม่ออก CSS เลยแม้แต่บรรทัดเดียว** ไม่ใช่การถอยไปใช้ค่าสำรอง แต่คือไม่มีอะไรเลย `pl-9` คือ padding เท่ากับศูนย์ ส่วน `gap-1.5` เคยเป็น gap เท่ากับศูนย์แบบเงียบ ๆ จนกระทั่งมีการเพิ่มค่า `1.5` เข้าไป และ `h-3.5 w-3.5` ไม่ออก CSS เลย ไอคอนเหล่านั้นจึงถอยไปใช้ขนาดโดยธรรมชาติของ SVG ที่ 24×24

ค่า `3.5` นั้น **จงใจไม่มี และต้องไม่ถูก "เติมให้ครบ"** เพราะ 333 จาก 338 ที่ใช้ค่านี้คือ `h-3.5 w-3.5` บนไอคอน การนิยามค่านี้ขึ้นมาจะย่อองค์ประกอบราว 167 ชิ้นให้เหลือ 7×7 ในคราวเดียว

ทางแก้สำหรับไอคอนคือสเกล `iconSize` ที่แยกออกมาต่างหากใน `packages/design/src/tokens/icon.ts` ซึ่งเปิดใช้เป็น utility คลาสเดียว `size-icon-xs` … `size-icon-xl` (12/14/16/20/24px) **ให้ใช้ `size-icon-*` กับไอคอน และใช้สเกลระยะห่างกับกล่องเลย์เอาต์เท่านั้น**

อีกสองเรื่องเกี่ยวกับ preset นี้:

- **มันไม่ hot-reload** การเปลี่ยน token หมายถึงต้องรีสตาร์ต dev server
- **Next แคช CSS ที่คอมไพล์แล้วไว้ใน `.next/cache/webpack` ข้ามการรีสตาร์ต** หากการเปลี่ยน token ดูเหมือนไม่มีผลอะไร ให้ลบไดเรกทอรีนั้นก่อนจะไปไล่หาสาเหตุอื่นใด มิฉะนั้นท่านจะไล่จับผีอยู่ทั้งบ่าย

### กับดักที่ 2: `realDataWhere()` — ส่วนที่ว่างเปล่าทั้งที่ฐานข้อมูลมีข้อมูลอยู่

`packages/db/src/data-quality.ts` export ฟังก์ชัน `realDataWhere()` ปัจจุบันคือ `data-quality.v2` ในโหมด **STRICT** แถวข้อมูลตัววัดจะนับว่าเป็นข้อมูลจริงก็ต่อเมื่อ `DataSource` ของ `IngestionRun` ที่เชื่อมอยู่มีค่า `mocked = false` เท่านั้น ส่วนแถวที่มี `ingestion_run_id IS NULL` จะถือว่าน่าสงสัยและ **ถูกตัดออก**

ดังนั้น ส่วนหนึ่งของ UI จะแสดงว่างเปล่าทั้งที่มองเห็นแถวข้อมูลใน SQL ได้ จากสองสาเหตุที่เป็นอิสระต่อกัน:

1. `data_sources.mocked = true` — และโปรดสังเกตว่า `mocked` เป็น **คนละคอลัมน์กับ `status`** ค่า `status='real'` ไม่ได้แปลว่า `mocked=false` ให้เปลี่ยนทั้งสองเสมอ และเปลี่ยนพร้อมกันในคราวเดียว
2. `ingestion_run_id IS NULL` — มีเส้นทางการเขียนข้อมูลบางเส้นทางลืมส่ง `ctx.runId` ผ่านเข้าไป

SQL สำหรับตรวจสอบเบื้องต้น:

```sql
SELECT COUNT(*) FILTER (WHERE t.ingestion_run_id IS NOT NULL) AS tagged,
       COUNT(*) FILTER (WHERE ds.mocked = false)              AS pass
  FROM <table> t
  LEFT JOIN ingestion_runs ir ON ir.id = t.ingestion_run_id
  LEFT JOIN data_sources  ds ON ds.id = ir.data_source_id
 WHERE t.program_id = '...';
```

`pnpm provenance:backfill` (ค่าตั้งต้นเป็น dry-run) รายงานจำนวนแถวกำพร้าแยกตามตาราง ส่วน `pnpm data-sources:audit` จับความคลาดเคลื่อนระหว่าง `status` กับ `mocked` ให้รันทั้งสองตัวหลังการเปลี่ยน connector ทุกครั้ง และหลังการรีเซ็ตฐานข้อมูลทุกครั้ง

### กับดักที่ 3: บัญชี Oracle จะถูกล็อกเมื่อเปิดการเชื่อมต่อถี่เกินไป

บัญชี Oracle ของสำนักทะเบียน มข. จะล็อกผู้ใช้ทันที เมื่อสคริปต์เปิดการเชื่อมต่อใหม่ทุกครั้งที่เรียกใช้งานภายในลูป ให้ใช้ session เดียวต่อการรันหนึ่งครั้ง — codebase นี้มี `OracleSession` ไว้เพื่อการนี้โดยเฉพาะ และ `apps/ingestion/src/lib/oracle-client.ts` ห่อวงจรชีวิตของการเชื่อมต่อไว้ให้แล้ว อย่าใช้ `withConnection` ภายในลูป

เรื่องนี้ขยายเป็นหลักการทั่วไปได้: ฐานข้อมูลของสถาบันทุกระบบที่ท่านไปแตะ จะมีนโยบายจำกัดอัตราการเชื่อมต่อ ซึ่งท่านจะรู้ตัวก็ต่อเมื่อละเมิดมันไปแล้ว การ "ยิงก่อนแล้วค่อยถาม" เป็นลำดับที่ผิดในเรื่องนี้ เพราะบัญชีบริการที่ถูกล็อกหมายถึงการต้องไปคุยกับทีมโครงสร้างพื้นฐาน ไม่ใช่แค่การลองใหม่

### กับดักที่ 4: ไฟล์ `.env` ประจำแต่ละแอป และความล้มเหลวเงียบของ Edge middleware

Next.js โหลด `.env` จาก `apps/web/` เท่านั้น **ไม่เคย** โหลดจากรากของ monorepo เมื่อไฟล์นั้นหายไป bundle ของ middleware ที่รันบน Edge runtime จะถูกคอมไพล์โดยที่ `NEXTAUTH_SECRET` เป็น undefined และ **ทุก route ที่ต้องล็อกอินจะตอบ 307 กลับไปที่ `/signin`** ในขณะที่ Node runtime ซึ่งเป็นที่ที่การล็อกอินทำงานอยู่นั้นทำงานได้ปกติ อาการภายนอกดูเหมือนบั๊กของระบบ auth แต่แท้จริงคือบั๊กของการโหลดค่า environment

วิธีแก้: `pnpm link-env` และบน Windows ที่สคริปต์คัดลอกไฟล์แทนการทำ symlink ให้รันซ้ำหลังแก้ `.env` ที่รากทุกครั้ง

ข้อจำกัดทางสถาปัตยกรรมที่เกี่ยวข้อง: `apps/web/middleware.ts` ตรวจสอบ session cookie ด้วย `jose` โดยตรง และ **ต้องไม่ import `@/lib/auth`** (ซึ่งจะดึง Prisma เข้ามาและใช้ได้เฉพาะบน Node) การเพิ่มการเรียก Prisma เข้าไปใน middleware จะทำให้ build ของ Edge พัง

### กับดักที่ 5: barrel ของ `@kku/shared` ทำให้ `node:crypto` รั่วออกมา

`packages/shared/src/index.ts` re-export subpath ที่ import `node:crypto` (`pdf/hash.ts`, `ingestion/kmitl-token.ts`, `ai/providers/google-ai.ts`) ดังนั้น **client component ต้องใช้ `import type` เท่านั้น** เมื่อ import จาก `@kku/shared` เพราะการ import แบบ runtime จะทำให้ build พัง

หากท่านต้องการค่าที่ใช้ตอน runtime ใน client component ให้ import จาก subpath ที่เจาะจงแทนการ import จาก barrel หรือย้ายค่านั้นไปไว้ในโมดูลที่ปลอดภัยสำหรับฝั่ง client

### กับดักที่ 6: dev server ค้างข้อมูลเก่า สองแบบซ้อนกัน

มีบั๊กเรื่องข้อมูลค้างสองแบบที่แตกต่างกันแต่แสดงอาการเหมือนกันเป๊ะ คือ "สคริปต์ `tsx` ทำงานได้ แต่แอปที่รันอยู่ไม่ได้":

- **`next dev` ยังคงใช้ Prisma client ตัวเก่าหลังการเปลี่ยน schema** หาก query ที่รันด้วย `pnpm tsx` ใหม่สำเร็จ แต่ route บน dev ล้มเหลว ให้รีสตาร์ต dev server อย่าไล่หาสาเหตุต่อ
- **`nest start --watch` เฝ้าดูเฉพาะ `apps/api/src`** การแก้ไขใน `packages/db`, `packages/shared` และอื่น ๆ จะไม่ทำให้เกิดการโหลดใหม่ ให้รีสตาร์ต API

ทั้งสองกรณี สัญชาตญาณที่อยากจะไล่หาสาเหตุต่อคือสิ่งที่กินเวลาของท่าน

### กับดักที่ 7: อิมเมจคอนเทนเนอร์ที่ไม่ได้รันเป็น root กับสิทธิ์ความเป็นเจ้าของ volume

MinIO ใน production รันด้วย UID 65532 (อิมเมจที่ Chainguard สร้างใหม่ เพราะ `minio/minio` ต้นทางหมดอายุการสนับสนุนแล้ว) volume ข้อมูลต้องถูก chown ไปเป็น 65532 **บนเครื่อง host** เพราะการรัน `chown` ผ่าน compose จะติด EPERM ภายใต้ `cap_drop` และไฟล์ secret ต้องมีสิทธิ์ 0644 มิฉะนั้น MinIO จะวนล่มพร้อมข้อความ "Invalid credentials" สภาพแวดล้อม dev จะไม่มีวันทำให้เกิดปัญหานี้ซ้ำ เพราะ dev ใช้ข้อมูลรับรองจากตัวแปร environment และใช้ volume ที่มีสิทธิ์ถูกต้องอยู่แล้ว `scripts/deploy.sh` จัดการทั้งสองเรื่องให้แล้ว ให้อ่านสคริปต์นั้นก่อนที่ท่านจะเขียนเส้นทางการ deploy ของท่านเอง

นอกจากนี้ คอนเทนเนอร์ ingestion รันด้วย UID **1010** ในขณะที่ web และ api รันด้วย 1001 ดังนั้นคำสั่ง `user:` ระดับ compose ของ ingestion ต้องระบุเป็น `1010:1010`

### การทดสอบเหล่านี้ปกป้องอะไรอยู่จริง ๆ

ชุดการทดสอบนี้ให้น้ำหนักไปที่ **ฟังก์ชันบริสุทธิ์ที่มีเนื้อหาเชิงนโยบาย** มากกว่าความครอบคลุมแบบ integration อย่างผิดปกติ ได้แก่ กราฟการเปลี่ยนสถานะและการกั้นสิทธิ์ตามบทบาท การจัดการค่าว่างของคะแนนสุขภาพหลักสูตร การแปลงข้อมูลของ connector กรณีขอบเรื่องลำดับคำนำหน้าในการแปลงตำแหน่งทางวิชาการ ratchet test ของมาตรฐาน prompt โครงสร้างเกณฑ์ AUN-QA และรูปแบบการปฏิเสธเชิงความปลอดภัย นี่เป็นการเลือกโดยเจตนา เพราะจุดเหล่านี้คือจุดที่การถดถอยแบบเงียบ ๆ จะเปลี่ยนสิ่งที่สภามหาวิทยาลัยได้รับฟัง

เมื่อท่านเขียน connector ของท่านเอง ให้ทำตามรูปแบบที่มีอยู่ คือมี fixture ใต้ `apps/ingestion/test/fixtures/<slug>/` และมีการทดสอบ transform ที่ยืนยันว่าทุกรหัสใน fixture มีการจับคู่ไว้แล้ว การทดสอบความครอบคลุมของการจับคู่สถานะใน `kku-registry` คือต้นแบบ เพราะมันป้องกันกรณีที่สำนักทะเบียนเพิ่มรหัสสถานะใหม่มาเงียบ ๆ

### CI

`.github/workflows/` มีสี่ workflow ได้แก่ `pr.yml`, `release.yml`, `e2e.yml`, `load.yml`

`pr.yml` รันตัวตรวจ migration เพื่อหา DDL ที่ทำลายข้อมูล lint **เฉพาะไฟล์ที่เปลี่ยน** ตรวจสอบ type รัน Prisma generate เปิด Postgres พร้อม pgvector apply migration กับฐานข้อมูลทดสอบ และรันการทดสอบ

**สถานะที่ท่านรับสืบทอดมา:** `PR checks` เขียวตลอดเส้น ส่วน `Release bundle` (ทำงานเมื่อ push tag) รัน `pnpm lint` ทั่วทั้ง repository และ **แดงอยู่จากงาน lint ค้างเดิม** ไม่ใช่จากการเปลี่ยนแปลงรายใด ตัว tarball แบบ pack-and-ship ที่สร้างบนเครื่องท้องถิ่นคือ artifact ของการปล่อยเวอร์ชันตัวจริง ท่านอาจอยากเคลียร์งานค้างนั้นแต่เนิ่น ๆ เพื่อให้ป้าย CI สีแดงใน fork ของท่านมีความหมาย

## 16. การ deploy และการกำหนดขนาดโครงสร้างพื้นฐาน

### รูปแบบ: pack-and-ship

เซิร์ฟเวอร์ production **ไม่เคยดึงอิมเมจจาก registry** ท่าน build อิมเมจบนเครื่องพัฒนา มัดรวมเป็น tarball ไฟล์เดียว โอนย้ายไป แล้ว `docker load` บนเซิร์ฟเวอร์

```bash
# On the dev machine (inside WSL2 if on Windows)
pnpm build:release <version>
# → dist/program-landscape-<version>.tar.gz  (~2.5 GB)
# → dist/program-landscape-<version>.tar.gz.sha256
```

ตัว bundle ประกอบด้วย `images.tar` (4 อิมเมจ ทั้งหมดเป็น `linux/amd64`) ไฟล์ compose ไฟล์ตั้งค่า nginx สคริปต์การ deploy ยูนิต systemd และเทมเพลตไฟล์ environment ไม่มีอะไรอื่นที่ต้องเดินทางไปด้วย

**อิมเมจสำหรับ production ทั้งหมดเป็น `linux/amd64`** หากเครื่องพัฒนาของท่านเป็น Mac สถาปัตยกรรม ARM การ build ต้องส่ง `--platform linux/amd64` ด้วย

**ข้อควรระวังหนึ่งข้อของกระบวนการ build:** `docker buildx` รัน `COPY` ของแต่ละอิมเมจ ณ ตอนที่ stage นั้นทำงาน ดังนั้น commit ที่เข้ามาระหว่างการ build จะติดไปกับบางอิมเมจแต่ไม่ติดกับอิมเมจอื่น หาก fix ตัวใดต้องอยู่ใน bundle ให้หยุดการ build ทำ prune แล้วเริ่มใหม่

บนเซิร์ฟเวอร์ `scripts/deploy.sh` ทำงานซ้ำได้โดยผลลัพธ์เหมือนเดิม และทำการสลับ symlink แบบ atomic (`/opt/program-landscape/current → releases/<ver>`) เป็นจุดที่ย้อนกลับไม่ได้ ทุกอย่างก่อนหน้าจุดนั้นจะถูก rollback ให้อัตโนมัติเมื่อเกิดความล้มเหลว การรัน migration ทำใน **คอนเทนเนอร์แบบใช้แล้วทิ้ง** (`docker compose run --rm --entrypoint "" api node node_modules/.bin/prisma migrate deploy`) แทนที่จะทำจากคอนเทนเนอร์ API ที่รันอยู่ตลอด ซึ่งจะแย่งกันทำงานกับ ingestion ตอน startup

สคริปต์ที่ทำงานคู่กัน: `rollback.sh`, `backup.sh`, `restore.sh`, `smoke-test.sh`, `pre-deploy-snapshot.mjs`, `generate-self-signed-cert.sh`

การ rollback โดยค่าตั้งต้นจะ **ย้อนเฉพาะโค้ด** โดย `rollback.sh` จะถามว่าจะกู้คืน snapshot ฐานข้อมูลก่อน deploy หรือไม่ ซึ่งคำตอบตามปกติคือไม่ เพราะ migration เดินหน้าทางเดียวและการย้อนโค้ดยังเข้ากันได้กับ schema

### โครงสร้าง TLS

รูปแบบของ มข. ซึ่งมหาวิทยาลัยไทยส่วนใหญ่ทำตามได้:

```
public → university reverse proxy (terminates public cert)
       → re-encrypts, forwards to our host on :8443 (self-signed)
       → our internal nginx (TLS + path routing)
       → web / api over plain HTTP inside the docker network
```

reverse proxy ต้นทางตั้งค่าด้วย `proxy_ssl_verify off` (หรือการตรึงลายนิ้วมือใบรับรองแบบ SHA-256) มีรายละเอียดหนึ่งข้อของ nginx ที่จะเล่นงานท่านหากท่านสร้างไฟล์ตั้งค่าขึ้นใหม่: `next-auth` อยู่ที่ `/api/auth/*` บนแอป web ในขณะที่คำนำหน้าของ NestJS คือ `/api/v1` ท่านจึงต้องมีกฎ `location /api/auth/` → web อย่างชัดเจน มิฉะนั้นการ auth จะได้ 404 จาก router ของ Nest

Security header ถูกกำหนดที่ **ชั้นแอปพลิเคชัน** ไม่ใช่ที่ nginx จึงถูกต้องเสมอไม่ว่าคำขอจะวิ่งผ่าน proxy เส้นทางใด

`DEPLOYMENT.md` คือคู่มือปฏิบัติการ ส่วน `docs/deployment/kku-network-integration.md` คือเอกสารที่ท่านส่งให้ทีมเครือข่ายของท่าน

| GPU | ไม่ต้องมี | ไม่ต้องมี | การประมวลผลของโมเดลทั้งหมดทำผ่าน API ของผู้ให้บริการ |

ให้อ่านส่วนที่เหลือของเอกสารนั้นเพื่อดูตารางข้อกำหนดเครือข่ายขาเข้าและขาออก ซึ่งระบุปลายทางทุกแห่งที่เซิร์ฟเวอร์ต้องเข้าถึงได้ และเป็นสิ่งที่ทีมเครือข่ายของท่านจะถามหาพอดี

**สุขอนามัยของพื้นที่ดิสก์เป็นเรื่องปฏิบัติการที่สำคัญจริง ไม่ใช่เชิงอรรถ** เครื่องพัฒนาของ มข. เคยใช้พื้นที่ถึง 92% ระหว่างรอบการ build หลายครั้งติดกัน (แต่ละครั้งมี tarball ~2.5 GB บวกไดเรกทอรีเตรียมข้อมูล ~6 GB บวกแคชการ build ที่เรียกคืนได้อีก 14 GB) และเครื่อง production เคยเต็ม 100% ระหว่างการ deploy จากไฟล์สำรองข้อมูลเก่าที่สะสมไว้ กฎง่าย ๆ คือ เก็บ tarball ของการปล่อยเวอร์ชันสามรุ่นล่าสุดไว้บนเครื่อง dev และรัน `docker builder prune -af` หลังทุกรอบการปล่อยเวอร์ชัน เก็บไดเรกทอรีการปล่อยเวอร์ชัน ไฟล์สำรองข้อมูล และอิมเมจสามรุ่นล่าสุดไว้บน production และตรวจ `df -h /` **ก่อน** รัน `deploy.sh` เสมอ เพราะ snapshot ก่อน deploy ต้องการพื้นที่ว่างราว 3 GB

การสำรองข้อมูลกำหนดเวลาด้วย systemd (ทุกคืนเวลา 02:00 น. ตามเวลา Asia/Bangkok) ไม่ใช่ cron โดยไฟล์ยูนิตมาพร้อมกับ bundle ใต้ `infra/systemd/` นโยบายการเก็บรักษาคือ รายวัน 30 วัน ก่อน deploy 90 วัน และรายเดือน 365 วัน

## 17. PDPA และธรรมาภิบาล

**ระบบนี้จัดเก็บข้อมูลส่วนบุคคลของนักศึกษาและบุคลากร** ไม่ใช่แค่ข้อมูลรวมกลุ่ม แต่เป็นระเบียนรายบุคคล ได้แก่ เลขประจำตัวประชาชนที่ผ่านการ hash ชื่อ ปีเกิด ประวัติการจ้างงาน คุณวุฒิการศึกษา และผลการประเมินการสอน

### ความเห็นชอบของ มข. ไม่ได้โอนมาถึงท่าน

แนวปฏิบัติด้าน PDPA ที่บันทึกไว้ทั่ว codebase นี้ — การ projection คอลัมน์ใน connector แต่ละตัว การ hash ที่เส้นแบ่ง การปกปิดเซลล์ที่มีจำนวนน้อยด้วย `HAVING COUNT(*) >= 5` และการวิเคราะห์ฐานทางกฎหมายใน `docs/pdpa.md` — ได้รับความเห็นชอบจากเจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) **ของ มข.** สำหรับการประมวลผล **ของ มข.** เท่านั้น สถาบันของท่านเป็นผู้ควบคุมข้อมูลส่วนบุคคลแยกต่างหากตามพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 ท่านจึงต้องได้รับความเห็นชอบจาก DPO ของท่านเอง บนบัญชีรายการข้อมูลส่วนบุคคลของท่านเอง ก่อนที่ท่านจะประมวลผลสิ่งใด

`docs/pdpa.md` และ `docs/dsar-workflow.md` เป็น **จุดตั้งต้น** ของท่าน มิใช่ความเห็นชอบที่โอนมาได้ ให้อ่านทั้งสองฉบับในความหมายว่า "นี่คือการออกแบบที่ DPO ของมหาวิทยาลัยไทยแห่งหนึ่งเคยเห็นว่ายอมรับได้ และนี่คือเหตุผลประกอบ" แล้วให้ DPO ของท่านเองทบทวนเทียบกับสิ่งที่ท่านทำอยู่จริง

### เอกสารเหล่านั้นมีอะไรอยู่บ้าง

`docs/pdpa.md`: บทบาท (ผู้ควบคุมข้อมูลส่วนบุคคล/ผู้ประมวลผลข้อมูลส่วนบุคคล) บัญชีรายการข้อมูลส่วนบุคคล การวิเคราะห์ฐานทางกฎหมายรายประเภทข้อมูล วิธีรองรับสิทธิของเจ้าของข้อมูลส่วนบุคคลตามมาตรา 30–36 แต่ละสิทธิ การวิเคราะห์การส่งหรือโอนข้อมูลไปต่างประเทศ (ซึ่งเกี่ยวข้องเพราะการเรียกใช้ AI ทำให้ข้อมูลออกนอกประเทศไทย) ระยะเวลาเก็บรักษา audit log จุดตรวจการลดปริมาณข้อมูลให้น้อยที่สุด การรับมือเหตุละเมิด และการทบทวนประจำปี

`docs/dsar-workflow.md`: ขั้นตอนปฏิบัติสำหรับคำขอใช้สิทธิเข้าถึงข้อมูล ตั้งแต่การรับคำขอ ขั้นตอนการส่งออกข้อมูลโดยผู้ดูแลระบบ การพิสูจน์ตัวตน การขอแก้ไขข้อมูลให้ถูกต้อง การลบข้อมูล การคัดค้านการตัดสินใจโดยอัตโนมัติ และการเก็บบันทึกหลักฐาน

### การตัดสินใจเชิงออกแบบที่แบกน้ำหนักด้าน PDPA ไว้

ให้รักษาสิ่งเหล่านี้ไว้เมื่อท่านเขียน connector ของท่านเอง:

- **รวมกลุ่มข้อมูลตั้งแต่ที่ต้นทาง** คำสั่ง `GROUP BY` และ `HAVING` ใน SQL ทำงานบนเซิร์ฟเวอร์ต้นทาง ข้อมูลรายบุคคลจึงไม่เคยวิ่งข้ามสายมา
- **hash ที่เส้นแบ่ง** `hashCitizenId()` ทำงานใน `transform()` เลขประจำตัวประชาชนดิบจึงไม่เคยถูกบันทึกลงฐานข้อมูล
- **ลดความละเอียดของวันที่** วันเดือนปีเกิดถูกลดเหลือเพียงปีเกิด
- **ระบุคอลัมน์อย่างชัดเจน** connector ทุกตัวระบุรายชื่อคอลัมน์ของตน ไม่มีที่ใดใช้ `SELECT *` การ projection *คือ* เส้นแบ่งความไว้วางใจ และคอมเมนต์ส่วนหัวของ connector แต่ละตัวก็ระบุเรื่องนี้ไว้
- **ใช้บัญชีบริการที่มีสิทธิ์อ่านอย่างเดียว** ไม่ใช้บัญชีระดับ superuser เป็นอันขาด

การส่งหรือโอนข้อมูลไปต่างประเทศเป็นเรื่องที่ต้องให้ความสนใจเป็นพิเศษ เพราะการเรียกใช้ AI ทุกครั้งส่งข้อมูลไปยัง Google หรือ Anthropic นอกประเทศไทย โดย `docs/pdpa.md` § *Cross-border data transfer* ครอบคลุมการวิเคราะห์ของ มข. ไว้ DPO ของท่านอาจได้ข้อสรุปที่ต่างออกไป และหาก DPO กำหนดให้การประมวลผลของโมเดลต้องอยู่ในประเทศ ชั้นนามธรรม `AiService` คือจุดที่ท่านจะสลับผู้ให้บริการ แต่ขอให้ทราบว่าผู้ให้บริการอีกสองรายใน factory ที่ไม่ใช่ Google และ Anthropic นั้นเป็นโครงเปล่าที่ throw ออกมา งานส่วนนั้นจึงเป็นงานจริงจัง

### เกตความพร้อม

`docs/readiness-checklist.md` กำหนดเกตสิบสองข้อที่ผลลัพธ์ใด ๆ ต้องผ่านก่อนจะนำเสนอต่อสภามหาวิทยาลัยได้ การไม่ผ่านเกตข้อใดจะบล็อกผลลัพธ์ส่วนนั้นและแสดงแบนเนอร์ในแอป แทนที่จะปล่อยตัวเลขที่มีข้อจำกัดออกไปเงียบ ๆ **เกตข้อ 11** คือข้อที่สถาบันผู้นำไปใช้มักข้ามมากที่สุด นั่นคือ connector ตัวจริงต้องมี **ประวัติการรันสีเขียวต่อเนื่อง 30 วัน** ก่อนจะขับเคลื่อนตัวเลขที่นำเสนอต่อสภามหาวิทยาลัยได้ ให้วางแผนเผื่อความล่าช้านี้ไว้ แทนที่จะมาค้นพบเอาในสัปดาห์ก่อนการนำเสนอต่อสภาครั้งแรกของท่าน

## 18. การต่อยอดแพลตฟอร์มด้วย Claude Code

codebase นี้สร้างขึ้นด้วย Claude Code และข้อเท็จจริงนั้นกำหนดวิธีที่ท่านควรต่อยอดมัน หากท่านใช้ผู้ช่วย AI ในโครงการนี้ การตั้งค่าด้านล่างคือสิ่งที่ทำให้ผลลัพธ์ของมันสอดคล้องกับโค้ดที่มีอยู่ แทนที่จะเป็นกองงานที่ดูดีแต่ใช้ไม่ได้

### `CLAUDE.md` คือสัญญา

`CLAUDE.md` ที่รากของ repository ถูกอ่านทุกครั้งที่เริ่ม session ของ Claude Code นี่คือเหตุผลที่ AI ผลิตโค้ดที่สอดคล้องกันใน repository นี้ เพราะไฟล์นั้นบรรจุคำถามเชิงกลยุทธ์ รายการโมดูล กลยุทธ์ด้านภาษา ธรรมเนียมการเขียนโค้ด กฎความพร้อมสำหรับสภามหาวิทยาลัย รูปแบบการ deploy และบันทึกการตัดสินใจยาว ๆ ที่อธิบายว่า *ทำไม* สิ่งต่าง ๆ จึงเป็นอย่างที่เป็น

**ให้ fork ไฟล์นั้นและเขียนส่วนที่เป็นเรื่องเฉพาะสถาบันใหม่ก่อน session แรกของท่าน** โดยเฉพาะ:

| ส่วน | สิ่งที่ต้องทำ |
|---|---|
| คำอธิบายโครงการ กลุ่มเป้าหมาย | เขียนใหม่ให้ตรงกับสถาบันของท่าน |
| คำถามเชิงกลยุทธ์แปดข้อ | เขียนใหม่ — คำถามเหล่านี้เป็นคำถามของสภามหาวิทยาลัยขอนแก่น และเป็นกรอบที่กำหนดทุกการตัดสินใจเชิงวิเคราะห์ที่ตามมา |
| แปดโมดูล | คงไว้ เว้นแต่ท่านจะตัดโมดูลใดออก |
| กลยุทธ์ด้านภาษา | ทบทวน — UI เป็นภาษาอังกฤษล้วน และผลลัพธ์การวิเคราะห์เป็นภาษาอังกฤษล้วน โดยมีรายการยกเว้นภาษาไทยแคบ ๆ |
| ชื่อคณะ จำนวนหลักสูตร | แทนที่ |
| สถานะปัจจุบัน / บันทึกการตัดสินใจ | **ตัดให้เหลือเพียงตัวชี้ไปยังประวัติของ มข. แล้วเริ่มบันทึกของท่านเอง** อย่าแบกบันทึก session ของ มข. ขนาด 170 KB ติดตัวไป เพราะมันจะเบียดบริบทของท่านเองจนหมด |
| ธรรมเนียมการเขียนโค้ด รายการสิ่งที่ห้ามทำ | คงไว้ตามเดิมทุกตัวอักษร — นี่คือส่วนที่ทำให้ผลลัพธ์ของ AI สอดคล้องกัน |
| คำสั่ง run/test/lint และส่วนแพลตฟอร์ม | ปรับ path และชื่อโฮสต์ |

`prompts/CLAUDE.md.template` คือเทมเพลตต้นฉบับที่ใช้สร้างไฟล์นั้นขึ้นมา และเป็นจุดเริ่มต้นที่สะอาดกว่าไฟล์ขนาด 170 KB ในปัจจุบัน

ข้อสังเกตเกี่ยวกับบันทึกการตัดสินใจ: `CLAUDE.md` ของ มข. มีหมายเหตุที่ระบุด้วยตนเองว่าบันทึกกระโดดจาก v1.1.3 ไป v1.6.1 และงานช่วง v1.2–v1.6 นั้นส่งมอบไปแล้วแต่ไม่เคยถูกบันทึกไว้ ให้ถือว่าเป็นการบันทึกเท่าที่ทำได้ และให้ถือว่า `apps/web/app/changelog/page.tsx` คือประวัติการปล่อยเวอร์ชันฉบับที่เป็นทางการ

### `prompts/` คือคู่มือการสร้างฉบับดั้งเดิม

ไดเรกทอรี `prompts/` บรรจุ prompt ที่เรียงลำดับไว้ซึ่งสร้างแพลตฟอร์มนี้ขึ้นมา ตั้งแต่ prompt 00 (bootstrap) จนถึง prompt 13b (การ deploy) บวกกับ prompt 14 (การเชื่อมต่อข้อมูลจริง) ที่ยังดำเนินอยู่ ท่านคงไม่ได้จะไปรันมันซ้ำ แต่มันคือคำอธิบายที่ดีที่สุดเท่าที่มีว่า *ทำไม* ระบบย่อยแต่ละส่วนจึงมีรูปร่างเช่นนั้น ให้อ่านฉบับที่ตรงกับสิ่งที่ท่านกำลังจะแก้

`prompts/14-integration-session-template.md` คือเทมเพลต session รายตัว connector ที่ใช้งานอยู่จริง และท่านควรใช้มันกับ connector ทุกตัวที่ท่านเขียน ส่วน `prompts/GLOBAL-UPDATES.md` บรรจุข้อกำหนดที่ตัดขวางทุกโมดูล และ `prompts/TROUBLESHOOTING.md` รวบรวมรูปแบบความล้มเหลวที่ทราบแล้ว

### กฎประจำบ้านที่ทำให้ผลลัพธ์ของ AI สอดคล้องกัน

กฎเหล่านี้อยู่ใน `CLAUDE.md` และเป็นสิ่งที่ผู้ช่วย AI จะปฏิบัติตามหากท่านคงไว้ และจะละเมิดอย่างเงียบ ๆ หากท่านลบทิ้ง:

- TypeScript แบบ strict **ห้าม `any`**
- ตรวจสอบด้วย Zod ที่ทุกเส้นแบ่ง I/O ทั้ง request, response, ingestion และการสกัดข้อมูลด้วย AI
- ใช้ design token เท่านั้น ห้ามกำหนดสี ฟอนต์ หรือระยะห่างตรง ๆ (ESLint บังคับใช้)
- `@AuditLog()` บนทุกการเปลี่ยนแปลงข้อมูล และ `@AiCall()` บนทุกการเรียกใช้ AI
- ใช้ server component เป็นค่าตั้งต้น ใช้ client component เฉพาะเมื่อต้องการการโต้ตอบ
- ใช้ conventional commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`)
- รัน `pnpm check` ก่อน commit
- กำกับเวอร์ชันระเบียบวิธีบนทุกตัววัด
- ห้ามใช้ SQL ดิบ ยกเว้นผ่าน `$queryRaw` ของ Prisma พร้อมผลลัพธ์ที่ตรวจสอบด้วย Zod

### ชุด prompt สำหรับเริ่มต้น

**สิ่งที่ prompt นี้ทำ:** ตั้งค่าและรัน pipeline การนำเข้า PDF เล่มหลักสูตรของท่าน ตั้งแต่การสร้าง manifest แบบ JSONL สำหรับ `pnpm pdf:bulk-load` (โดย dry-run ก่อนเสมอ และห้ามสร้างตัวจับคู่ชื่อไฟล์แบบ fuzzy) การทดลองสรุปหลักสูตรสามหลักสูตรที่ต่างระดับกันเพื่อดูว่า `program-digest.v1` รองรับรูปแบบเอกสารหลักสูตรของท่านหรือไม่ ไปจนถึงการรันเป็นชุด การอนุมัติ และการรัน pipeline เต็มบนหลักสูตรเดียวโดยข้ามเฟส 4

> Set up and run the curriculum-PDF ingestion pipeline for our programmes.
>
> 1. Read `docs/pdf-ingestion.md` and the header of `apps/ingestion/src/scripts/programs-pipeline.ts`.
> 2. Build a JSONL manifest for `pnpm pdf:bulk-load` from our PDFs at [path], keyed on programme code. Dry-run first and show me the match rate and the unmatched list before committing anything. Do not build a fuzzy filename matcher — KKU retired theirs after it mislinked about 30 programmes; unmatched PDFs get attached by hand through `/admin/programs/[id]?tab=files`.
> 3. Run `pnpm programs:digest` on three programmes of different levels. Show me the extracted digest for each, and specifically: does `program-digest.v1` handle our curriculum document format, or does it assume KKU's layout? Report any prompt changes you would need — but do not edit a published prompt version in place; a behaviour change means a new version constant.
> 4. Once I approve the sample, run `pnpm programs:digest-bulk` and report cost, failure count, and per-failure reason.
> 5. Run `pnpm programs:approve-pending` and report how many skills matched our taxonomy versus landed in the `PROPOSED_SKILL` queue.
>
> Then run `pnpm programs:pipeline <code> --skip=phase4` on one programme end-to-end (skipping phase 4 because our registrar connectors are not wired yet) and show me the resulting Deep-Dive page.
>
> **Done when:** every programme with an available PDF has an approved digest; the `PROPOSED_SKILL` queue count is reported as an analyst worklist; and one programme's Deep-Dive renders with real extracted content rather than empty states.

**เสร็จเมื่อ:** ทุกหลักสูตรที่มี PDF มีรายการสรุปที่ผ่านการอนุมัติแล้ว มีการรายงานจำนวนคิว `PROPOSED_SKILL` ในฐานะรายการงานของนักวิเคราะห์ และหน้า Deep-Dive ของหลักสูตรหนึ่งแสดงเนื้อหาที่สกัดได้จริง แทนที่จะเป็นสถานะว่างเปล่า

### จุดที่การใช้ AI ช่วยจะผิดพลาดในโครงการนี้ — ขอให้เจาะจงเรื่องนี้

ผู้ช่วย AI เก่งจริงกับงานเชิงกลไกใน codebase นี้ ได้แก่ การเขียน connector โดยเทียบเคียงจากตัวที่มีอยู่ การกวาดเปลี่ยนชื่อข้ามไฟล์นับร้อย การเขียน transform test จาก fixture และการร่างเอกสาร ให้ใช้มันกับงานเหล่านั้น

แต่มัน **เชื่อถือไม่ได้ และมั่นใจผิด ๆ กับเรื่องที่คู่มือนี้ระบุว่าเป็นกับดักพอดี**:

- **สเกลระยะห่าง** AI ที่ผ่านการฝึกด้วย Tailwind จะเขียน `h-4 w-4` บนไอคอน และเขียน `pl-9` เป็น padding โดยไม่ลังเล ทั้งสองอย่างผิดในโครงการนี้ในลักษณะที่ไม่เกิด error ใด ๆ แต่ได้ผลลัพธ์ที่ขนาดผิด ข้อบกพร่องสองรายการที่แยกจากกันใน repository นี้เกิดจากเรื่องนี้พอดี ให้สั่งมันอ่าน `packages/design/src/tokens/spacing.ts` และ `icon.ts` ก่อนแตะ utility ใด ๆ ที่เกี่ยวกับระยะห่างหรือขนาด
- **การประทับ provenance** `ingestionRunId: ctx.runId` บนทุกแถวที่ insert เป็นสิ่งที่ลืมได้ง่าย และผลลัพธ์คือ UI ที่ว่างเปล่าแบบเงียบ ๆ แทนที่จะเป็น error ให้กำหนดเป็นเกณฑ์การยอมรับที่ระบุชัดใน prompt ของ connector ทุกตัว
- **การตัดสินใจเรื่อง schema** ว่าฟิลด์ใหม่ควรเป็นคอลัมน์ เป็นก้อน JSONB หรือเป็นตารางใหม่ migration นั้นเป็นแบบเพิ่มเข้าไปหรือแบบทำลายข้อมูล และ unique constraint มีปฏิสัมพันธ์กับความหมายของ NULL ใน Postgres อย่างไร เรื่องเหล่านี้ต้องใช้มนุษย์ codebase นี้มีคำตอบที่ได้มาด้วยราคาแพงอยู่แล้ว (เช่น การทำ upsert เองด้วย `findFirst → update | create` ในกรณีที่ compound unique key มีค่า NULL อยู่) ซึ่ง AI จะไม่คิดขึ้นมาใหม่ได้เอง
- **น้ำหนักในระเบียบวิธี** น้ำหนักเหล่านี้เข้ารหัสการตัดสินคุณค่าเชิงสถาบันว่าหลักสูตรใดสำคัญและเพราะอะไร AI จะผลิตน้ำหนักที่ดูสมเหตุสมผลออกมาได้ทันที และ "ดูสมเหตุสมผล" คือสิ่งที่ผิดที่สุดสำหรับตัวเลขที่จะใช้ปิดหลักสูตร
- **แนวปฏิบัติด้าน PDPA** AI จะเขียน `SELECT *` ให้อย่างเต็มใจ การ projection ทุกชุดคือเส้นแบ่งความไว้วางใจ และต้องผ่านการลงนามโดยมนุษย์ และโดย DPO ของท่าน ไม่ใช่โดยโมเดล
- **การ "แก้" สิ่งที่จงใจละไว้** ทั้งค่า `3.5` ในสเกลระยะห่างที่หายไป กฎค่าว่างไม่เท่ากับศูนย์ และรายการในแค็ตตาล็อกที่เลิกใช้แล้วแต่ยังคงไว้ — ทั้งหมดดูเหมือนบั๊กแต่ไม่ใช่ คอมเมนต์ในโค้ดอธิบายเหตุผลไว้แล้ว ให้แน่ใจว่า AI ได้อ่านคอมเมนต์เหล่านั้น

กฎที่ใช้ได้จริงคือ ปล่อยให้ AI เขียน แล้วท่านอ่านสิ่งที่มันเขียนในสี่หมวดข้างต้นด้วยตาตัวเองทุกครั้ง

- **Storybook ตั้งค่าไว้แล้วแต่ยังไม่มี story เลย** หน้า `/styleguide` ในแอป web ทำหน้าที่เป็นสัญญาเชิงภาพแทน

| 8 | การจัดหา PDF หลักสูตร และ pipeline การสรุปเอกสาร | 2–4 สัปดาห์ โดยการจัดหาเอกสารกินเวลาส่วนใหญ่ |
| 9 | การเขียนใหม่ Tier 3 ตัวแรก (สำนักทะเบียน ซึ่งส่งผลต่อระบบปลายทางมากที่สุด) | 2–4 สัปดาห์ |
| 10 | connector Tier 3 ที่เหลือ ตามลำดับความสำคัญ | ตัวละ 2–4 สัปดาห์ |
| 11 | การปรับระเบียบวิธีร่วมกับสภามหาวิทยาลัยหรือองค์กรเทียบเท่าของท่าน | 2–4 สัปดาห์ ส่วนใหญ่เป็นงานเชิงสถาบัน ไม่ใช่เชิงเทคนิค |
| 12 | การเชื่อมต่อ SSO การ deploy ขึ้น production และการประสานงานกับทีมเครือข่าย | 2–3 สัปดาห์ |
| 13 | การทบทวนและลงนามเห็นชอบโดย DPO | ทำคู่ขนานไปกับทุกอย่าง ให้เริ่มแต่เนิ่น ๆ |
| 14 | ช่วงประวัติการรันสีเขียว 30 วันต่อ connector หนึ่งตัว ก่อนนำไปใช้กับสภามหาวิทยาลัย | 30 วัน หลีกเลี่ยงไม่ได้ ให้วางแผนเผื่อไว้ |

**หมุดหมายที่ได้ผลลัพธ์ใช้งานได้จริงเป็นครั้งแรกตามความเป็นจริงคือสี่ถึงหกเดือน** โดยเวลาส่วนใหญ่หมดไปกับการเข้าถึงข้อมูลและการจัดหาเอกสาร ไม่ใช่งานวิศวกรรม งานวิศวกรรมนั้นเสร็จไปแล้วเป็นส่วนใหญ่ สิ่งที่ท่านได้จาก codebase นี้คือเดือนเหล่านั้น ไม่ใช่เดือนที่ตามมาหลังจากนั้น

**คำแนะนำเรื่องลำดับงานที่สำคัญกว่าตัวเลขประมาณการ:** ให้เริ่มยื่นขอสิทธิ์เข้าถึงทุกระบบตั้งแต่สัปดาห์แรก ก่อนที่ท่านจะเขียนโค้ดใด ๆ เพราะ connector หนึ่งตัวคืองานหนึ่งถึงสามวัน แต่ต้องรอบัญชีบริการอีกแปดสัปดาห์ ให้จัดลำดับคิวงานตามข้อเท็จจริงข้อนี้

หากท่านนำไปใช้ มข. จะได้ประโยชน์จากการรับทราบว่ามีอะไรพัง ท่านต้องเขียนอะไรใหม่บ้าง และอะไรที่ถ่ายโอนได้ดีหรือแย่กว่าที่คู่มือนี้คาดการณ์ไว้ โดยเฉพาะเรื่อง connector ตระกูล UniCon ซึ่งประสบการณ์ของมหาวิทยาลัยไทยทุกแห่งเทียบเคียงกันได้โดยตรง
