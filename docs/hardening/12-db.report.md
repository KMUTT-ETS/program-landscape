## 1. Migration linter (item 1)

### Implementation — `scripts/migration-linter.ts`

A pure-function `lintSql(file, sql)` core + a CLI shell. Detects 8 destructive patterns in `.sql` files and fails CI unless an explicit allow-annotation justifies the exception.

| Rule ID | Pattern | Why it's destructive |
|---|---|---|
| `drop-table` | `\bDROP\s+TABLE\b` | Destroys all rows. |
| `drop-column` | `\bDROP\s+COLUMN\b` | Destroys per-row data. |
| `rename-column` | `\bRENAME\s+COLUMN\b` | Atomically breaks every caller — no overlap window. |
| `rename-table` | `\bRENAME\s+TO\b` (table or type) | Same — atomic break. |
| `alter-column-type` | `\bALTER\s+COLUMN\s+"?\w+"?\s+(SET\s+DATA\s+)?TYPE\b` | Postgres rewrites every row + may be lossy. |
| `set-not-null-no-default` | `\bALTER\s+COLUMN\s+"?\w+"?\s+SET\s+NOT\s+NULL\b` (without a `DEFAULT` or `UPDATE` in the surrounding window) | Fails if any existing row is NULL. |
| `truncate` | `\bTRUNCATE\b` | Destroys all rows. |
| `drop-type` | `\bDROP\s+TYPE\b` | Destroys an enum/composite type. |

### Allow-annotation

```sql
-- migration-linter: allow-destructive (reason: <why>)
```

The `reason: ...` payload is **required** — the regex won't match an annotation without it, so a bare "allow-destructive" doesn't sneak through.

### CI wiring (`.github/workflows/pr.yml`)

A new `migration-linter` job runs **before** the heavy `lint-typecheck-test` job. ~30s end-to-end. PRs fail-fast on a destructive migration before spending 25 minutes on the rest of the suite.

```yaml
migration-linter:
  runs-on: ubuntu-latest
  timeout-minutes: 3
  steps:
    - uses: actions/checkout@v4
    - uses: pnpm/action-setup@v4 …
    - uses: actions/setup-node@v4 …
    - run: pnpm install --frozen-lockfile
    - run: pnpm tsx scripts/migration-linter.ts
```

### The lost-update fix — `decisions.service.updateStatus`

The classic **read-modify-write** hazard: `findUnique` → `assertTransitionAllowed(snapshot)` → `update`. Two concurrent calls could both pass the assertion against the same stale snapshot, then both write — second-write-wins semantics violate the workflow graph + lose audit trail.

Fix:

```ts
return prisma.$transaction(async (tx) => {
  const existing = await tx.councilDecision.findUnique({ ... });
  if (!existing) throw new NotFoundException();
  assertTransitionAllowed(existing.status, params.toStatus);
  assertTransitionAllowedForRole(params.toStatus, params.userRole);

  if (params.toStatus === 'COUNCIL_REVIEWED') {
    await captureSnapshot(params.decisionId, false);
  }

  // Compare-and-swap — only update if status STILL matches the
  // snapshot we read.
  const result = await tx.councilDecision.updateMany({
    where: { id: params.decisionId, status: existing.status },
    data: { status: params.toStatus },
  });
  if (result.count === 0) {
    throw new ApiError(
      'VALIDATION_FAILED',
      'Decision status changed concurrently — retry the request.',
      { decisionId: params.decisionId, expectedStatus: existing.status },
    );
  }
  return tx.councilDecision.findUniqueOrThrow({ where: { id: params.decisionId } });
});
```

Two layers:
1. **`$transaction` boundary** ensures the read + the conditional write live in the same Postgres MVCC snapshot.
2. **Conditional `updateMany` with `where: { id, status: existingStatus }`** — Postgres returns `count=0` if another transaction got there first. We surface a 409-equivalent `VALIDATION_FAILED` so the client can retry.

This is the textbook "compare-and-swap" pattern — equivalent to `SELECT ... FOR UPDATE` but cleaner because the lock is implicit in the row predicate.

### Other multi-write services — disposition

The other 7 services were inspected but **don't carry a lost-update risk**:

| Service | Why no transaction needed |
|---|---|
| `education-refresh.service.ts` | Each write is on a different cube row; cubes are partitioned by `(cube_name, refresh_id)` and never overlap. |
| `analyst.service.ts` | Each chat turn writes ≤2 rows (USER message + ASSISTANT message + optional ANALYST_FEEDBACK). The conversation row was already created in step 2 of the same call. No external concurrent writer. |
| `pdf-intake.service.ts` | PdfDocument upserts are content-hashed (`@unique` on `contentHash`); the upsert is atomic. State transitions (PENDING → DONE) are guarded by the BullMQ worker — only one worker per job. |
| `risks.service.ts` | Each call writes one risk_assessment row + N risk_measure rows; both keyed on a freshly-created assessment id. No racing reader. |
| `pdf.service.ts` | Each render writes one PdfGeneration row keyed on `id` (cuid). |
| `cockpit.service.ts` | SavedCockpitView writes are per-user, per-name; unique constraint on `(userId, name)` makes them idempotent. |
| `decision-review.service.ts` | Outcome-review rows are append-only (one per due-horizon). |

The audit + this disposition is the deliverable — wrapping every multi-write service in `$transaction` would add latency for zero safety gain.

## 3. Connection pool (item 3)

### Sizing math

Postgres `max_connections` defaults to **100** in the `postgis/postgis:16-3.4` image. Pool budget allocated:

| Service | Pool size | Rationale |
|---|---:|---|
| `api` | 10 | Concurrent HTTP traffic; mostly read-heavy. Burst-tolerant via the throttler chain (prompt 09). |
| `ingestion` | 8 | One connection per worker × 4 active queues × 2 concurrency. |
| `web` | 5 | Next server actions + the new `auth.signin` lockout queries. |
| Reserved (migrations + ad-hoc psql) | 5 | `prisma migrate deploy` runs in a one-shot container during deploy; a console session for ops debugging. |
| **Total** | **28** | Leaves ~72 of 100 as headroom. |

### Wiring

`.env.prod.example` updated:

```bash
DATABASE_URL=postgresql://kku_prod:REPLACE_ME@postgres:5432/program_landscape?schema=public&connection_limit=10
```

Per-service overrides happen at deploy time — operator copies `.env.prod.example` to `/opt/program-landscape/.env.prod` and tweaks the `connection_limit` query-string fragment per service.

### PgBouncer — deferred

Single-instance prod with a 100-connection ceiling and a 28-conn budget doesn't need PgBouncer. Tracked as the next reliability item if we scale to 3+ api replicas.

New `infra/postgres/init/02-tuning.sql` runs once at first volume init:

```sql
ALTER SYSTEM SET log_min_duration_statement = 250;  -- log statements ≥250ms
ALTER SYSTEM SET log_connections = on;
ALTER SYSTEM SET log_disconnections = on;
ALTER SYSTEM SET log_lock_waits = on;

ALTER SYSTEM SET log_temp_files = 0;            -- log every temp file
```

Logs land in stdout → captured by the json-file driver per `docker-compose.prod.yml` (50 MB × 5 files per service, prompt 07). Operator can `docker compose logs program-landscape-postgres | grep -i 'duration:'` to surface the slowest queries.

## 5. Snapshot drill (item 5)

### Bug found + fixed

`scripts/deploy.sh` lines 88-95 (before this prompt) **swallowed snapshot failures**:

```bash
sudo DEPLOY_ROOT="$DEPLOY_ROOT" "$RELEASE_DIR/scripts/backup.sh" "pre-deploy-$VERSION" || \
  log "WARNING: pre-deploy snapshot failed — continuing"
```

This violates the prompt's policy — and worse, hides the very condition the snapshot exists to protect against (a destructive migration with no restore point).

Fixed:

```bash
if [ "${SKIP_PRE_DEPLOY_SNAPSHOT:-0}" = "1" ]; then
  log "WARNING: SKIP_PRE_DEPLOY_SNAPSHOT=1 — NO RESTORE POINT IF MIGRATION FAILS."
else
  log "Taking pre-deploy DB snapshot (refuses to deploy on failure)"
  if [ ! -x "$RELEASE_DIR/scripts/backup.sh" ]; then
    fail "snapshot script $RELEASE_DIR/scripts/backup.sh not executable — cannot deploy without a restore point"
  fi
  sudo DEPLOY_ROOT="$DEPLOY_ROOT" "$RELEASE_DIR/scripts/backup.sh" "pre-deploy-$VERSION" || \
    fail "pre-deploy snapshot FAILED — refusing to deploy. Re-run after the DB is reachable, or set SKIP_PRE_DEPLOY_SNAPSHOT=1 (NOT RECOMMENDED)."
fi
```

The `SKIP_PRE_DEPLOY_SNAPSHOT=1` escape hatch is for the **first deploy** when there is no DB yet (pg_dump has nothing to dump). After the first successful deploy, never use it again.

### `backup.sh` — already restorable

`backup.sh` (verified, no change needed):
- Uses `pg_dump --format=custom --compress=9 --no-owner --no-acl` — restorable via `pg_restore`.
- `set -euo pipefail` so any sub-command failure exits non-zero.
- Has its own `fail()` function that prints to stderr + exits 1.

The chain is now: any `backup.sh` failure → propagates non-zero exit → `deploy.sh fail()` → deploy halts.
