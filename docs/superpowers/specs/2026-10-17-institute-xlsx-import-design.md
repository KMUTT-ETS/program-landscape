# Institute data import from spreadsheets

- **Date:** 2026-10-17
- **Status:** design complete; reviewed once; all open questions resolved (§11)
- **Branch:** `feat/institute-xlsx-import` (off `develop`)
- **Related:** `2026-10-15-white-label-organization-design.md` (branding; this document is its data counterpart)

## 1. Intent

Program Landscape is being adopted by universities other than KKU. The white-label
work lets an adopter set their name, logo and colours from an admin page. It
deliberately leaves the data out of scope, saying that another adopter "disables or
replaces" the `kku-*` connectors.

This document is how they replace them.

Nearly every institution-specific dataset behind the Program Deep-Dive is reachable
only through code: an Oracle or MSSQL connector pointed at KKU's own warehouse, a
script with a hardcoded path, or a constant in `prisma/seed.ts`. An adopter who
already holds the same figures in spreadsheets — which is the normal case — cannot
get them in. They would have to write a connector.

The goal is that an adopter with spreadsheets never edits code. They download a
template, fill it, upload it, and the Deep-Dive renders their data.

### Why now

The product is at the point of being handed to other institutions. Branding without
data is a demo. The Deep-Dive is the flagship surface and the one an evaluating
university will open first; today it renders almost entirely empty for anyone who is
not KKU.

## 2. Goals, non-goals, anti-goals

### Goals

| # | Goal |
|---|---|
| G1 | An adopter populates every institution-specific dataset the Deep-Dive reads, without editing code or the database. |
| G2 | Templates are generated by the application, so they cannot drift from the validator that accepts them. |
| G3 | A file is accepted or refused while the operator is still watching, with the offending rows named. |
| G4 | Re-uploading the same dataset next term updates what changed and leaves the rest alone. |
| G5 | Imported rows are visible — they carry provenance, and where canonicality is required they are canonical. |
| G6 | Adding the sixteenth dataset is a schema declaration, not another parser. |
| G7 | The KKU deployment behaves exactly as it does today. Connectors are untouched. |

### Non-goals

- Replacing the connectors. An institution with a warehouse keeps using one; upload
  is an alternative route to the same tables, not a migration.
- Importing data the Deep-Dive does not read.
- Editing individual rows through the UI. The file is the unit of work.
- Multi-tenancy. One institution per installation, as in the white-label design.
- Importing AI-derived tables (`ProgramSkill`, `ProgramFaculty`, `ProgramCourse`).
  These are extracted from each programme's curriculum PDF and that path already
  works for any adopter who has the PDFs.
- Alumni outcomes by individual graduate. Explicitly cut from this scope.

### Anti-goals

Things that would make this a failure even if it technically worked:

- **A file that imports halfway.** Partial success leaves the operator unable to tell
  what is in the system. A file is wholly accepted or wholly refused.
- **An upload that appears to succeed but renders nothing.** There are *two*
  independent ways to cause this and both must be handled:
  `realDataWhere()` excludes rows whose `ingestionRunId` is null (§6.5), and
  `IS_CANONICAL_PROGRAM` excludes programmes whose `sequenceNoFromSheet` is null
  (§6.8). Either one produces an upload that reports success, puts rows in the
  table, and leaves every section empty.
- **A template that no longer matches the validator.** The reason templates are
  generated rather than committed.
- **A destructive action reachable by routine use.** Deleting is a separate,
  deliberate act on a different screen.
- **A second registry for datasets that already have one.** §6.7.
- **An import that launders personal data into the system.** The connectors' privacy
  guarantees live in SQL that an uploaded file bypasses entirely (§7).

## 3. Constraints

- **`realDataWhere()` is strict.** `packages/db/src/data-quality.ts:51` returns
  `{ ingestionRun: { dataSource: { mocked: false } } }`. A null `ingestionRunId` is
  excluded. Every imported metric row must be attributed to an `IngestionRun`
  against a `DataSource` with `mocked = false`.
- **Canonicality is a second, independent filter.**
  `packages/db/src/canonical-programs.ts:18` defines
  `IS_CANONICAL_PROGRAM = { sequenceNoFromSheet: { not: null } }`, and Council
  surfaces enumerate through `withCanonical()`.
- **Three spreadsheet parsers already exist and none is reusable.** JobThai's
  fixed-7-column validator, the employment survey's fuzzy Thai header resolver, and a
  hand-rolled CSV parser for programmes. This design adds the first general one; it
  does not refactor those three.
- **`xlsx` is server-only.** `packages/shared/src/jobthai/index.ts:1` explains the
  rule: the guarantee is that the module stays out of every barrel. `xlsx@0.18.5` is
  a dependency of `apps/ingestion`, `apps/api` and `packages/shared`, and
  deliberately **not** of `apps/web`.
- **`packages/shared` has no `@prisma/client` dependency.** Anything naming
  `PrismaClient` cannot live there. This drives the placement in §6.1.
- **`apps/ingestion` is the sole BullMQ consumer.** `apps/api` enqueues only.
- **Roles are `SUPER_ADMIN | SYSTEM_ADMIN | UNIVERSITY_USER | FACULTY_USER |
  PROGRAM_USER`** (`packages/shared/src/auth/permissions.ts:246`). CLAUDE.md's
  `ANALYST`/`ADMIN`/`COUNCIL` vocabulary is stale and must not be used.
- **Org PII policy applies.** Raw national ID numbers, and names paired with a
  student or employee number, must never be written to output files, reports or
  logs. The importer's error messages are an output surface and are bound by this.
- **Conventions from `CLAUDE.md`:** no `any`, Zod at every I/O boundary, `@AuditLog()`
  on mutations, design tokens only, `path.join()` for paths, pnpm scripts not Make.

### 4.1 Decisions reversed during design, and why

Recorded because the reasoning matters more than the outcome.

**Scoped replace on the upload screen → rejected.** The first proposal gave the
upload a mode selector: upsert, or replace everything within the range the file
declares. Rejected because it puts a destructive control inside the one action
performed every term. Familiarity is what makes that dangerous; by the hundredth
upload nobody reads the selector. The realistic failure is someone exporting only
the current term, choosing replace meaning "refresh the current numbers", and losing
five years of history silently.

**Per-batch undo → rejected.** Removing a batch cleanly answers "delete the rows this
file created", but because uploads upsert, a bad file may have *overwritten* a good
row rather than inserted one. Undo would then need the previous value, which nothing
stores. Reverting correctly requires replaying the prior file — at which point
"start over and replay" is the simpler primitive, and the only one whose end state is
predictable.

**Start over, with every uploaded file retained → chosen.** Clearing a dataset and
replaying the files is explainable in one sentence and has no partial-state
reasoning. This makes file retention load-bearing: start-over is recoverable only
because the workbooks are kept, **and because the batch rows that name them survive**
(§6.6).

## 5. What is in scope

"Institution-specific" means the data describes this university and no other, so no
amount of public data substitutes for it.

### 5.1 Bridge tables are not needed

`RegistryProgramMapping`, `HrOrgMapping` and `AdmissionStatProgramMapping` translate
a *source system's* faculty and programme names into Program Landscape ids. They
exist because an Oracle view says `"คณะวิศวกรรมศาสตร์ | วศ.บ. โยธา | ปริญญาตรี | -"` and
something must map that to a programme id.

An uploaded sheet has no such problem: it names the programme by the code the
adopter themselves chose when they uploaded the Programme template. The reference is
direct. Bridge tables stay relevant only for adopters running connectors, which is
the KKU case and already works.

This removes three datasets from the inventory and, more importantly, removes the
chicken-and-egg problem of needing mappings before any data loads.

## 6. Design

### 6.1 One declaration per dataset, and where it lives

The whole design rests on this. Each importable dataset is declared once; template
generation, validation, the guide sheet, pre-fill and loading all read that
declaration.

**Placement.** The declaration carries `prefill` and `load`, which need
`PrismaClient`. `packages/shared` has no Prisma dependency and cannot host them.

The registry lives in **`packages/db/src/import/`**, which already depends on Prisma
and is where this repo keeps its database logic — `program-deep-dive.ts`,
`health-score.ts` and the rest sit beside it. It must not import `xlsx`. The
spreadsheet parser and the template writer, which do, live in
`apps/api/src/import/`.

Since §6.4 removed the queue, `apps/api` is the only caller today and could have
hosted the loaders. `packages/db` is still the right home: it matches where
comparable logic already lives, and it leaves the door open for a future dataset
that does need a worker, without moving the registry to get there.

```ts
interface ImportColumn {
  /** Exact header text in the data sheet. Matched literally, not fuzzily. */
  header: string;
  /** Machine key used in errors and in the loader's row type. */
  key: string;
  type: 'text' | 'integer' | 'decimal' | 'date' | 'boolean' | 'enum';
  required: boolean;
  enumValues?: readonly string[];
  /** Prose for the guide sheet. One or two sentences, plain language. */
  guide: string;
  /** Shown in the guide sheet's Example column. */
  example: string;
  /** Reference to another dataset's key; existence is checked at validation. */
  references?: { dataset: string; column: string };
  /** Marks a headcount column that gates k-anonymity on its row. See §7. */
  groupSizeFor?: { minimum: number };
}

/** How the loader finds an existing row. See §6.9. */
type ImportMatch =
  /** Prisma compound unique. Every component must be non-nullable. */
  | { kind: 'unique'; columns: readonly string[] }
  /** findFirst → update | create. For nullable components or absent constraints. */
  | { kind: 'manual'; columns: readonly string[]; fallback?: readonly string[] };

/**
 * How a file's rows relate to rows already held.
 * 'upsert'      — match and update, insert the rest, touch nothing else.
 * 'term-scoped' — the file declares a term; that term is replaced wholesale.
 *                 Not an operator choice: a fixed property of the dataset. See §6.11.
 */
type ImportStrategy =
  | { kind: 'upsert'; match: ImportMatch }
  | { kind: 'term-scoped'; termColumns: readonly string[]; match: ImportMatch };

interface ImportDataset {
  slug: string;                    // 'enrollment-metrics' — MUST match §6.7
  title: string;
  description: string;
  tier: 0 | 1 | 2;
  sheetName: string;
  columns: readonly ImportColumn[];
  /** Duplicate keys within one file are always an error, under either strategy. */
  strategy: ImportStrategy;
  prefill?: (prisma: PrismaClient, opts: PrefillOptions) => Promise<PrefillRows>;
  load: (ctx: ImportLoadContext, rows: readonly ImportRow[]) => Promise<ImportLoadResult>;
}
```

### 6.2 Template generation

`GET /api/v1/admin/imports/:dataset/template` returns a generated `.xlsx`:

- **Data sheet**, named per the declaration. Row 1 is the headers, in declared order.
  For tier 1 and 2, rows 2..n come from `prefill()` (§6.10) with value columns blank.
  For tier 0, headers only.
- **Guide sheet**, always named `Guide`. One row per column: Column, Required, Type,
  What to put, Example, Allowed values. A short preamble names the dataset, the key
  columns, and states that re-uploading updates matching rows.

The parser reads only the data sheet and ignores every other sheet, so the guide can
be as long as it needs to be, and an adopter may keep their own working sheets in the
same workbook.

Filename: `<slug>-template-YYYY-MM-DD.xlsx`.

### 6.3 Upload

`POST /api/v1/admin/imports/:dataset` — multipart, field `file`, mirroring the
JobThai controller. Limit 25 MB, as `JOBTHAI_MAX_UPLOAD_BYTES`.

Validation order, all before anything is written:

1. **File** — extension `.xlsx`, non-empty, within the size limit.
2. **Sheet** — the declared data sheet exists.
3. **Headers** — the set matches the declaration exactly. Missing columns are named.
   **Unknown columns are an error**, not ignored: a misspelled header would otherwise
   be silently dropped and read as an empty column, and an extra column of personal
   data would be silently accepted (§7).
4. **Cells** — type, required-ness, enum membership, per column.
5. **Key** — every key column present; no duplicate keys within the file.
6. **References** — every `references` value exists. A programme code not in the
   system is an error naming the code and the row.
7. **Privacy** — §7.
8. **Shrink guard** — if the file's row count is under half what the dataset
   currently holds, refuse, as the research-services connector does. Overridable by
   an explicit confirmation flag, surfaced in the UI as a second step. For a
   term-scoped dataset the comparison is **against the same term**, never the whole
   table; comparing one term against all of them would fire on every normal upload.

Any failure returns `400` with a structured list of
`{ sheet, row, column, message }`, capped at the first 100, with a total count.
**Nothing is stored and no `IngestionRun` is created.** Row numbers are spreadsheet
row numbers, so they match what the operator sees.

On success:

1. Content hash of the bytes. A hash already present **on a live batch** for this
   dataset returns the existing batch and reports it as a duplicate, loading nothing.
   Cleared batches do not block re-upload — that is how replay works (§6.6).
2. The file is put in MinIO, bucket `MINIO_BUCKET_CSV_UPLOADS`, key
   `imports/<dataset>/<hash>.xlsx`.
3. An `ImportBatch` row is created.
4. An `IngestionRun` is created against the dataset's `DataSource`, trigger `MANUAL`,
   `triggeredByUserId` set.
5. `load()` upserts every row, stamping `ingestionRunId`.
6. The run and the batch are completed with counts.

### 6.4 Everything is synchronous

Validation is synchronous — the operator is standing there, and JobThai's service
comment is right that failing asynchronously sends them to a job log.

Loading is synchronous too. **There is no queue and no worker.**

This was not the first plan. The draft had a row threshold above which the batch was
enqueued to BullMQ, driven entirely by `ClassOffering` at roughly 121,000 rows. Making
that dataset term-scoped (§6.11) cut the largest single file to about 12,000 rows and
changed the write from row-by-row upsert to delete-then-bulk-insert, which is a few
chunked statements. Nothing in scope now needs more than a few seconds.

What that removes is worth naming, because it is most of the complexity the draft
carried: a worker, a queue binding, a polling UI, batch states that mean "still
going", and the whole class of failures where a load dies after the request returned
and nobody is watching. A dataset that later needs queueing can have it; the
declaration interface does not change.

A guard belt remains: a file whose row count exceeds `IMPORT_MAX_ROWS`
(default 50,000) is refused with a message saying the dataset should be split — for
class offerings, by term. That is a real limit, not a fallback to async.

### 6.5 Provenance

One `DataSource` per importable dataset, slug `xlsx-<dataset>`, `mocked: false`,
`inputFormat: 'XLSX'`, `scheduleEnabled: false`, seeded from the import registry so
the registry stays the single source of truth.

This buys the per-dataset stats dashboard at `/admin/data-sources/[slug]` for free,
and keeps `realDataWhere()` working with no change to it.

An installation may legitimately have both a connector and an importer writing the
same table. Last writer wins, and the row's provenance shows which it was.

### 6.6 Start over

On each dataset's admin screen, not on the upload screen. Requires typing the dataset
name to confirm. `imports:destroy`, `@AuditLog({ action: 'import.start_over' })`.

**What it deletes.** Rows of that dataset whose `ingestionRunId` belongs to one of
the dataset's own import runs — never rows written by a connector, and never the
whole table. D17 adds the provenance column to the five tables that lack one
precisely so this scoping is possible everywhere.

**What it keeps.** The uploaded files in MinIO, *and* the `ImportBatch` rows that
name them. The batch is marked `CLEARED` rather than deleted. This is not tidiness:
`filename`, `storageKey`, `uploadedByUserId` and `createdAt` exist only on
`ImportBatch`, so deleting those rows would leave the MinIO objects as orphans under
hash-named keys, with nothing able to list them. The recovery story that justified
rejecting per-batch undo lives entirely in these rows.

The screen lists cleared batches with download links and a one-click re-upload, which
is why the dedupe check in §6.3 is scoped to live batches only.

**Cascade protection.** Starting over on a tier-0 dataset is refused while dependent
rows exist — clearing Programmes would cascade to every metric table. The message
names what depends on it and the order to clear in. This is deliberately more
annoying than the alternative, because "start over on Programmes" silently becoming
"wipe the installation" is the exact failure §4.1 argues against.

**Ordering.** Data rows before runs before batch status. The deferred evaluation and
DQ tables have non-null `ingestionRunId` with `onDelete: Restrict`, which makes
ordering a hard constraint rather than a nicety if they are ever brought into scope.

### 6.7 Admin UI — extend, do not duplicate

`/admin/data-setup` already exists and already is the index page this design needs:
`page.tsx:33` describes itself as the operational hub where every input category is a
card with current state and a link to its detail flow. More pointedly,
`/admin/data-setup/raw/[dataset]/page.tsx:33` already holds a per-dataset registry
with its own `ColumnSpec[]` — **keyed on the same slugs this design proposes**
(`enrollment-metrics`, `student-demographics`, `financial-metrics`,
`faculty-budgets`, `faculty-members`, `faculty-compensation`, `research-outputs`).

Standing a second registry beside it, on the same slugs, with a second column list,
is exactly the drift G2 exists to prevent — one level up. So:

- The import declaration becomes the **single** source for both. The raw viewer's
  `ColumnSpec` is derived from `ImportColumn`, not maintained alongside it.
- The dataset page at `/admin/data-setup/raw/[dataset]` gains the import affordances:
  download template, upload, batch list, start-over at the foot, visually separated.
- The `/admin/data-setup` index gains per-dataset import state and flags empty tier-0
  datasets, since nothing else can load until they are filled.
- No `/admin/data-import` section is created.

Reconciling the two column types is Phase 1 work and is the main reason Phase 1 is
not merely scaffolding.

Validation failures render as a table the operator can read against their
spreadsheet: row, column, what is wrong.

### 6.8 Programmes must be canonical

`IS_CANONICAL_PROGRAM` keys on `sequenceNoFromSheet IS NOT NULL`, and Council
surfaces enumerate through `withCanonical()`. A programme imported without one loads
successfully and is invisible everywhere that matters.

The importer therefore does what `programs.service.ts:534` already does: on insert,
assign the next sequence number; on upsert of an existing code, leave the existing
value alone. The comment there records that the master sheet was detached on
2026-07-08 and admin-created programmes are first-class — imported ones are the same
case.

`sequenceNoFromSheet` is `@unique`, so concurrent uploads can collide. Since D6
requires the whole file to succeed or fail, allocation happens inside the load
transaction and a collision retries the transaction rather than failing the upload.

It is **not** an import column. The adopter has no reason to care about it, and
exposing it would invite them to set it badly.

### 6.9 Matching, when the key is not a usable unique

`FacultyCompensation`'s key `(facultyId, departmentId, rank, fiscalYear)` has a
nullable `departmentId`. Postgres treats `NULL ≠ NULL` in unique indexes, so the
constraint does not enforce uniqueness for faculty-level rows, and Prisma's
compound-key `where` rejects a null component. The `kku-hr` connector already works
around this with `findFirst → update | create`.

`ResearchOutput` has the same problem for a different reason: its two unique
constraints are `(openalexId, facultyMemberId)` and `(scholarPaperId, facultyMemberId)`,
and an imported row carries neither id.

This is a framework capability, not a per-dataset quirk, which is why `ImportMatch`
is a discriminated union (§6.1) rather than a string array. Declarations choose
`unique` where a real compound unique exists and `manual` otherwise. Settling this in
Phase 1 is what makes G6 true.

### 6.10 Pre-fill

Pre-fill exists to stop the commonest error — a programme code typed or spelled in a
way the system does not recognise — by shipping the identifying columns already
correct.

Tier 1 and 2 templates are pre-filled with the cross product of **canonical active
programmes** and a **year range**. The range is the last five academic years ending
at the current one, read from the existing academic-year setting
(`/admin/app/academic-year`), not from the metric table — which on an adopter's first
day is empty, so enumerating "years already in the system" would yield nothing and
make the first upload hand-built. The template download accepts optional `fromYear`
and `toYear` parameters to widen it. **[mine]**

Datasets not keyed on a year (`FacultyMember`, `FacultyBudget`) pre-fill differently
or not at all, per their declaration.

### 6.11 Term-scoped datasets

Class offerings are the one dataset where upsert is the wrong shape. Its current
producer (`link-class-offerings.ts:285`) deletes the whole table and rebuilds it,
because the registrar's export is a statement of what exists, not a list of changes.
Upserting it would mean a section cancelled after the previous upload stays in the
system permanently, since nothing in the file says "this is gone".

So the dataset declares itself term-scoped. The workbook carries the academic year
and semester it covers — in the data columns, not a cover sheet, so the file is
self-describing and cannot be uploaded against the wrong term by mistake. Validation
requires every row to carry the same term and names any row that does not. Loading
deletes that term's rows and bulk-inserts the file's, in one transaction.

Three things follow, all of them simplifications:

- A term's contents are always exactly the last file uploaded for it. Stale rows
  cannot accumulate.
- The shrink guard compares like with like (§6.3 step 8).
- Delete-then-bulk-insert is fast enough to stay synchronous (§6.4).

**This is not the replace mode rejected in §4.1.** That was a toggle the operator
chose on every routine upload, where the danger was a familiar control doing
something destructive on the hundredth use. This is a fixed property of one dataset,
with no control in the UI at all: the operator picks a file and uploads it, exactly
as everywhere else. The scope comes from the file's own contents, not from a
decision made at upload time.

Instructor rosters (`ClassOfferingTeacher`) are **not** part of this dataset. They
key on instructor email, which is personal data the §7 rules do not cover, and the
Deep-Dive's GPA figures do not read them.

## 7. Privacy

This is the part a spreadsheet silently breaks.

The connectors do not protect personal data in application code. They protect it in
SQL, before anything is fetched:

- `kku-hr` aggregates salary with `HAVING COUNT(*) >= 5`, so no compensation figure
  describes fewer than five people.
- `kku-finance` aggregates tuition with `HAVING COUNT(DISTINCT STUDENTCODE) >= 5`.
- `kku-hr` and `kku-research-services` hash national ID numbers with SHA-256 **inside**
  SQL Server and MySQL respectively; the application never receives one.
- `kku-registry`'s PDPA posture is simply that its `GROUP BY` makes individual rows
  unreachable.
- `kku-research` deliberately omits `people.pid` from its projection.

An uploaded workbook has none of this. An adopter can quite reasonably type a
compensation row covering two people, or paste a column of national ID numbers,
and nothing in the current system would stop them.

So the importer re-imposes the rules itself:

1. **Unknown columns are rejected** (§6.3 step 3). This is the primary defence: a
   column the declaration does not describe cannot be imported, so an ID column
   pasted alongside the real data is refused rather than stored.
2. **Group-size gate.** A column declared `groupSizeFor: { minimum: 5 }` — the
   headcount on a compensation row — fails the file if any row is below it. The
   message names the rows and explains why, without quoting their contents.
3. **Pattern scan.** Any text cell matching a Thai national ID — 13 digits passing
   the mod-11 check, so long course and programme codes do not false-positive —
   fails the file. The message names the row and column and **does not echo the
   value**, per the org PII policy.
4. **No raw-ID columns exist.** Where a table stores a hashed identifier
   (`FacultyMember.citizenIdHash`), the template does not offer a raw column at all.
   Adopters needing identity matching supply their own employee code, which is not
   sensitive alone.

Error messages are an output surface. They name rows and columns; they never
reproduce cell values that triggered a privacy rule.

## 8. Migrations

All additive.

### 8.1 `ImportBatch` (new)

```prisma
model ImportBatch {
  id               String   @id @default(cuid())
  datasetSlug      String   @map("dataset_slug")
  filename         String
  contentHash      String   @map("content_hash")
  storageKey       String   @map("storage_key")
  fileSize         Int      @map("file_size")
  rowCount         Int      @map("row_count")
  status           ImportBatchStatus
  errorMessage     String?  @map("error_message")
  uploadedByUserId String?  @map("uploaded_by_user_id")
  ingestionRunId   String?  @map("ingestion_run_id")
  ingestionRun     IngestionRun? @relation(fields: [ingestionRunId], references: [id], onDelete: SetNull)
  clearedAt        DateTime? @map("cleared_at")
  createdAt        DateTime @default(now()) @map("created_at")

  @@unique([datasetSlug, contentHash])
  @@index([datasetSlug, createdAt])
  @@index([ingestionRunId])
  @@map("import_batches")
}

enum ImportBatchStatus { PENDING LOADING SUCCEEDED FAILED CLEARED }
```

The unique is on `(datasetSlug, contentHash)`, not the hash alone, so the same file
may legitimately be uploaded to two datasets. `CLEARED` is what makes replay possible
(§6.6) — the dedupe check in §6.3 ignores cleared rows.

### 8.2 Provenance columns (D17)

Add nullable `ingestionRunId` with `onDelete: SetNull` and an index to `Faculty`,
`Department`, `Program`, `FacultyMember`.

None of these is read by `realDataWhere()`, so adding the column changes no existing
behaviour. The importer stamps it; the connectors and seed are left alone, and a null
simply means "not written by an import". That is sufficient for start-over, which
only ever deletes rows it can positively attribute to one of its own runs.

### 8.3 `ResearchOutput` matching

No migration. The importer declares
`{ kind: 'manual', columns: ['doi', 'facultyMemberId'], fallback: ['title', 'year', 'facultyMemberId'] }`.
`doi` is indexed but not unique, which is why this is `manual` and not `unique`, and
why no constraint is added — one would conflict with existing connector-written rows.

## 9. Build order

The framework is the work; the datasets are declarations. Prove it on a thin slice
before declaring fourteen of anything.

**Phase 1 — framework and tier 0.** Declaration types including `ImportMatch` and
`ImportStrategy`, the generic parser and validator, template generation,
`ImportBatch`, the upload endpoint, start-over, and the reconciliation of the
existing `/admin/data-setup` registry with the new declaration (§6.7). Declarations
for Faculty, Department and Program, with canonicality (§6.8). At the end of this
phase an adopter can stand up an empty installation's org chart from three
spreadsheets, which is today impossible at any price.

Only the `upsert` strategy needs an implementation in this phase, but
`ImportStrategy` must be in the interface from the start — retrofitting a second
strategy after fourteen declarations exist is the kind of change this design is
meant to avoid.

**Phase 2 — tier 1.** The four core metric datasets, plus pre-fill, which first has
programmes to pre-fill from. At the end of this phase the Deep-Dive's students,
financials and outcomes sections render for an adopter. This is the proof that
provenance is right — if `realDataWhere()` is wrong, it shows here, loudly.

**Phase 3 — tier 2.** The remaining eight, as declarations, plus the `term-scoped`
strategy (§6.11) for class offerings.

Phase 1 and 2 are the deliverable that makes the product adoptable. Phase 3 is
completeness.

## 11. Questions raised in review, and how they were settled

**Class offerings — kept in scope, as a term-scoped dataset.**
The recommendation was to drop them and leave them to a connector, on the reasoning
that nobody maintains 121,000 rows of class sections by hand, so whoever can produce
the file can produce it from a database.

That reasoning was wrong, and the owner said so: **an adopter may have no registrar
database access at all.** Someone in the registrar runs a query and sends a
spreadsheet; the operator never gets credentials. Under that arrangement a connector
is not an available alternative at any price, and dropping the dataset would mean
telling those adopters the courses section simply does not work for them.

Keeping it required solving the three objections rather than avoiding them, which
§6.11 does by making the dataset term-scoped. The result is smaller than the design
that excluded it, because it also removed the queue (§6.4).

**Employer feedback — deferred.** No unique key, and no writer in any installation.
Importing it would mean adding a constraint and a provenance column to a table
nothing has ever written to. Revisit if an adopter asks.

**Teaching evaluations and digital competency — deferred.** Both sections stay blank
for an adopter. The review correctly found that the stated reason for deferring
`EvaluationQuestion` was wrong — its key is two columns and its provenance nullable,
so it is importable; it is simply useless without `EvaluationResponseSummary`, which
genuinely is awkward. The DQ cubes have no unique constraint at all and would need a
schema change before upsert means anything. §5.2 records this accurately now.

**Instructor rosters — deferred.** Split out of class offerings rather than folded
in, because they key on personal email addresses and the GPA figures do not need
them.
